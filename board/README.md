# Luna TUI (herdr plugin)

The plugin tile is `icon.png`, generated by `pnpm icons` from `scripts/mark.mjs` (study page: `design/icons/luna-tui.html`).

A lazygit-style view of the machine's tickets, for [herdr](https://herdr.dev/). Nine
columns named after the harness stages: Backlog, Intake, Triage, Approved, Build,
Verify, Evidence, Ship, Done. The board holds no state of its own: it reads and writes
through the machine's HTTP API at `../machine`, and follows its `/events` stream
for live updates.

Run the commands below from this `board/` folder, or use the `pnpm board:*`
scripts from the repo root. Start the machine first (`pnpm dev` from the repo
root) — the board still runs without it, but shows "machine offline" and retries
every 2s until it reconnects.

## Run it standalone

```sh
cargo run --release
```

The board connects to whichever machine is up: `pnpm dev`'s on `http://127.0.0.1:4317` first, then
`pnpm start`'s container on `:4318`. It checks again on every reconnect, so switching between
the two needs no restart. `HARDNESS_MACHINE_URL` pins one address instead.

## Install as a herdr plugin (local link)

```sh
pnpm board:link      # from the repo root: builds, then `herdr plugin link ./board`
herdr plugin action invoke hardness.board.open
```

Linking is a one-time step: herdr runs `target/release/hardness-board` from this folder, so a
later `pnpm board:build` is picked up the next time the pane opens.

Optional keybinding in your herdr config:

```toml
[[keys.command]]
key = "prefix+shift+b"
type = "plugin_action"
command = "hardness.board.open"
description = "open board"
```

## First launch: importing the old local board

If a `board.json` from an earlier version of this board is found (in the herdr
plugin state directory, or the current directory when run standalone), its
tickets are created on the machine once, then the file is renamed to
`board.json.imported` so the import never runs twice.

## Keys

Press `?` in the board for the full list. The main ones:

| Key | Action |
|---|---|
| `h` / `l`, `j` / `k` | move between columns and tickets |
| `enter` | open the ticket's workspace: a popup with a rail of sections (see below) |
| `=` | card density: three lines, four with `worked · diff · tests`, or one |
| `n` / `e` / `d` | new ticket, edit in place with vim-style keys (`i`/`a`/`o`… insert, `esc`/`q` back to normal, `ctrl+s` saves), delete (asks first) |
| `a` | advance: move a backlog ticket to intake, start it, approve a plan or tests, answer triage's questions, retry an escalation (with optional guidance; it resumes the stage it stopped in with a fresh retry budget), resume after a usage limit |
| `A` | memory review: approve without writing the proposed rules to `docs/agents/project-context.md` (`a` applies them) |
| `r` | send the plan or tests back, with a required reason |
| `X` | abort the running or paused stage (asks first) |
| `w` | kill the ticket's worktree once you are done with it (asks first); its branch and commits stay |
| `R` | search for a repo to set on the ticket, instead of typing a path |
| `f` | focus the agent's watch tab in herdr |
| `o` | open the linked GitHub issue in the browser |
| `/` / `!` / `@` | filter by title or `#id`; show only tickets that need you; show only this repo's tickets |
| `z` | fold: show every column at once, collapsing all but the focused one to its header bar |
| `F` | Floor: the machine's 7d and 30d metrics full screen (`r` refreshes, `esc` or `F` closes) |
| `P` | Pulls: every open PR involving you, split by what you do about it (see below) |
| `S` | Slack: your mentions, DMs, threads and watched handles, triaged and split by what you do about them (see below); `W` inside it edits the Watches |
| `x` | actions menu for the selected ticket |
| `q` | quit (closes a popup instead, if one is open) |

## Tickets

`enter` opens a ticket in a popup over the board. Inside it, a rail of eight sections on the
left (a tab strip on a terminal under 100 columns) and one pane on the right; `h`/`l` or `1`…`8`
switch, `j`/`k` scroll the pane or pick a row where the section lists some, `+` toggles the popup
between most of the screen and all of it. Every section draws from everything the machine knows
about the ticket, whether or not a gate was decided: the approved plan stays readable after `a`.
While a gate is open, its strip sits on top of every section with the keys that answer it.

| Section | Shows | Keys inside |
|---|---|---|
| Overview | the status, then one row per acceptance criterion with its state in the plan, how many cases prove it and what verifying found; repo, branch, issue, why, spend; the ticket's description and criteria; a setup gate's `luna.yaml` and proof, triage's questions, the memory review's rules | `e` edits the ticket's text |
| Plan | triage's latest plan (brief, criteria, assumptions, slices) and its history: send-backs with their reason, your edits, the approval | `e` edits brief, criteria and assumptions until Build starts; `a` / `r` at the gate |
| Tests | test_design's cases under the criterion each proves, with ✓ ✗ – from verifying | `e` edits the cases while they wait for your check (`## criterion`, `- case`, the approach under it) |
| Runs | every stage run with how long it took, its cost and turns; the selected run's error, per-case verdicts and files | `j`/`k` pick a run |
| Diff | the branch against its base: files with +/−, the selected file's patch | `j`/`k` pick a file |
| Evidence | the QA verdict and every artifact the stages produced, by kind | `j`/`k` pick a file |
| PR | the branch's pull request as the Pulls inbox sees it: checks by name, review state, threads, the task in flight; or the URL the ship gate reported | `o` opens it, `S` ships at the gate |
| Activity | every event | |

The popup opens on the section the open gate concerns: the Plan at `approve plan`, the Tests
at `check tests`, the Runs when escalated. `e` on the board (outside the popup) keeps its old
meaning: the two-pane plan editor at the plan gate, the ticket's text otherwise.

The plan editor splits into two columns: triage's plan on the left (brief, criteria to build,
assumptions; slices stay as triage wrote them), the ticket's own description and criteria on the
right. `tab` moves between the two while editing; `ctrl+s` saves whichever side changed. The plan
may be edited through the test check too, since nothing is built yet; each edit is kept as a
revision the Plan section's history shows. On a terminal narrower than 110 columns the two stack
instead, plan first. `n` fills a new ticket in as the same markdown `e` edits:

```markdown
# Login page

## Description

Users can sign in with email and password.

## Acceptance criteria

- Invalid password shows an error
- Successful login redirects to /home
```

Editing is vim-style modal, not a plain text box: it opens in normal mode
(`hjkl` to move, `dd`/`x` to delete, `u`/`ctrl+r` undo/redo), `i`/`a`/`o`/…
enter insert mode, `esc` goes back to normal. `ctrl+s` saves from either
mode; `esc` or `q` in normal mode cancels. Nothing opens outside the board
for this anymore — no `$EDITOR`, no second window to switch to.

The repo isn't part of this text — it's never typed freely, only set through
`R`'s search, so a stray edit can't silently blank it or point it somewhere
wrong. A new ticket's repo defaults to herdr's workspace, or the board's own
working directory when it runs standalone — either way, the nearest repo
root above it. `a` on a backlog or intake ticket with no repo set opens the
repo search instead of advancing, so you fix it before a stage runs. `R`
opens the same search anytime: type to filter, enter to set it — no path to
type or get wrong. It lists every repo under `HARDNESS_REPOS_DIR` (default
`~/Developer`), whether a repo sits directly under it or is grouped with
others under a project folder (`~/Developer/some-project/backend`,
`.../frontend`, both found). Triage's questions (`a` on a ticket awaiting
answers) still open in `$EDITOR`, pre-filled with its recommended answers —
that flow didn't move in place yet.

A new ticket starts in Backlog. `a` moves it to Intake (no stage runs, it's
just a deliberate "I'm shaping this one up" step); `a` again starts triage.

The board opens a herdr tab following each stage's agent (`docker logs -f` on
its container), whether the machine runs in Docker or on your host, and closes it
once the ticket is closed. Stages already running when the board starts get a tab
too. Tabs only open while a board is running. Approving the Ship gate (`a` on `awaiting_ship`)
pushes the task's branch and opens a real PR through the GitHub API — see the root
`README.md`'s "Shipping" section for what that needs.

## Tests

```sh
cargo test
```

Most of the board's logic only shows up when it is actually talking to a
running machine, so unit tests here are light (markdown parsing, timestamp
math). The real check is running it against the machine — see the repo root
`README.md`.

## Pulls

`P` opens the PR inbox: every open pull request on GitHub where your review is requested or that you authored, as the machine polls it every minute (`:prs` opens it too). Six splits, `h`/`l` or `1`–`6` between them, `j`/`k` down the rows, oldest first:

| Split | A PR lands here when |
|---|---|
| Review requested | a teammate's PR asks for your review |
| Ready to merge | yours, approved, every check green, mergeable, no unresolved threads |
| CI failed | yours, a check failed |
| CI running | yours, a check still running |
| Changes requested | yours, changes requested or review threads still open |
| Mine | everything else you authored, drafts included |

Review requested, Ready to merge, CI failed and Changes requested count on the Board tab's badge and raise a herdr notice when a PR moves into them.

| Key | Does |
|---|---|
| `m` | merge: squash and delete the branch, after one `y` (Ready to merge only) |
| `c` | CI fix: an agent diagnoses the red run; a fixable one is fixed, checked and pushed to the PR's branch |
| `v` | review: an agent reads the diff and posts line comments under your name right away; an approve or request-changes verdict waits at the Ship gate for `a` |
| `t` | threads: an agent answers every unresolved review thread on your PR, pushes, posts the replies and resolves the threads it settled |
| `o` / `enter` | open the PR in the browser / jump to its task on the board when one is running |
| `R` | poll GitHub now |
| `x` | the same actions as a menu, each saying why it is off when it is |

From 100 columns the view is a list beside a detail pane. A row reads `✓ ▌repo  #n  title  age  tag` in fixed columns, the checks glyph first (`✓` green, `✗` red, `◐` running), the repo's colour bar next (the same colour its cards wear), `⚙` while a task runs for it and `⌂` when the machine has no clone of the repo; only the title is ever cut. The pane shows the selected PR: author and branches, every check by name, the review state and unresolved threads, the task in flight, and the four keys with why each is off. Under 100 columns the pane hides and `x` shows the same detail over the list. A dispatch on such a PR opens the clone prompt: the same filter-as-you-type search `R` uses, over the folders under `HARDNESS_REPOS_DIR`; `enter` clones into `<folder>/<name>` and runs the action once it lands, `esc` leaves the row read-only. `c` and `t` are off on a fork head (nothing can push to it), `v` is off on your own PRs, and all three are off while a task already runs for the PR.

## Slack

`S` opens the Slack inbox (`:slack` too): everything your Activity tab shows plus the handles you watch, as the machine polls it every minute and a triage pass sorts it. Six splits, `h`/`l` or `1`–`6` between them, `j`/`k` down the rows. Needs reply and Decide go P0 first, then oldest; the other splits newest first.

| Split | An item lands here when |
|---|---|
| Needs reply | triage says a reply is expected and you have not replied |
| Waiting on them | you asked something in a thread and nobody answered |
| Decide | a decision or a blocker without an explicit question |
| FYI | everything P2/P3 that is not automated |
| Snoozed | you pressed `s`; it returns to its split when the timer ends |
| Done | you replied, pressed `d`, or made it a ticket |

A P0 or P1 entering Needs reply or Decide counts on the Board tab's badge and raises a herdr notice; so does any item whose thread moved after you cleared it (`Reopened`). Lower priorities and the other splits are quiet.

| Key | Does |
|---|---|
| `r` | reply: the editor opens with triage's draft (vim keys, like every editor); `ctrl+s` posts it as you in the thread, `esc` backs out; nothing is ever sent without the key |
| `t` | ticket: a Backlog task from the message and its thread, titled with the summary, in the repo the channel name matches; one `y` first, and the repo picker follows when none was guessed |
| `d` | done: clears the item here at once; Slack itself is not touched. If the thread moves afterwards the item comes back, re-triaged, with `new since you cleared it` in the pane |
| `s` | snooze: 1h, 3h, tomorrow 9:00 or next Monday 9:00 (your local 9:00) |
| `n` | nudge (Waiting on them only): the reply editor with a one-line reminder |
| `!` / `-` | priority up / down one step; re-triage keeps your value |
| `o` / `enter` | open the message in Slack / jump to its ticket on the board when it has one |
| `W` | Watches (below) |
| `R` | poll Slack now |
| `x` | the same actions as a menu, each saying why it is off when it is |

From 100 columns the view is a list beside a detail pane. A row reads `P0 ▌#channel  @author  summary  age  tag` in fixed columns: the priority first (`P0` red, `P1` yellow, `P3` muted), the channel's colour bar next (the same hue a repo of that name wears on the board), the author, triage's one-line summary (the only column ever cut; `×N` when a thread's mentions collapsed into one row), the age, then `⎇` for a thread, `⚙` once it is a ticket and `↺` when it came back after you cleared it. The pane shows where and who, the thread's last messages, the message itself, triage's verdict (`P0 · blocker · reply expected`), why, the links it found (with the linked PR's split from your Pulls inbox), the draft, and every key with why it is off. Under 100 columns the strip shortens its labels (`Reply`, `Wait`, `Snz`…), the pane hides and `x` shows the same detail over the list. The strip also says when Slack was last polled and, with an app token, whether the Socket Mode websocket is `live` or down.

Every item that expects a reply carries a due time under the reply SLA for its priority. The targets come from the rules file's `## SLA` section (defaults: P0 10m, P1 30m, P2 and P3 1h); the machine computes them, the board only shows them. The pane says `due      in 12m (P1 · 30m SLA)`, and within five minutes of it the row's age turns yellow. Past it the item is overdue: the row's summary and age go red, the tag leads with `‼`, it sorts to the top of Needs reply and Decide (the longest overdue first, ahead of P0), the strip counts them as `‼ N overdue`, the Board badge counts each one once whatever its priority, and a notice fires the moment it tips over (once; coming back inside the SLA is not news).

### Watches

A watch is anything beyond your own handle the inbox should treat as addressed to you: a user group (`@platform-team`), a broadcast (`@here`, `@channel`, `@everyone`; these ship on and can be switched off, not deleted), a keyword, or a whole channel. `W` opens them: `j`/`k` move, `space` switches one on or off, `e` cycles its priority floor (none, P0, P1, P2: an item matching the watch is at least that), `d` deletes, `n` adds. Type `@` to complete a user group, `#` to complete a channel, anything else is a keyword; `enter` saves it. Watches live in the machine, so every board shares them and triage reads them.

## Floor

`F` opens the Floor: one full-screen table with a 7d and a 30d column, read from the machine's `GET /metrics?since=7d|30d`. It shows tasks closed, created and open, what needs you, running and queued now, cycle time (median and p90), first-pass rate for verifying, ci_watch and implementing, escalation rate with the top reasons, retries per task, cost, and queue depth, slot use and utilisation. A per-stage table (runs, median, p90, cost) sits below it, or beside it on terminals 110 columns or wider. With the Slack inbox on, a Slack block sits under the stage table: items and replies by priority over 7d / 30d, how many of the 7d replies came inside their SLA (count and share), the median and p90 time to reply, the share answered within an hour, and the SLA targets in force as `10m/30m/1h/1h` (`GET /slack/metrics?since=7d|30d`); a machine without the inbox simply leaves it out. Numbers load when you open the view and again on `r`; if the machine is unreachable the error shows in the footer and the last numbers stay. Fold moved from `F` to `z` to make room.
