# Luna TUI (herdr plugin)

The plugin tile is `icon.png`, generated by `pnpm icons` from `scripts/mark.mjs` (study page: `design/icons/luna-tui.html`).

A lazygit-style view of the machine's tickets, for [herdr](https://herdr.dev/). Nine
columns named after the harness stages: Backlog, Intake, Triage, Approved, Build,
Verify, Evidence, Ship, Done. The board holds no state of its own: it reads and writes
through the machine's HTTP API at `../machine`, and follows its `/events` stream
for live updates.

Run the commands below from this `board/` folder, or use the `pnpm board:*`
scripts from the repo root. Start the machine first (`pnpm dev` from the repo
root) — the board still runs without it, but shows "machine offline" and retries
every 2s until it reconnects.

## Run it standalone

```sh
cargo run --release
```

The board connects to whichever machine is up: `pnpm dev`'s on `http://127.0.0.1:4317` first, then
`pnpm start`'s container on `:4318`. It checks again on every reconnect, so switching between
the two needs no restart. `HARDNESS_MACHINE_URL` pins one address instead.

## Install as a herdr plugin (local link)

```sh
pnpm board:link      # from the repo root: builds, then `herdr plugin link ./board`
herdr plugin action invoke hardness.board.open
```

Linking is a one-time step: herdr runs `target/release/hardness-board` from this folder, so a
later `pnpm board:build` is picked up the next time the pane opens.

Optional keybinding in your herdr config:

```toml
[[keys.command]]
key = "prefix+shift+b"
type = "plugin_action"
command = "hardness.board.open"
description = "open board"
```

## First launch: importing the old local board

If a `board.json` from an earlier version of this board is found (in the herdr
plugin state directory, or the current directory when run standalone), its
tickets are created on the machine once, then the file is renamed to
`board.json.imported` so the import never runs twice.

## Keys

Press `?` anywhere for the keys of what has the keyboard: the board, the ticket popup, the
Inbox, the Digest, the Floor, Pulls, Slack or its Watches. The sheet is read from one registry
(`src/keys.rs`) that the `x` menus, the `:` completion and the tables in this file
derive from too, so they cannot disagree. It knows the ticket under the cursor: the title names
it and its state, a key that works right now is bright with what it does (`a  approve the plan`
at the plan gate, `a  start` on a draft), a key that does not is dim with the reason (`r  (only
a setup, plan or tests go back)`), and a meaning that cannot apply is left out. It opens with every group as rows; `?` again folds the dense groups
(Move, Filter, Views, App) to one line of keys. Inside
the sheet `j`/`k` and `ctrl+d`/`ctrl+u` move the cursor and `enter` runs the row; pressing a
bright key closes the sheet and runs it (a dim one only says why); `/` searches every view's keys
by key or label (`merge` finds `m` and says `in Pulls`; `enter` on it says to open Pulls first);
`esc` or `q` closes. Under a popup the layer beneath folds to one line at the bottom
(`▸ board keys: …`). Two columns from 100 columns wide, one below.

The footer is a few short words per view (`? help  n new  a advance  enter open  x actions …`);
`?` has the rest. After `g` or `z` with no second
key for 400 ms it lists the second keys (`g ▸  g first ticket …  s order columns by stage …`).
Inside an editor `?` types a character, so the editor's title carries its keys and follows the
vim mode (`normal · i a o insert · dd x delete · u ^r undo · ctrl+s save · esc q cancel`, then
`insert · esc normal · ctrl+s save`). At the `:` prompt the commands the text is a prefix of show
above it with what they do; `tab` cycles them, `enter` runs the picked one, or the only one left
(`:fo` runs `fold`), else the text as typed.

`R` opens the repo search only on a ticket with no repo, the one time it matters; with a repo set
it says to use `:repo <name>` or the `x` menu's "set the repo", so a stray `R` never re-points a
ticket. `:repo <name>` sets the one repo under the repos root whose path holds the name (a path
as given when it starts with `/`, `~` or `.`); `:filter` covers filtering by repo.

## Tickets

`enter` opens a ticket in a popup over the board. Inside it, a rail of eight sections on the
left (a tab strip on a terminal under 100 columns) and one pane on the right; `h`/`l` or `1`…`8`
switch, `j`/`k` scroll the pane or pick a row where the section lists some (`J`/`K` scroll a line
there, `ctrl+d`/`ctrl+u` and PgDn/PgUp half a page anywhere; picking a row brings it into view),
`+` toggles the popup between most of the screen and all of it. Every section draws from everything the machine knows
about the ticket, whether or not a gate was decided: the approved plan stays readable after `a`.
While a gate is open, its strip sits on top of every section with the keys that answer it.

| Section | Shows | Keys inside |
|---|---|---|
| Overview | the status, then one row per acceptance criterion with its state in the plan, how many cases prove it and what verifying found; repo, branch, issue, the Jira link and the SLA clocks, why, spend; the ticket's description and criteria; a setup gate's `luna.yaml` and proof, triage's questions, the memory review's rules | `e` edits the ticket's text, `J` links or unlinks the Jira issue |
| Plan | triage's latest plan (brief, criteria, assumptions, slices) and its history: send-backs with their reason, your edits, the approval | `e` edits brief, criteria and assumptions until Build starts; `a` / `r` at the gate |
| Tests | test_design's cases under the criterion each proves, with ✓ ✗ – from verifying | `e` edits the cases while they wait for your check (`## criterion`, `- case`, the approach under it) |
| Runs | every stage run with how long it took, its cost and turns; the selected run's error, per-case verdicts and files; opens on the latest run | `j`/`k` pick a run, `J`/`K` scroll |
| Diff | the branch against its base: files with +/−, the selected file's patch (the machine sends at most 512 KB of it and the pane says when it cut) | `j`/`k` pick a file, `J`/`K` scroll the patch, `o` opens the file from the worktree |
| Evidence | the QA verdict and every artifact the stages produced, by kind; opens on the latest | `j`/`k` pick a file, `J`/`K` scroll, `o` opens it |
| PR | the branch's pull request as the Pulls inbox sees it: checks by name, review state, threads, the task in flight; or the URL the ship gate reported | `o` opens it, `S` ships at the gate |
| Activity | every event | |

The popup opens on the section the open gate concerns: the Plan at `approve plan`, the Tests
at `check tests`, the Runs when escalated. `e` on the board (outside the popup) keeps its old
meaning: the two-pane plan editor at the plan gate, the ticket's text otherwise.

The plan editor splits into two columns: triage's plan on the left (brief, criteria to build,
assumptions; slices stay as triage wrote them), the ticket's own description and criteria on the
right. `tab` moves between the two while editing; `ctrl+s` saves whichever side changed. The plan
may be edited through the test check too, since nothing is built yet; each edit is kept as a
revision the Plan section's history shows. On a terminal narrower than 110 columns the two stack
instead, plan first. `n` fills a new ticket in as the same markdown `e` edits:

```markdown
# Login page

## Description

Users can sign in with email and password.

## Acceptance criteria

- Invalid password shows an error
- Successful login redirects to /home
```

Editing is vim-style modal, not a plain text box: it opens in normal mode
(`hjkl` to move, `dd`/`x` to delete, `u`/`ctrl+r` undo/redo), `i`/`a`/`o`/…
enter insert mode, `esc` goes back to normal. `ctrl+s` saves from either
mode; `esc` or `q` in normal mode cancels. Nothing opens outside the board
for this anymore — no `$EDITOR`, no second window to switch to.

The repo isn't part of this text — it's never typed freely, only set through
the repo search, so a stray edit can't silently blank it or point it somewhere
wrong. A new ticket's repo defaults to herdr's workspace, or the board's own
working directory when it runs standalone — either way, the nearest repo
root above it. `a` on a backlog or intake ticket with no repo set opens the
repo search instead of advancing, so you fix it before a stage runs. `R`
opens the same search on a ticket without a repo (on one with a repo it points
you to `:repo <name>` or the `x` menu's "set the repo", so a stray `R` never
re-points a ticket): type to filter, enter to set it — no path to type or get
wrong. It lists every repo under `HARDNESS_REPOS_DIR` (default `~/Developer`),
whether a repo sits directly under it or is grouped with others under a
project folder (`~/Developer/some-project/backend`, `.../frontend`, both
found). Triage's questions (`a` on a ticket awaiting answers) open in place
too, pre-filled with its recommended answers; `ctrl+s` sends them.

A new ticket starts in Backlog. `a` moves it to Intake (no stage runs, it's
just a deliberate "I'm shaping this one up" step); `a` again starts triage.

Press `f` on a ticket with a running stage to open a herdr tab following its
agent (`docker logs -f` on its container), whether the machine runs in Docker or
on your host; `f` again focuses that tab. Nothing opens by itself: once the tab
exists, later stages of the ticket re-point it, and the board closes it once the
ticket is closed. Approving the Ship gate (`a` on `awaiting_ship`)
pushes the task's branch and opens a real PR through the GitHub API — see the root
`README.md`'s "Shipping" section for what that needs.

## Pulls

`P` opens the PR inbox: every open pull request on GitHub where your review is requested or that you authored, as the machine polls it every minute (`:prs` opens it too). Six splits, `h`/`l` or `1`–`6` between them, `j`/`k` down the rows, oldest first:

| Split | A PR lands here when |
|---|---|
| Review requested | a teammate's PR asks for your review |
| Ready to merge | yours, approved, every check green, mergeable, no unresolved threads |
| CI failed | yours, a check failed |
| CI running | yours, a check still running |
| Changes requested | yours, changes requested or review threads still open |
| Mine | everything else you authored, drafts included |

Review requested, Ready to merge, CI failed and Changes requested count on the Board tab's badge and raise a herdr notice when a PR moves into them.

`m` merges after one `y` (Ready to merge only). `c` dispatches an agent that diagnoses the red
run; a fixable one is fixed, checked and pushed to the PR's branch. `v` dispatches an agent that
reads the diff and posts line comments under your name right away; an approve or request-changes
verdict waits at the Ship gate for `a`. `t` dispatches an agent that answers every unresolved
review thread on your PR, pushes, posts the replies and resolves the threads it settled. `enter`
jumps to the PR's task on the board when one is running, else opens the PR.

`R` polls GitHub now. A poll reads every PR, so it runs in the background: the header says `◐ polling GitHub…` until the answer lands, then a toast says `polled GitHub`, and a second `R` meanwhile only says it is already polling. Slack's `R` does the same.

From 100 columns the view is a list beside a detail pane. A row reads `✓ ▌repo  #n  title  age  tag` in fixed columns, the checks glyph first (`✓` green, `✗` red, `◐` running), the repo's colour bar and name next (the name after the owner's `/`, the same colour its cards wear), `⚙` while a task runs for it and `⌂` when the machine has no clone of the repo; only the title is ever cut; the list scrolls to keep the selected row in view. The pane shows the selected PR: author and branches, every check by name, the review state and unresolved threads, the task in flight, and the four keys with why each is off. Under 100 columns the pane hides and `x` shows the same detail over the list. A dispatch on such a PR opens the clone prompt: the same filter-as-you-type search `R` uses, over the folders under `HARDNESS_REPOS_DIR`; `enter` clones into `<folder>/<name>` and runs the action once it lands, `esc` leaves the row read-only. `c` and `t` are off on a fork head (nothing can push to it), `v` is off on your own PRs, and all three are off while a task already runs for the PR.

## Slack

`S` opens the Slack inbox (`:slack` too): everything your Activity tab shows plus the handles you watch, as the machine polls it every minute and a triage pass sorts it. Six splits, `h`/`l` or `1`–`6` between them, `j`/`k` down the rows. Needs reply and Decide go P0 first, then oldest; the other splits newest first.

| Split | An item lands here when |
|---|---|
| Needs reply | triage says a reply is expected and you have not replied |
| Waiting on them | you asked something in a thread and nobody answered |
| Decide | a decision or a blocker without an explicit question |
| FYI | everything P2/P3 that is not automated |
| Snoozed | you pressed `s`; it returns to its split when the timer ends |
| Done | you replied, pressed `d`, or made it a ticket |

A P0 or P1 entering Needs reply or Decide counts on the Board tab's badge and raises a herdr notice; so does any item whose thread moved after you cleared it (`Reopened`). Lower priorities and the other splits are quiet.

`r` opens the editor with triage's draft (vim keys, like every editor); `ctrl+s` posts it as you
in the thread, `esc` backs out; nothing is ever sent without the key. `t` makes a Backlog task
from the message and its thread, titled with the summary, in the repo the channel name matches;
one `y` first, and the repo picker follows when none was guessed. `d` clears the item here at
once; Slack itself is not touched, and if the thread moves afterwards the item comes back,
re-triaged, with `new since you cleared it` in the pane. `s` snoozes for 1h, 3h, tomorrow 9:00 or
next Monday 9:00 (your local 9:00). `N` (Waiting on them only) opens the reply editor with a
one-line reminder. `!` / `-` move the priority one step; re-triage keeps your value. `enter`
jumps to the item's ticket on the board when it has one, else opens the message in Slack.

From 100 columns the view is a list beside a detail pane. A row reads `P0 ▌#channel  @author  summary  age  tag` in fixed columns: the priority first (`P0` red, `P1` yellow, `P3` muted), the channel's colour bar next (the same hue a repo of that name wears on the board), the author, triage's one-line summary (the only column ever cut; `×N` when a thread's mentions collapsed into one row), the age, then `⎇` for a thread, `⚙` once it is a ticket and `↺` when it came back after you cleared it. The pane shows where and who, the thread's last messages, the message itself, triage's verdict (`P0 · blocker · reply expected`), why, the links it found (with the linked PR's split from your Pulls inbox), the draft, and every key with why it is off. Under 100 columns the strip shortens its labels (`Reply`, `Wait`, `Snz`…), the pane hides and `x` shows the same detail over the list. The strip also says when Slack was last polled and, with an app token, whether the Socket Mode websocket is `live` or down.

Every item that expects a reply carries a due time under the reply SLA for its priority. The targets come from the rules file's `## SLA` section (defaults: P0 10m, P1 30m, P2 and P3 1h); the machine computes them, the board only shows them. The pane says `due      in 12m (P1 · 30m SLA)`, and within five minutes of it the row's age turns yellow. Past it the item is overdue: the row's summary and age go red, the tag leads with `‼`, it sorts to the top of Needs reply and Decide (the longest overdue first, ahead of P0), the strip counts them as `‼ N overdue`, the Board badge counts each one once whatever its priority, and a notice fires the moment it tips over (once; coming back inside the SLA is not news).

### Watches

A watch is anything beyond your own handle the inbox should treat as addressed to you: a user group (`@platform-team`), a broadcast (`@here`, `@channel`, `@everyone`; these ship on and can be switched off, not deleted), a keyword, or a whole channel. `W` opens them; `e` cycles the priority floor through none, P0, P1, P2 (an item matching the watch is at least that). After `n`, type `@` to complete a user group, `#` to complete a channel, anything else is a keyword; `enter` saves it. Watches live in the machine, so every board shares them and triage reads them.

## Jira

A ticket carries at most one Jira issue; the machine syncs it (the repo's `luna.yaml` says which Jira status each task state moves it to) and the board shows the link. `J` on a ticket with no issue opens a prompt like `R`'s repo search: type a key or a few words, the machine searches from the third character on (`GET /jira/search`, your open issues first), rows read `PLAT-123  In Progress  summary`, `enter` links the row (`POST /tasks/:id/jira`), `ctrl+n` (or `enter` on the first row, `+ create an issue from this ticket`) creates one in the repo's project and links it (`POST /tasks/:id/jira/create`), `esc` backs out. A typed key such as `PLAT-7` links as is without picking a row, and `:jira PLAT-7` does the same from the palette (`:jira` alone is `J`). On a linked ticket `J` asks `unlink PLAT-123? y/n`; `y` drops the link and leaves the issue alone. On a machine without Jira configured the prompt refuses with the reason in the footer. `x` lists the key with the other actions.

What the ticket shows:

- Overview: `Jira       PLAT-123 · In Progress · due Fri · High` (muted `—  J links an issue` until linked), with a red `⚠ blocked: no transition to "In Review" from "Blocked"` line under it while the last declared transition is refused, and an `SLA` row with the clocks the ticket has: `gate 12m of 1h` (red `overdue 40m` once past), `stage implementing 42m of 4h` (yellow from 80% of the target, red past it), `cycle 1d 3h of 3d`, `jira due Fri` (red when the issue's due date passed). Clocks the machine does not report are left out; a machine without them has no row.
- Cards: the second line ends in ` · PLAT-123` when linked; a ticket past any clock leads with `‼` and its head line goes red, like an overdue Slack row; a stage past 80% turns the age yellow. A ticket made from a Jira issue wears the key in front of its title where a GitHub one wears `#42`.
- Activity: `jira → In Progress`, `jira blocked: no transition to "In Review" from "Blocked" — why`, `jira moved to Done`.
- Within a column a ticket past its gate SLA sorts first, whatever the order; the `!` filter keeps that.
- Notices: `Gate overdue` the moment the gate clock tips over (once), `Stage over SLA` when the stage clock does, `Jira` when someone moves the linked issue in Jira while the ticket runs (`PLAT-123 moved to Done while #abcdef12 runs`). The header counts the tickets past a clock as `‼ N overdue`, and the Board tab's badge reads `Board !2 ‼1`: the needs-you count as before, then the overdue count. An overdue gate is already waiting on you, so it is not counted twice.

## Floor

`F` opens the Floor: one full-screen table with a 7d and a 30d column, read from the machine's `GET /metrics?since=7d|30d`. It shows tasks closed, created and open, what needs you, running and queued now, cycle time (median and p90), the gates answered and the share answered within their SLA with the median wait per gate state (`wait approval median`, from `metrics.gates`), first-pass rate for verifying, ci_watch and implementing, escalation rate with the top reasons, retries per task, cost, and queue depth, slot use and utilisation. A per-stage table (runs, median, p90, cost) sits below it, or beside it on terminals 110 columns or wider. With the Slack inbox on, a Slack block sits under the stage table: items and replies by priority over 7d / 30d, how many of the 7d replies came inside their SLA (count and share), the median and p90 time to reply, the share answered within an hour, and the SLA targets in force as `10m/30m/1h/1h` (`GET /slack/metrics?since=7d|30d`); a machine without the inbox simply leaves it out. Numbers load when you open the view and again on `R` (refresh is `R` in every view, as Pulls and Slack poll with it); if the machine is unreachable the error shows in the footer and the last numbers stay.
