# Configuration

## Credentials

The machine keeps scoped secrets for a repository's checks and its QA target in `~/.config/hardness/secrets/<repository>/<NAME>`. The folder name is the repository's folder name and 8 hex of its path. Use one file for each name, with mode 600, no links, and at least 8 characters. The machine refuses a name that is an engine's or the machine's variable. It also refuses a name that starts `HARDNESS_`, `LUNA_`, `MACHINE_`, `GIT_`, `NODE_`, `LD_`, `CLAUDE_`, `CODEX_`, `DOCKER_` or `BUILDKIT_`. `luna.yaml` names a secret and never holds one.

Put `claude-oauth-token` or `anthropic-api-key` in `~/.config/hardness/`. Without one, nothing runs for real. The default engine of every task stage is a Claude one. This includes the triage of the Slack inbox and Jira intake. So the machine makes every stage a stub. `POST /runs` is the exception. It runs a pack on any engine whose credential is there.

Each engine runs on its own credential. A stage gets only the credential of its own engine. A Claude stage never sees the Codex login or an API key. A `codex:*` stage never sees the Claude token. The one exception is a pack whose helper runs on another engine (`verifying`'s `second-opinion` on `codex:sol`). The helper runs inside the stage's container (`delegate`, see [architecture](architecture.md#factory-mode)). So the stage also gets the credential of that helper, each credential once. The stage then holds the Codex login for its whole run, one Codex run at a time as below. The machine leaves a helper's credential out, with a `stage.note`, in three cases. The credential is missing. The machine holds it back (`MACHINE_DISABLE_RUNTIMES`, a monthly cap). Another run holds it for more than two minutes. Then the stage runs without the helper. The machine reads the credentials when a stage starts. So a login or key that you add later counts without a restart. `GET /engines` says which engines this machine can run and, for the others, what is missing.

| Engines | Credential | Read from | Reaches the stage as |
|---|---|---|---|
| `claude:*` | the subscription token, else an API key | `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, then `claude-oauth-token`, `anthropic-api-key` in `~/.config/hardness/` | that one variable |
| `codex:*` | the Codex (ChatGPT) login | `$CODEX_HOME/auth.json`, else `~/.codex/auth.json`, as `codex login` writes it | a per-run copy (below), `CODEX_HOME=/tmp/.codex` |
| `openai:*` | an OpenAI API key, opt-in and metered | `OPENAI_API_KEY`, then `~/.config/hardness/openai-api-key` | `OPENAI_API_KEY` |
| `jev` | a Vercel AI Gateway key or a TypeSafe API key, opt-in and metered | `AI_GATEWAY_API_KEY`, then `~/.config/hardness/ai-gateway-api-key`, then `TYPESAFE_API_KEY`, then `~/.config/hardness/typesafe-api-key`: the first found | that one variable |

A task or a repo's `luna.yaml` can pick an engine for a stage. If this machine lacks the credential of that engine, the pack's default engine runs instead. The task logs `stage.engine` with the reason. If the default engine itself lacks its credential, the stage fails with the reason.

The Codex CLI owns its login. It rewrites `auth.json` when it refreshes the token. So no stage shares the host's file. Each `codex:*` run gets its own copy. The copy is `auth.json` (0600) in a `codex/` folder (0700) under the run's folder in the state dir. The machine mounts it writable at `/tmp/.codex`. When the container is gone, the machine checks the copy. Codex may have refreshed the token in it. If the run changed the copy, the machine writes it back to the host file. The write is atomic: a temporary file, then a rename, 0600. The machine writes back only while the host file still holds what the machine copied. If the host file changed meanwhile, the machine keeps the host's file and logs it. The host file changes when you log in again, or when another run writes back first. The machine never writes back a copy that is not a Codex login like the host's. This covers a copy that is not JSON, has other top-level keys, or is over 64 KB. If a write-back fails, the machine removes its temporary file. When the machine starts, it removes any `auth.json.*.tmp` left in the Codex home. The machine deletes the copy either way.

A refresh rotates the token. So two runs on one copy could revoke the login. Because of this, `codex:*` runs take turns, one at a time on the machine (stages and context-only packs alike). A run takes the login before it copies it. It hands the login on after its write-back. So the next run starts from the refreshed token. A stage that waits its turn says so on the task's activity (`stage.note`). A stage that does not get the login within its own timeout fails with that reason. Under compose (`pnpm start`), the machine mounts your Codex home (`$CODEX_HOME`, else `~/.codex`) read-write into the machine container. The container sets `CODEX_HOME` to it. See [Compose](#compose).

Jev is the decision model behind `triage_signals`. It is opt-in and metered, unlike the Claude subscription. Each call costs $0.042 per million input tokens. This is the price in `contracts/src/models.ts`. The machine computes a run's `costUsd` from it. The machine reaches Jev in two ways. The key that the machine finds first decides which way. One way is the Vercel AI Gateway with a Gateway key (model `typesafe-ai/jev`, through the AI SDK's `experimental_decide`). The other way is TypeSafe's own API with a TypeSafe key. With either key, intake classifies each new GitHub or Jira issue before it becomes a task (see [architecture](architecture.md#jira)). `POST /runs` also runs `triage_signals` for clients. Without a key, intake behaves exactly as before and nothing else changes. Keep the key in the file (`umask 077`). Never put it in a shell history or a command line.

| Variable | Default | What it does |
|---|---|---|
| `OPENAI_API_KEY` | unset, `openai:*` off | the key an `openai:*` stage runs on; also read from `~/.config/hardness/openai-api-key`. The `codex:*` engines run the same models on the Codex login instead |
| `CODEX_HOME` | `~/.codex` | where the machine finds the Codex login (`auth.json`) to copy into a `codex:*` stage |
| `AI_GATEWAY_API_KEY` | unset | the Vercel AI Gateway key the Jev runtime calls `experimental_decide` with (model `typesafe-ai/jev`); also read from `~/.config/hardness/ai-gateway-api-key`, preferred over the TypeSafe key when both are there, and passed by name only to a `jev` stage |
| `TYPESAFE_API_KEY` | unset | the key the Jev runtime (`@typesafe-ai/sdk`) calls `systemOne` with when there is no Gateway key; also read from `~/.config/hardness/typesafe-api-key`, and passed only to a `jev` stage. With neither key, Jev is off: `GET /engines` shows `jev` unavailable, `POST /runs` answers 409 `no_credential` for `triage_signals`, and intake classifies nothing |
| `TYPESAFE_BASE_URL` | `https://api.typesafe.ai` | the TypeSafe API root, for a proxy or a test server |

Every ceiling raises a `budget.alert` on `/events`. The alert fires the first time a run takes the spend past 80, 90 and 100% of the ceiling. The ceilings are a task's, a repo's month's from its `PIPELINE.md`, the day's, and each engine cap of `MACHINE_ENGINE_BUDGETS` or a repo's `budget.engines`. An engine cap's alert has `scope: "engine"` and names the cap's `engine`. It also names its `repo` for a luna.yaml cap. `taskId` is null when a `POST /runs` call crossed it. The board shows each alert as a notice. Nothing runs while a task waits on you, so idle time costs nothing. A stage container lives only for its stage.

## Per-repo config: `luna.yaml`

A `luna.yaml` at the root of a repo holds everything the machine needs to run that repo. It says how to check the repo, what runs beside it, and how the pipeline behaves. The board's `:setup <repo>` command has an agent read the repo and propose the file. The command proves every proposed check once. It writes the file after you approve it. You can also write the file by hand. The machine reads it from the checkout, not the task worktree, at every stage. So an edit takes effect without a restart. An uncommitted file already counts. If a version does not parse, the machine reports it once. The last good version stays in force.

```yaml
checks:                                   # the repo's own checks; without this key they are detected from the tree
  - name: board tests
    run: cargo test                       # a shell line, run in cwd (default: the worktree root)
    cwd: board
    paths: ["board/**"]                   # only for a change touching one of these; no paths means always
  - name: machine tests
    run: pnpm test
    cwd: machine
    paths: ["machine/**", "contracts/**"]
    coverage: coverage/lcov.info          # an lcov report the run writes, relative to cwd; Verify measures the change's added lines against it
    minutes: 6                            # how long the check takes (optional): a check with no paths runs in Build's regression sweep when this is within build.regression_full_suite_minutes
```

Every key is optional. The machine ignores unknown keys. Under `jira.on`, `jira.fields` and `sla.stage`, the keys must be task states (`sla.stage`: running ones). The machine drops an unknown key with one warning per version of the file. The rest applies. Durations are `30m`, `4h`, `3d` or `off`. `jira.on` works by status *name*. The machine matches the name against the transitions that Jira offers from the issue's current status, without regard to case. If the issue is already in that status, nothing happens. If no transition leads there, the task gets a `jira.blocked` event (with Jira's own words when it refused). The board shows the event, and the pipeline goes on. The machine posts comments and created issues as Atlassian Document Format. It builds them from markdown. Markdown here covers paragraphs, `#` headings, `- ` bullets, `- [ ]`/`- [x]` task lists, `1.` ordered lists, `**bold**`, `` `code` ``, bare urls as links. So a ticket's criteria arrive as checkboxes. `branch` also takes `{slug}`, `{route}` and `{id}`. It must contain `{key}` or `{id}`. If a pattern has neither, the machine drops it with a warning and uses the default. So two tasks never share a branch, and no render is ever `main`. Sometimes the repo already has the branch that a pattern names. An older task on the same issue can cause this. Then the machine appends `-<id8>` to patterns without `{id}` or `{slug}`. Once a task works on its branch, that branch stays, whatever the issue's type becomes. Nobody can change or remove its link until the task closes. An unknown issue type renders `{type}` as `task`. Unlinked tasks keep `task/<id>-<slug>`. A writable stage never runs on `main`, `master`, `develop` or the repo's default branch. `auto_approve_plan_minutes` needs triage to report `confidence: high` and `risk: low`. It also needs triage to have asked nothing. Anything less waits for you as always. A Luna Notch task (`source.kind: notch`) always waits, because the notch approves its own plans. The machine logs each approval that it does make as `plan.auto_approved` with the reason on the approval.

`engines` maps a pack to the engine it runs on in this repo. An engine outside the pack's `engines.allowed` makes the file invalid. The machine reports it like any other bad value. The last good version stays in force. A setup proposal with such an engine fails the stage, like any proposal the machine cannot read. A task's own choice (`stages` on `POST /tasks`, `PATCH /tasks/:id/stages`) wins over the file. The file wins over the pack's default. The machine reads a pack's engine when its stage starts. So an edit counts from the next stage on. A stage that already runs keeps its engine, also across a restart.

`budget.engines` caps an engine in this repo the way `MACHINE_ENGINE_BUDGETS` caps it on the machine. It uses the same keys and rules. It counts only this repo's stage runs this month. A key that names no engine or credential makes the file invalid. A key that names Claude also makes the file invalid. At the cap, the repo's tasks run that pack's default with a note. The machine's caps still apply on top.

A check with `coverage` names an lcov report that its run writes. The path is relative to the check's `cwd`. Vitest, jest, pytest-cov, cargo-llvm-cov and go via gcov2lcov all emit one. After the check passes, Verify reads the report. It measures *patch coverage*. This counts how many of the lines that the branch added the report saw run. A file with uncovered added lines gives a `test` finding (confidence 0.9). The verifier weighs the finding. The finding never fails the stage by itself. The numbers are in the stage's `detail.coverage` and in the verifier's input. The machine notes a missing or unreadable report. Neither case fails the stage. The machine ignores a path that climbs out of the worktree.

Each `services` entry runs as its own container. It runs beside every stage that runs the repo's code (implementing, verifying, e2e) and beside every check run. It runs on a private docker network for that run. Other containers reach it by its key as hostname. The `exports` become env in the stage or check container. The machine tears the services down with the stage or check. So two tasks of one repo never share a database. A service whose `ready` line does not exit 0 within a minute escalates the stage with the service's log tail.

`PIPELINE.md` is the earlier per-repo file, with front matter that holds the `policy` keys and `qa_target` lines. It still works when there is no `luna.yaml`. The machine gives a deprecation notice once per repo. `luna.yaml` wins when both exist.

## GitHub gates

`pnpm --filter @hardness/machine gates owner/name [--checks board,machine] [--dry-run]` applies a repository ruleset named `hardness gates` to the default branch. The ruleset needs one approving review from someone other than the last pusher. It dismisses reviews when the branch moves. It allows no deletion and no force-push. It needs the named checks green. GitHub enforces it whatever an agent does. The pipeline cannot approve its own PR. The machine's side of the same gate: a writable stage refuses any branch outside `task/`.

## Environment cache

Every stage and check container mounts a docker volume named `hardness-cache-<repo>` at `/cache`, with npm, pnpm, yarn, Go, cargo, pip and uv pointed at it. A retry, or the next task of the same repo, installs from that warm cache instead of the network. `docker volume rm hardness-cache-<repo>` starts a repo over.

## Compose

`docker compose up` (and `pnpm start`) runs the machine in a container that drives your host's Docker through its socket. Every path that the machine hands to `docker run` must exist at the same path on the host. So the compose file mounts these at identical paths:

| `LUNA_REPOS_DIR` | `~/Developer` | where your repos live; task repo paths must be inside it, and so must `WORKTREES_DIR` |

| `LUNA_GIT_NAME`, `LUNA_GIT_EMAIL` | your `git config` (via `pnpm start`) | identity for commits the machine makes itself (the approved memory rules) |
| `LMNR_*`, `MACHINE_TRACES` | unset | passed through to the machine container; `LMNR_BASE_URL` defaults to `http://lmnr-app` there. The `observe` profile's own secrets (`LMNR_POSTGRES_*`, `LMNR_CLICKHOUSE_*`, `LMNR_SHARED_SECRET_TOKEN`, `LMNR_AEAD_SECRET_KEY`, `LMNR_NEXTAUTH_SECRET`, `LMNR_FRONTEND_PORT`) have local defaults in `compose.yaml`; `make integrations` writes random ones into `.env`, which is what anything beyond one person's laptop should use |

Compose mounts `~/.config/hardness` read-only for the Claude credential and the API token. The container binds `0.0.0.0`. So the machine there asks every call for `machine-api-token`. `pnpm start` writes this file once (`openssl rand -hex 32`, mode 0600), and the board reads it. The other variables in the table above pass through to the container as well.

Compose mounts your Codex home (`$CODEX_HOME`, else `~/.codex`) read-write at `/root/.codex-host`, with `CODEX_HOME` pointing there. The `codex:*` engines use it. The machine copies `auth.json` into the folder of each run. It writes a refreshed token back and keeps the file's owner. So a stage container never sees the folder. Without a `codex login` on the host, the folder is empty. Then `codex:*` picks run on the pack's default, with a line on the task that says so. The other variables in the table above pass through to the container as well.

## What the machine keeps for learning (wave 18)

Everything below stays on this computer. It stays under the state dir (`MACHINE_STATE_DIR`, default `~/.local/state/hardness`). It reaches `evals/` only through `pnpm eval harvest`. The command scrubs the data. A person reviews it in a PR. It also stays in the local trace tool that you already run. The machine pushes nothing to the datasets or labelling queue of the trace tool, except by a command that a person types.

- **Decision records** (`MACHINE_DECISIONS`, on): one per decision pack call. Each holds its stored (redacted) context, answer, verdicts, what the machine did with it (`acted`), cost and later truths. Files are owner-only (0600, folders 0700).
- **Traces** (`MACHINE_TRACES`) have four modes. `off` sends nothing. `metadata` sends one trace per stage with the facts of the run. `host` is `metadata` plus, from the host alone, the last 200,000 characters of the transcript. For the machine's own decisions, `host` also adds the stored context and the answer. `full` adds the container's own spans and hands the key to the container, so it is never a default. `host` is the default **with a trace key and a collector on this computer**. The collector is `localhost`, a loopback address, or the compose service name `lmnr-app`. A collector at any other address defaults to `metadata`, and the boot line says why. So an upgrade never starts to send contexts, answers and transcripts to a hosted collector. Set `MACHINE_TRACES=host` to ask for it. Without a key, tracing is off. The machine then logs once at boot `traces off: no trace key; decision records and ground truth are still kept`. In `host`, no container gets the key, the address or the span. A collector that does not answer gives one warning line and no traces until the next start. `docker compose --profile observe up -d` starts the collector.
- **Retention**: `MACHINE_DECISIONS_RETENTION_DAYS` (365) bounds decision records and the files under `<state dir>/ground-truth/`. `MACHINE_DECISIONS_MAX_MB` (4096, 0 for no cap) bounds `decisions/`.
- **`learning` in `luna.yaml`** (wave 18): `records` (true), `context` (`full` or `answers`: keep no context), `truth` (true), `traces` (`off`, `metadata` or `host`). The machine refuses `full` here. A repository can only lower what the machine keeps. It can never raise it. `MACHINE_DECISIONS=off` or `MACHINE_TRACES=off` is a ceiling over any repository.
- **Disk, as an estimate (not measured)**: a card leaves a few dozen records. Each record has a few to a few tens of kilobytes. The trace tool also holds a transcript of up to 200,000 characters. This is about 0.2 to 1 MB per card. So a few cards a day take roughly 0.5 to 2 GB a year before the cap. `pnpm eval records --sizes` prints what `decisions/`, `ground-truth/` and `evals/.runs/` take today.
- **The prune** (nightly, in the machine's sweep) removes only what retention covers. It removes decision records and ground-truth files older than the retention. Over the size cap, it removes records with no truth first, oldest first. It acts only under the machine's own `decisions/` and `ground-truth/` folders. It acts only on names that it lists itself. It never acts on a link or on a name that is not its own pattern. It never removes a record younger than 7 days. It never removes a record that an open card needs. It logs one line. The machine does not prune the own store of the trace tool. To empty that store, run `docker compose --profile observe down --volumes`, which removes its data. `pnpm eval prune-runs [--older-than 30]` clears old run folders under `evals/.runs/`.
- **A transcript** goes to the trace tool only for the machine's own calls. It never goes there for a private conversation. A client's `POST /runs` call and the call of a private thread send the facts of the run and no transcript. Every transcript, span input and span output passes the machine's secret values, the token shapes, and the masking of e-mail addresses and phone numbers. The secret values are its tokens, the provider keys, the Claude token, the Codex login, the database password and the Slack tokens.
- **A client's record** (a `POST /runs` call) keeps the answer and not the context it sent.
- **What a pull writes back**: `pnpm eval dataset pull` writes cases (marked for review) and nothing onto a record. With `--write-labels`, it prints each label. It writes the label as a `queue` truth. It writes only onto a record of the machine's own that waits for a label here. The record must have no label from a person. A label that a person types at the board or at the command line always outranks it. The command skips a label that is not valid for the questions of the pack. `dataset push --queue` sends the same records that `label push` does, and no others.
- **What the machine never keeps, whatever a switch says.** It never keeps a secret, the text of a private Slack conversation, or personal data that `maskPii` masks in every copy out. The redactors run before the machine stores or traces anything. The text of a private Slack conversation leaves the stored record, and harvest and the queue skip it. A full trace and a kept decision context pass the same redaction as a stored record. Every ground-truth file passes the machine's secret values and the token shapes. The outcome file of a private conversation holds the outcome, the size of the difference and the record ids, with no text. The machine caps one record's stored context at 200 KB. It cuts a string at 20,000 characters with a marker. Each cut counts as a redaction.
- **The size cap** applies at the nightly sweep, not at each write. It never removes a record with a person's truth, a record under 7 days, the record of an open card or a ground-truth file. When what the sweep cannot prune is over the cap, the sweep says so in one warning line. The machine removes temporary files that a writer left after a day. It does not follow a symbolic link where `decisions/` or `ground-truth/` should be.
- **Limits, in plain words.** The machine does not catch a secret that someone splits, reverses, hex-encodes or compresses. It does not catch a secret with no known shape that is not among the machine's own values. The own database of the trace tool has no retention of the machine's. Anything on this computer that holds the project key reads every trace. A stored record keeps a ticket's personal data as the model got it. A harvested case replays a stranger's text to a model. `evals/baselines/` and the case folders are inputs to the defaults rule. So they need the same review as code.

## Observability (Laminar)

Luna keeps the facts of every run in Postgres (`stage_runs`, `pack_runs`) and the transcripts on disk. Laminar ([laminar.sh](https://laminar.sh), Apache 2.0, self-hosted) gives them a UI. The UI shows one trace per stage run, `POST /runs` call and eval case. It shows a session per task and cost over time. It also shows the replay evals as evaluations that you can compare across engines. Laminar is opt-in and local:

1. Run `docker compose --profile observe up -d`. It starts Laminar's lightweight stack beside the machine. The stack has its own Postgres, ClickHouse and Quickwit, bound to localhost. It needs about 2 GB of images and a couple of GB of RAM while up. The UI is `http://localhost:5667`. Anyone on this computer can sign in.
2. Create a project in the UI.
3. Put the project's API key in `~/.config/hardness/lmnr-project-api-key` (`umask 077`) or in `LMNR_PROJECT_API_KEY`. `make integrations` does this for you.
4. Restart the machine (`pnpm start` or `pnpm dev`). It logs `traces host · Laminar at …`. `MACHINE_TRACES=metadata` keeps only the facts of the run. `MACHINE_TRACES=full` also hands the containers the key.

The machine opens one root span per run. `application/telemetry.ts` is the port. `adapters/laminar/` is the adapter. It is the only place in the machine that imports `@lmnr-ai/lmnr`, and it loads only when you set a key. In `full` mode, the machine also hands the stage container the key, Laminar's address and that span, serialized, as `LMNR_SPAN_CONTEXT`. Inside the container, the factory (`factory/src/core/telemetry.ts`) initializes Laminar from them. It plugs in Laminar's integrations. So the model calls are children of the machine's span. The integrations are these: the Claude Agent SDK's `query()` wrapped (every turn, tool call and subagent, with prompts, completions, tokens and cost). The AI SDK's telemetry registers before Jev's `experimental_decide`. Each built eve agent exports through `LaminarSpanProcessor`. Those spans are their own traces. The eve session id that the run's `session` event names joins them to the run. The machine closes the root span after the container exits. It adds the facts of the run row and, in `full`, the transcript. If Laminar is down at boot, the machine runs without traces and says so once in the log. The machine drops a span that it cannot send, with a warning. A container that cannot load the SDK runs untraced and says so on its transcript. The SDK runs dotenv on its working directory when it loads. The factory removes whatever dotenv added. So a `.env` committed to a repo cannot change the environment of a run. `pnpm eval` reports to the same Laminar from the same variables (see [evals/README.md](../evals/README.md)). Laminar's own AI features need a provider key in its containers. They are chat with a trace, SQL with AI, and Signals. Luna leaves them off here. The `eval_judge` pack is the judge. Direct Anthropic or OpenAI SDK instrumentation does not apply. The factory never imports those SDKs.

## Runner image

The image carries Node 24, `gh` and Go. It carries Python with a pinned Graphify (`GRAPHIFY_VERSION`). The headless code-only graph build of Graphify is `/graph-tools/build.py`, run as an entrypoint override. A stage reads the repo's graph read-only at `/graph`. The image carries a pinned Rust toolchain (`RUST_VERSION` in `machine/runner/Dockerfile`, with clippy and rustfmt). So a repo whose suite is `cargo test` runs as it is. The image carries the Codex CLI (`CODEX_VERSION`, pinned). Eve's `chatgpt()` asks the CLI for the token of the login. The image also carries the factory with its three SDKs installed. It carries an eve agent built for each pack that allows an eve engine (`triage`, `slack_triage`, `chat_triage`). It carries one generic `decide` app for the decision packs and for each helper on one (`verifying--second-opinion`). Every check container also gets your git identity. This is the `user.name` and `user.email` that git resolves for the repo. So a suite that commits in a scratch repo runs as you. A repo with no identity escalates the verifying stage instead of committing as nobody.

`pnpm --filter @hardness/machine runner:build` runs `machine/runner/build.sh`. The script builds the image from this checkout, with the repository root as the build context. It copies in `factory/` and `contracts/`. It installs them with the workspace lockfile. So the image runs exactly what the checkout tests. The script labels each image with a key over those files and the Dockerfile. It skips the build when that key is current. So `pnpm images` (run by `pnpm start` and `pnpm dev`) is instant when nothing changed. `REBUILD=1 pnpm images` builds anyway. The image has the tags `hardness-runner:dev` and `hardness-runner:<key>`. `runner-qa:build` runs the same script with `--qa`. It then builds `hardness-runner-qa:dev` from `machine/runner-qa/Dockerfile` on top of it. `runner-video:build` runs it with `--video`. This builds the QA image first. It then builds `hardness-runner-video:dev` from `machine/runner-video/Dockerfile` (repository root as the context). `pnpm images` builds all three.

The video image adds the tools in `/video-tools` on top of the QA image. `narrate.ts` makes the voice with kokoro-js. It makes word timestamps with whisper-tiny.en through transformers.js. The build bakes both models into `/models`, and the tool reads them offline. `cards.ts` renders a time-driven card page frame by frame through the chromium of the QA image. `compose.ts` does the ffmpeg cuts, narration, captions and chapters. `measure.ts` makes frame statistics, loudness, contact sheets and a transcript. `fixture.ts` is the demo fixture that the recorder imports. The logic is in pure libraries beside them that the machine's test suite covers. Each tool reads and writes only under its job dir `/work`. The machine runs it with no network and no credential. `pnpm --filter @hardness/machine runner-video:smoke` builds a 20-second synthetic job. It runs all four tools inside the image. Size, measured at build: the video image takes 6.55 GB on disk (1.79 GB compressed). The QA image takes 5.56 GB (1.49 GB). So the video image adds about 1 GB. The two models take 235 MB of it. The npm packages (onnxruntime among them) take most of the rest.

Inside a stage container, the runner sees `/in/stage.json`, `/out`, `/work` and `/session`. `/work` is the card's work folder. It has a git repository of the agent's own in `.git`, which the machine never reads. `/session` is the task's SDK session dir (`CLAUDE_CONFIG_DIR`). `LUNA_FACTORY=1` marks the run. `LUNA_STAGE_DRY_RUN=1` renders the prompt and the SDK options without a model call (the sandbox smoke uses it). On an eve engine, it prints the agent, model, tools and guard policy instead. For a decision pack, it prints the questions and the state that it would send to Jev. A repo may keep binding rules for every stage in `docs/agents/project-context.md`. The memory review proposes additions to it.

## Board

The board uses whichever machine answers. It tries `http://127.0.0.1:4317` (`pnpm dev`) first. Then it tries `http://127.0.0.1:4318` (`pnpm start`). It checks again on every reconnect. `HARDNESS_MACHINE_URL` pins one address instead. When `MACHINE_API_TOKEN` or `~/.config/hardness/machine-api-token` holds a token, the board sends it on every call. `HARDNESS_REPOS_DIR` is where the board's repo search (`R`) looks for repos (default `~/Developer`). `LUNA_APPROVER` names you on every approval and send-back that the board makes. If you leave it unset, the board sends no name. A plan of High risk needs two distinct names. So without it, the machine answers `approver_required`. The name is an attestation, not access control. The machine has one bearer token and no per-person identity. So the two-approver rule records who said they approved. It cannot stop one token holder from naming two people.
