# Configuration

## Credentials

The machine keeps scoped secrets for a repository's checks and its QA target in `~/.config/hardness/secrets/<repository>/<NAME>`. The folder name is the repository's folder name and 8 hex of its path. Use one file for each name, with mode 600, no links, and at least 8 characters. The machine refuses a name that is an engine's or the machine's variable. It also refuses a name that starts `HARDNESS_`, `LUNA_`, `MACHINE_`, `GIT_`, `NODE_`, `LD_`, `CLAUDE_`, `CODEX_`, `DOCKER_` or `BUILDKIT_`. `luna.yaml` names a secret and never holds one.

Put `claude-oauth-token` or `anthropic-api-key` in `~/.config/hardness/`. Without one, nothing runs for real. The default engine of every task stage is a Claude one. This includes the triage of the Slack inbox and Jira intake. So the machine makes every stage a stub. `POST /runs` is the exception. It runs a pack on any engine whose credential is there.

Each engine runs on its own credential. A stage gets only the credential of its own engine. A Claude stage never sees the Codex login or an API key. A `codex:*` stage never sees the Claude token. The one exception is a pack whose helper runs on another engine (`verifying`'s `second-opinion` on `codex:sol`). The helper runs inside the stage's container (`delegate`, see [architecture](architecture.md#factory-mode)). So the stage also gets the credential of that helper, each credential once. The stage then holds the Codex login for its whole run, one Codex run at a time as below. The machine leaves a helper's credential out, with a `stage.note`, in three cases. The credential is missing. The machine holds it back (`MACHINE_DISABLE_RUNTIMES`, a monthly cap). Another run holds it for more than two minutes. Then the stage runs without the helper. The machine reads the credentials when a stage starts. So a login or key that you add later counts without a restart. `GET /engines` says which engines this machine can run and, for the others, what is missing.

| Engines | Credential | Read from | Reaches the stage as |
|---|---|---|---|
| `claude:*` | the subscription token, else an API key | `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, then `claude-oauth-token`, `anthropic-api-key` in `~/.config/hardness/` | that one variable |
| `codex:*` | the Codex (ChatGPT) login | `$CODEX_HOME/auth.json`, else `~/.codex/auth.json`, as `codex login` writes it | a per-run copy (below), `CODEX_HOME=/tmp/.codex` |
| `openai:*` | an OpenAI API key, opt-in and metered | `OPENAI_API_KEY`, then `~/.config/hardness/openai-api-key` | `OPENAI_API_KEY` |
| `jev` | a Vercel AI Gateway key or a TypeSafe API key, opt-in and metered | `AI_GATEWAY_API_KEY`, then `~/.config/hardness/ai-gateway-api-key`, then `TYPESAFE_API_KEY`, then `~/.config/hardness/typesafe-api-key`: the first found | that one variable |

A task or a repo's `luna.yaml` can pick an engine for a stage. If this machine lacks the credential of that engine, the pack's default engine runs instead. The task logs `stage.engine` with the reason. If the default engine itself lacks its credential, the stage fails with the reason.

The Codex CLI owns its login. It rewrites `auth.json` when it refreshes the token. So no stage shares the host's file. Each `codex:*` run gets its own copy. The copy is `auth.json` (0600) in a `codex/` folder (0700) under the run's folder in the state dir. The machine mounts it writable at `/tmp/.codex`. When the container is gone, the machine checks the copy. Codex may have refreshed the token in it. If the run changed the copy, the machine writes it back to the host file. The write is atomic: a temporary file, then a rename, 0600. The machine writes back only while the host file still holds what the machine copied. If the host file changed meanwhile, the machine keeps the host's file and logs it. The host file changes when you log in again, or when another run writes back first. The machine never writes back a copy that is not a Codex login like the host's. This covers a copy that is not JSON, has other top-level keys, or is over 64 KB. If a write-back fails, the machine removes its temporary file. When the machine starts, it removes any `auth.json.*.tmp` left in the Codex home. The machine deletes the copy either way.

A refresh rotates the token. So two runs on one copy could revoke the login. Because of this, `codex:*` runs take turns, one at a time on the machine (stages and context-only packs alike). A run takes the login before it copies it. It hands the login on after its write-back. So the next run starts from the refreshed token. A stage that waits its turn says so on the task's activity (`stage.note`). A stage that does not get the login within its own timeout fails with that reason. Under compose (`pnpm start`), the machine mounts your Codex home (`$CODEX_HOME`, else `~/.codex`) read-write into the machine container. The container sets `CODEX_HOME` to it. See [Compose](#compose).

Jev is the decision model behind `triage_signals`. It is opt-in and metered, unlike the Claude subscription. Each call costs $0.042 per million input tokens. This is the price in `packages/contracts/src/models.ts`. The machine computes a run's `costUsd` from it. The machine reaches Jev in two ways. The key that the machine finds first decides which way. One way is the Vercel AI Gateway with a Gateway key (model `typesafe-ai/jev`, through the AI SDK's `experimental_decide`). The other way is TypeSafe's own API with a TypeSafe key. With either key, intake classifies each new GitHub or Jira issue before it becomes a task (see [architecture](architecture.md#jira)). `POST /runs` also runs `triage_signals` for clients. Without a key, intake behaves exactly as before and nothing else changes. Keep the key in the file (`umask 077`). Never put it in a shell history or a command line.

| Variable | Default | What it does |
|---|---|---|
| `OPENAI_API_KEY` | unset, `openai:*` off | the key an `openai:*` stage runs on; also read from `~/.config/hardness/openai-api-key`. The `codex:*` engines run the same models on the Codex login instead |
| `CODEX_HOME` | `~/.codex` | where the machine finds the Codex login (`auth.json`) to copy into a `codex:*` stage |
| `AI_GATEWAY_API_KEY` | unset | the Vercel AI Gateway key the Jev runtime calls `experimental_decide` with (model `typesafe-ai/jev`); also read from `~/.config/hardness/ai-gateway-api-key`, preferred over the TypeSafe key when both are there, and given to a `jev` stage as a secret file (never as a `-e`) |
| `TYPESAFE_API_KEY` | unset | the key the Jev runtime (`@typesafe-ai/sdk`) calls `systemOne` with when there is no Gateway key; also read from `~/.config/hardness/typesafe-api-key`, and passed only to a `jev` stage. With neither key, Jev is off: `GET /engines` shows `jev` unavailable, `POST /runs` answers 409 `no_credential` for `triage_signals`, and intake classifies nothing |
| `TYPESAFE_BASE_URL` | `https://api.typesafe.ai` | the TypeSafe API root, for a proxy or a test server |

Every ceiling raises a `budget.alert` on `/events`. The alert fires the first time a run takes the spend past 80, 90 and 100% of the ceiling. The ceilings are a task's, a repo's month's from its `PIPELINE.md`, the day's, and each engine cap of `MACHINE_ENGINE_BUDGETS` or a repo's `budget.engines`. An engine cap's alert has `scope: "engine"` and names the cap's `engine`. It also names its `repo` for a luna.yaml cap. `taskId` is null when a `POST /runs` call crossed it. The board shows each alert as a notice. Nothing runs while a task waits on you, so idle time costs nothing. A stage container lives only for its stage.

## Per-repo config: `luna.yaml`

A `luna.yaml` at the root of a repo holds everything the machine needs to run that repo. It says how to check the repo, what runs beside it, and how the pipeline behaves. The board's `:setup <repo>` command has an agent read the repo and propose the file. The command proves every proposed check once. It writes the file after you approve it. You can also write the file by hand. In Claude Code, the `luna-setup` skill does this with you. The skill is the plugin in this repo's `plugins/` folder (see [install](install.md)). It reads the repo and asks what only you can decide. It writes the file with the app start and the egress hosts. It checks the file with `POST /repos/config/check`. It proves the checks and the app start in the sandbox with `POST /repos/config/prove`. The proof names each host that the sandbox refused. Then the skill opens the file as a PR. The machine reads the file from the checkout, not the task worktree, at every stage. So an edit takes effect without a restart. An uncommitted file already counts. If a version does not parse, the machine reports it once. The last good version stays in force.

Every key is optional. The machine ignores unknown keys. Under `jira.on`, `jira.fields` and `sla.stage`, the keys must be task states (`sla.stage`: running ones). The machine drops an unknown key with one warning per version of the file. The rest applies. Durations are `30m`, `4h`, `3d` or `off`. `jira.on` works by status *name*. The machine matches the name against the transitions that Jira offers from the issue's current status, without regard to case. If the issue is already in that status, nothing happens. If no transition leads there, the task gets a `jira.blocked` event (with Jira's own words when it refused). The board shows the event, and the pipeline goes on. The machine posts comments and created issues as Atlassian Document Format. It builds them from markdown. Markdown here covers paragraphs, `#` headings, `- ` bullets, `- [ ]`/`- [x]` task lists, `1.` ordered lists, `**bold**`, `` `code` ``, bare urls as links. So a ticket's criteria arrive as checkboxes. `branch` also takes `{slug}`, `{route}` and `{id}`. It must contain `{key}` or `{id}`. If a pattern has neither, the machine drops it with a warning and uses the default. So two tasks never share a branch, and no render is ever `main`. Sometimes the repo already has the branch that a pattern names. An older task on the same issue can cause this. Then the machine appends `-<id8>` to patterns without `{id}` or `{slug}`. Once a task works on its branch, that branch stays, whatever the issue's type becomes. Nobody can change or remove its link until the task closes. An unknown issue type renders `{type}` as `task`. Unlinked tasks keep `task/<id>-<slug>`. A writable stage never runs on `main`, `master`, `develop` or the repo's default branch. `auto_approve_plan_minutes` lets the timer approve a plan after that wait. It approves only when the plan's risk is low, every check (coverage, plan, risk) proceeded and the plan asks nothing. It carries no flag and no re-plan evidence. It needs one approver at most (`plan.approvers`). A medium or high risk plan also counts when its council passed and `plan.council.counts_as_pass` is true. A reply, an archive and a split always wait for you. Anything less waits for you as always. A Luna Notch task (`source.kind: notch`) always waits, because the notch approves its own plans. The timer never approves a plan for an untrusted card (a GitHub author outside owner, member and collaborator). It never approves a plan that carries answers the question council settled. These wait for a person. The machine logs each approval that it does make as `plan.auto_approved` with the reason on the approval.

`engines` maps a pack to the engine it runs on in this repo. An engine outside the pack's `engines.allowed` makes the file invalid. The machine reports it like any other bad value. The last good version stays in force. A setup proposal with such an engine fails the stage, like any proposal the machine cannot read. A task's own choice (`stages` on `POST /tasks`, `PATCH /tasks/:id/stages`) wins over the file. The file wins over the pack's default. The machine reads a pack's engine when its stage starts. So an edit counts from the next stage on. A stage that already runs keeps its engine, also across a restart.

`effort` maps a pack to the effort it runs at in this repo. The value is `low`, `medium` or `high`. A decision pack takes no effort, so the file is invalid with one. A pack that runs on its own, not in a task (`foreman`, `slack_triage`, `chat_triage`, `decompose`, `ticket_reply` and the like), takes none either: the file is invalid with one. The four review passes are the exception: they run inside the review stage, so each takes an effort. An unknown pack or value makes the file invalid too. The file does not check the effort against an engine. The engine can differ per task. The machine checks it when the stage starts. If the engine that runs does not support the effort, the stage runs the pack's own effort. A `stage.engine` event on the task gives the reason. The machine reads the effort when a stage starts. So an edit counts from the next stage on.

`limits` maps an agent pack to `{ max_turns, minutes }`: the turns and the wall-clock minutes one run of the pack gets in this repo. Each is optional and a whole number (`max_turns` 1 to 500, `minutes` 1 to 240). A decision pack, a pack that runs on its own, not in a task, an unknown pack or a bad value makes the file invalid, as with `effort`. Without it, a feature card's `plan`, `test_design`, `build_tests`, `implementing`, `verifying` and `e2e` runs get the pack's default times a size factor: 1 up to 2,000 lines, 2 up to 8,000 and 3 above. The lines are the plan's own estimate once there is a plan, else the `size_estimate` decision's `est_loc` when it was sure, else the factor is 1. The planner's own default is 60 turns and 20 minutes, since it runs before any plan exists. The fast lane is not scaled. A `limits` entry replaces the pack's turns and minutes whatever the size. A field it leaves out keeps the default. The run's `limits` event says what applied: `by` is `size×2`, `size×3` or `luna.yaml`. `size.hard_limit_loc` may be as high as 100,000 lines. A ticket that the `size_estimate` decision calls not reviewable is split only when its estimate is also over the upper bound of `size.target_loc`. Within the target, it stays a flag on the plan gate (`size: hard to review as one change`).

The PR review runs four dedicated passes beside the main reviewer on every PR, whatever the files: `review_security`, `review_migration`, `review_iac` and `review_second`. Each is a pack with its own `engines:` and `effort:` entry. The default is `claude:sonnet` at medium effort. A pass may also run on `codex:luna`, `claude:opus` or `codex:sol`. The main reviewer stays on `claude:opus` at high effort. The passes run in parallel with each other and with the main reviewer, each in a read-only clone of its own at the PR's head, the code the main reviewer reads. A `codex:*` pass waits for the Codex login, which is leased one run at a time, so Codex passes serialize in any case. A pass that fails is a note on the review, never a failure. Every finding is checked once more by the `finding_confirm` decision pack (list it under `policy.decisions` to change its bars, for the question `real`). A pass-only finding it is not sure of stays; one it drops does not. The main reviewer's finding is never dropped: a doubt only marks it unsure, and the mark shows at the gate, not in the posted comment. The `already_raised` pack (question `same`) drops a finding that repeats a comment others already left on the PR. The `finding_classify` pack moves a finding's severity both ways at its proceed bar; a security finding is lowered only on a nit answer of 0.9 or more. On a re-review the `comment_intent` pack reads each author reply: a question is answered by the reviewer, an acknowledgement gets no reply. When the PR already has a review by the machine's GitHub login, the review reads only what changed since it, and the `thread_settle` decision pack (also under `policy.decisions`) settles each of the review's own open threads that the new code fixed or the author answered soundly. The reviewer answers the rest. A pass may also run on `codex:luna`, `claude:opus`, `codex:sol` or `claude:haiku`. What only a pass found is checked once more by the `finding_confirm` decision pack (list it under `policy.decisions` to change its bars, for the question `real`). A finding it is not sure of stays, marked `Unsure:`;

Before a review runs, three decision packs read it. All three are Jev decisions: without a Jev key they fall back to `claude:haiku`, and with no decision at all the review runs as it always did. Their bars sit under `policy.decisions` like the others.

- `pr_risk` scores the PR low, medium or high from its file paths and line counts, with no diff. Low runs the main reviewer on Opus at medium effort and the four passes on `claude:haiku` at low effort. Medium is today's defaults. High runs the passes on `claude:sonnet` at high effort, and `review_second` on `codex:sol` (else `codex:luna`) when the machine has the Codex login. An engine or an effort that `luna.yaml` names for a pack always wins over this. The stage detail keeps `risk` with the level, who decided (`jev`, `fallback` or `skipped`) and what was applied. Over `review.max_shards`, the same pack scores each part of a big PR, and the best-scored parts are read; the path heuristic stays the fallback for a part it cannot score.
- `rereview_worth` reads the activity since our last review (the new comments on our threads, the delta) when the PR watch sends the card back. A merge of the base branch is spotted by git, with no decision: the delta is no new code. A thanks, an acknowledgement, a bot or agent restating a point or a CI-only or config-only change is noise: only `thread_settle` runs, so no reviewer and no pass. The threads the code fixed or the author's reply settled are resolved at the gate. With nothing to post, no gate opens and the card keeps watching. A merge commit with its own conflict fixes counts as a merge of the base.
- `criteria_met` asks, for each acceptance criterion of the linked Jira tickets and board cards (at most 20), whether the diff meets it. A criterion it is sure is unmet becomes a `bug` finding and one it is unsure of a `question` finding. They count toward the verdict but get no line comment, since no line of the diff is theirs: the review's body names each one ("Not met: …", "Unclear: …"). A met one is a tick. The stage detail keeps `criteria` and the gate lists them. A re-review does not check criteria again.

`compliance` lists the regimes that apply to this repo: `soc2`, `hipaa`, `gdpr`, `lgpd` and `us_privacy`. A repo with no patient data leaves out `hipaa`. An unknown regime or a repeated one makes the file invalid. The compliance review (pack `compliance_review`) runs on a PR only when the list has at least one regime. Its lead dispatches the reviewer of each regime the diff touches, with the repo's control pages from its wiki (`Compliance/`). The machine reads the list when the review starts. So an edit counts from the next review on.

`budget.engines` caps an engine in this repo the way `MACHINE_ENGINE_BUDGETS` caps it on the machine. It uses the same keys and rules. It counts only this repo's stage runs this month. A key that names no engine or credential makes the file invalid. A key that names Claude also makes the file invalid. At the cap, the repo's tasks run that pack's default with a note. The machine's caps still apply on top.

A check with `coverage` names an lcov report that its run writes. The path is relative to the check's `cwd`. Vitest, jest, pytest-cov, cargo-llvm-cov and go via gcov2lcov all emit one. After the check passes, Verify reads the report. It measures *patch coverage*. This counts how many of the lines that the branch added the report saw run. A file with uncovered added lines gives a `test` finding (confidence 0.9). The verifier weighs the finding. The finding never fails the stage by itself. The numbers are in the stage's `detail.coverage` and in the verifier's input. The machine notes a missing or unreadable report. Neither case fails the stage. The machine ignores a path that climbs out of the worktree.

Each `services` entry runs as its own container. It runs beside every stage that runs the repo's code (implementing, verifying, e2e) and beside every check run. It runs on a private docker network for that run. Other containers reach it by its key as hostname. The `exports` become env in the stage or check container. The machine tears the services down with the stage. A pass of checks (the regression sweep, or Verify's checks) starts them once for the whole pass, on one network, and tears them down when the pass ends. So the pass pays for one database start, not one per check. Two tasks of one repo never share a database. A service whose `ready` line does not exit 0 within a minute escalates the stage with the service's log tail.

`PIPELINE.md` is the earlier per-repo file, with front matter that holds the `policy` keys and `qa_target` lines. It still works when there is no `luna.yaml`. The machine gives a deprecation notice once per repo. `luna.yaml` wins when both exist.

### The `economy` section (the token economy)

The `economy` section sets the loop guard, the learned facts and the tool pruning for the repository (RFC 0007, see [architecture](architecture.md#token-economy)). Every key is optional. Each key has the default shown. An unknown key makes the file invalid, and the machine names it.

```yaml
economy:
  loop_guard: on          # on | off
  facts: on               # on | free | off
  tool_prune: propose     # propose | off
  propose_every: 3        # closed cards between two runs of the fact proposer
  promote_cards: 5        # distinct cards a fact needs before the retro can promote it
  guard:
    judge_confidence: 0.7
    redirects: 1
    backstop_mult: 2.5
    envelope_min_samples: 5
  prune:
    runs: 10
    min_cards: 2
    cards: 5
```

| Key | Default | Bounds | What it does |
|---|---|---|---|
| `loop_guard` | `on` | `on`, `off` | `off` gives the run no loop guard. No redirect and no stop happen. |
| `facts` | `on` | `on`, `free`, `off` | `on` states free facts and proposed facts to each run. `free` states free facts only and makes no model call. `off` learns and states none. |
| `tool_prune` | `propose` | `propose`, `off` | `propose` collects tool evidence and proposes unused tools. `off` collects none, proposes none and applies no mask. |
| `propose_every` | 3 | whole number, 1 to 100 | The fact proposer runs after this many closed cards of the repository. |
| `promote_cards` | 5 | whole number, 1 to 100 | A fact needs this many distinct cards before the retro can offer it for the project context. |
| `guard.judge_confidence` | 0.7 | 0 to 1 | The least confidence of a `loop_judge` verdict that the guard acts on. |
| `guard.redirects` | 1 | whole number, 0 to 3 | The notes a run gets before the stop. `0` stops the run at the first stuck verdict. |
| `guard.backstop_mult` | 2.5 | 1 to 10 | A stuck segment past the envelope times this number is stopped with no judge. |
| `guard.envelope_min_samples` | 5 | whole number, 1 to 100 | The passing runs of a pack that the guard needs before it acts. Under it, the guard only records. |
| `prune.runs` | 10 | whole number, 1 to 500 | The runs a tool must go unused over, across at least `prune.min_cards` cards, before the machine proposes it. |
| `prune.min_cards` | 2 | whole number, 1 to 100 | The distinct cards that go with `prune.runs`. |
| `prune.cards` | 5 | whole number, 1 to 100 | The machine also proposes a tool that went unused over this many distinct cards. |

A repository can turn a mechanism off, or tune a number inside its bounds. A tuned number can make a mechanism more eager as well as less. A lower `guard.backstop_mult` or `guard.redirects` makes the guard stop sooner. A repository cannot do these things:

- Turn on what `MACHINE_ECONOMY=off` turned off.
- Change the fixed rules: the gate and stuck numbers, the 90th percentile and its margin of 1.25, and the fact lifecycle.
- Add a tool or widen a pack's access. A mask only removes.
- Approve a mask, drop a fact or restore a tool. A person does that through the routes in [api.md](api.md).

## MCP servers: `mcp.yaml` and `pnpm mcp`

The machine bridges the tools of MCP servers into the stages whose pack names them (RFC 0013). Only the machine declares a server; a repository's `luna.yaml` `design` narrows. The file is `~/.config/hardness/mcp.yaml`, or the one `MACHINE_MCP_SERVERS` names:

```yaml
untrusted: deny            # allow: a card from outside the repository's own people may also be given bridged tools (default deny)
servers:
  - name: figma-desktop    # lowercase letters, digits and dashes; a stage sees it as figma_desktop_<tool>
    transport: http        # http (needs url) or stdio (needs command)
    url: http://host.docker.internal:3845/mcp
    credential: { kind: none }          # none, oauth, or ref: { kind: ref, ref: "env:NAME" | "literal:<value>" | "op://vault/item/field" }
    tools: [get_design_context, get_screenshot]   # the most the machine bridges; a pack and a repo can only narrow it
  - name: figma
    transport: http
    url: https://mcp.figma.com/mcp
    credential: { kind: oauth, scopes: [mcp:connect] }
    tools: [get_design_context]
```

The machine keeps an image that a tool returns only up to 3 MiB, at most 8 a call and 20 MB a run. It drops the rest and counts them in `imagesDropped`. A pack that reads images (`vision: true`) runs only on an engine whose catalog model has `vision`.

`op://` references need the 1Password CLI installed and signed in inside the machine's image; `env:` works without it. A `ref` token reaches a stdio server as `MCP_TOKEN` in its environment and an http server as a bearer header; it never reaches a stage container.

| Command | What it does |
|---|---|
| `pnpm mcp status` | lists the declared servers: transport, whether a token is saved, whether the server answers, its tools |
| `pnpm mcp login <server>` | asks the machine for the authorization URL, opens it in the host's browser, and waits for the redirect (`MACHINE_PUBLIC_URL`, else the machine's port). It waits until the machine says the login is over (`loginPending` in `GET /mcp`). It fails when the login did not finish (`loginFailed`), even with an older token still stored. A login is good for ten minutes, and a new one replaces the server's earlier one. The tokens are kept in `<MACHINE_STATE_DIR>/mcp/<server>.json` |

`pnpm mcp` talks to the machine API at `MACHINE_URL` (default `http://localhost:4317`) with `MACHINE_API_TOKEN`, else `~/.config/hardness/machine-api-token`. A server that refuses dynamic client registration (Figma's remote server) needs a client registered by hand, saved as `<MACHINE_STATE_DIR>/mcp/<server>.client.json`, which the login reads.

| `design.parity.bar` | `0.75` | the confidence (0 to 1) under which the parity reviewer opens the `awaiting_design` gate. |
| `design.parity.publish` | `auto` | whether the frame | build pair images go on the PR and into Evidence. `auto`: only when GitHub says the repository is private. A public repository, or one whose visibility cannot be read (no token, no GitHub remote), counts as public. `always`: publish. `never`: list the pairs on the board only |
| `design.budget.max_tokens` | `1000000` | the tokens the designer agents may spend on one card. `0` is a config error: use `design: off` |
| `design.budget.max_minutes` | `45` | the minutes the designer agents may run on one card. `0` is a config error: use `design: off` |

The machine finds a card's design in the Figma links of the issue or ticket and its attachments. Else it uses `design.figma`.

The spec runs in Plan, before the planner, on a card with a design reference or on a `frontend` card. A fast-lane card gets a spec only when it has a reference. A failed spec never stops the plan: the plan goes on without it and the gate says so. The audit runs in Verify's browser step, only when the browser run passed. It needs a QA target. With no `verify.e2e.start` and no deploy, the browser run boots its own server, so the audit is skipped and `detail.a11y` says so. Audit blockers send the card back to Build through the e2e loop, so they count against `verify.e2e_rounds`.

### Design parity and the sign-off gate

RFC 0013, phase 3. When a change touches rendered files and the card has a design reference, the browser run also captures each UI scenario, and a `design_parity` reviewer compares it with the Figma frame. Open findings, a frame that could not be compared, or a confidence under `design.parity.bar` stop the card at `awaiting_design`. It is a gate in Verify, and `design: off` turns it off with the other designer steps. See "Design parity and the sign-off gate" in [architecture.md](architecture.md).

- **Waive.** `POST /tasks/:id/design/findings/:findingId/waive` takes `{ kind: "not_a_difference" | "accepted", reason }`, a reason of 3 to 500 characters. The board's `:waive <finding id> <reason>` and `:accept <finding id> <reason>` call it. The board's Design page, in the rail at the gate, shows each frame beside its build. Approve (`a`) and send back with a note (`r`) are the ordinary decision. A waiver holds in later rounds while the difference is the same. That means the same finding, with the same expected and built values (parity) or the same state and axe rule (accessibility). A changed value opens the finding again.
- **Ground truth.** On a repo that keeps ground truth, a waiver is written to `<MACHINE_STATE_DIR>/ground-truth/design_parity/<task>-<finding>.json` and a sign-off to `<task>-<gate>.json`. The reasons pass the machine's text cap and escaping first. `pnpm eval harvest --pack design_parity --include-images [--since <date>]` turns the waivers into eval cases ([evals/README.md](../evals/README.md)). A case copies a screenshot of the app and a render of the frame, so without `--include-images` the command writes nothing.
- **Kept at sign-off** is not stored. It is derived: the findings on an approved gate that are not waived.
- **Publishing and visibility.** `publish: auto` asks the GitHub port, `GitHub.repoPrivate(slug)`. It answers `true`, `false` or null; the no-token adapter answers null, and null counts as public. So a machine with no GitHub token never publishes a pair under `auto`.
- **Known gap.** The ship monitor's restack rebuilds the PR body without the card's facts. The Design & accessibility block drops then, as the findings already did.

### The ui-designer helper

RFC 0013, phase 5. On a card with a design reference, `implementing` may hand a pure UI slice to a writable helper in its own container (see [architecture](architecture.md#pipeline), Build step 4). Nothing here is an environment variable. The limits are fixed in the machine's code:

| Limit | Value | What it does |
|---|---|---|
| `MIN_HELPER_MINUTES` | `8` | the machine refuses to delegate when the helper would get fewer minutes than this: the smaller of the design budget's minutes left and the implementer's minutes left, less its reserve |
| `IMPLEMENTER_RESERVE_MINUTES` | `3` | minutes of the implementer's budget that the helper's limit never takes |
| helper requests | `4` per run | `slice_delegate` calls the build watch answers; past this the watch answers with an error itself |
| pick requests, pick acks | `12` per run each | the pick handshake's own cap |
| helper commits | `20` | the most commits the machine takes from one helper |
| `slice_wait` | `240` s at most | one wait; it returns `running` after that and the agent asks again |
| `HELPER_START_LIMIT_MS` | `75` s | the machine gives up on a helper that has not started by then (a slow sync or clone), inside the factory's 90 s wait for the answer |

The helper runs at `effort.implementing` of the repo's `luna.yaml` (there is no per-task effort), on `claude:sonnet` or the repo's `engines.ui_design`. Its tokens and minutes count against `design.budget`, not Build's budget. The pick needs git 2.40 or later on the machine. On an older git the machine turns delegation off, tells the implementer, and the implementer builds every slice itself.

Delegation is off, with the reason given to the implementer, when:

- `design: off` is set for the repo (the helper is a designer step);
- the card's design is off (`design.card_off`, from an approved `design_budget` escalation with `response.design = "off"`);
- the card has no design reference;
- the design budget is spent;
- no slice of the plan is a pure UI slice.

A merge conflict that survives the one re-run escalates the card as `merge_conflict`.

### The design budget

The designer runs of a card (the spec, the audit) count against `design.budget`. The machine reads the runtime's own token count and the run's minutes, never a model's text. When a run spends the budget, the next designer step escalates the card with the reason `design_budget`. A person answers it at the escalated gate:

- Approve: the card gets a fresh design budget (`design.budget_reset`).
- Approve with `response.design = "off"`: also turns design off for this card (`design.card_off`). Every designer step is skipped for it.

On-demand runs have no card, so the budget does not apply to them. The pack-run cap and the daily spend ceiling do.

### On demand: `POST /design/spec` and `POST /design/audit`

Both take the machine API token and a `repo` that is a checkout the machine knows. The machine resolves the link, the QA target and its credential itself. A client never sends a URL, a host or a credential.

| Route | Body | Answers |
|---|---|---|
| `POST /design/spec` | `{ repo, link, engine? }`, a Figma link | a `DesignSpecReport`: the design reference and the spec |
| `POST /design/audit` | `{ repo, target, engine? }`, the name of one of the repo's `qa_targets` | an `A11yReport`: the findings at the repo's level and mode, the pages and notes |

They run through the same machinery as `POST /ticket-chat`: the pack-run cap, the daily ceiling, a `pack_runs` row and the untrusted sandbox. The machine keeps no report. The errors are `404 unknown_repo`, `404 unknown_target`, `400 no_design_reference`, `409 design_off`, `503 qa_image_missing` and `503 agents_off`. A run from these routes counts as trusted for bridged tools only (it holds the machine token, so it is the operator): a default machine, with `untrusted: deny`, still gives it the Figma tools. The pack and the sandbox still treat every input and every tool result as data.

The board runs them: `:spec <figma link>` and `:audit <qa target>`. The report opens in a popup, and `c` makes a card from it.

### Mobbin

`design_spec` and `a11y_audit` may read Mobbin through the bridge, with the search tools only. Mobbin is off until the operator declares it in `mcp.yaml`. Check Mobbin's terms of use before you do. Luna has not.

### Engines

`design_spec` runs on Claude (`claude:sonnet`, `claude:opus`). `a11y_audit` is Claude-only too. Codex joins it when an a11y eval on `codex:sol` matches the Claude baseline. The cases are `evals/design_spec/cases` and `evals/a11y_audit/cases`; see [the evals](../evals/README.md).

## Machine sandbox policy

The owner's file (`~/.config/hardness/sandbox.yaml`, or the path in `MACHINE_SANDBOX_POLICY`) says what any repository's sandbox may ask for. A repo's `luna.yaml` stays inside it; the file is never read from a checkout. Every key is optional and its default is today's behaviour. An unknown or invalid key stops the machine at start and names it (`limits.max_cpu: ...`). `GET /health` shows the policy in force as `sandboxPolicy`. The machine reads the file only at start. An edit needs a restart. If `seccomp` names a path, the file must exist, be a readable regular file and parse as JSON. Otherwise the machine stops at start and names the key and the path.

```yaml
runtime: { default: runc, untrusted: runc }   # runc | runsc (read where trust is known)
seccomp: default                              # default | an absolute path to a seccomp profile
limits: { max_cpu: 128, max_memory_gb: 1024, max_pids: 1024 }
egress: { deny: [], max_repo_hosts: 50, repo_hosts: allow }   # repo_hosts: allow | deny
images: { repo_base: allow, devcontainer: allow }             # allow | deny
cache: { split_by_trust: true }
bash_sandbox: off                             # off | on
```

How the bounds apply to a repo's `luna.yaml`, each with a reason left where you will see it:

| Key | Effect | Where the reason is |
|---|---|---|
| `limits.max_cpu`, `limits.max_memory_gb` | a repo's `sandbox.cpu` and `sandbox.memory_gb` are capped | a note on the task, at the start of a stage |
| `egress.deny` | every host the repo chose is dropped when it matches an entry (`*.x.com` covers subdomains): `sandbox.egress.allow`, the hosts a lockfile's `resolved` URLs name (and a Yarn 2+ lockfile's `resolution:` URLs, such as `xlsx` fetched from `cdn.sheetjs.com`), the `qa_targets` hosts and the `deploy.url_pattern` host. A repo wildcard `*.S` goes too when a deny names `S` or a host under it. Case, a trailing dot and a port are ignored. GitHub, each ecosystem's own registries and the engines' hosts are the machine's and stay | `bounds` on the repo's row in `GET /repos` |
| `egress.repo_hosts: deny` | every one of those repo hosts is dropped | the same |
| `egress.max_repo_hosts` | only the first N repo hosts are kept, counted over all of them in that order: allow list, lockfile, QA targets, preview | the same |
| `images.repo_base: deny` | `sandbox.image.base` is ignored (the machine's image runs) and `POST /repos/base/approve` refuses | the same, and the refusal |
| `seccomp: <path>` | stage, check, app and service containers get `--security-opt seccomp=<path>` | none; it is the machine's own setting |
| `images.devcontainer: deny` | `.devcontainer/devcontainer.json` is not read: no image and no `containerEnv` from it | none |
| `limits.max_pids` | the `--pids-limit` of stage, check and app containers; a service gets the same value, at most 512 | none; it is the machine's own setting |
| `limits.max_cpu`, `limits.max_memory_gb` on services | each service runs with `--cpus` and `--memory` of the bounded size of the container it runs beside | none |
| every container | a luna.yaml proof (the setup stage's proposal or `POST /repos/config/prove`) runs on the file's sandbox held within the policy: cpu, memory and hosts, with the reasons in the proof's `bounds` and the setup notes. On-demand runs (`POST /runs`, Slack triage, Jira intake) run as untrusted input; evals run as trusted, with the engine relay and the pack's own egress list, as the machine runs the pack; the graph build runs as trusted, the video tools by the card's trust. They all take the policy's seccomp, runtime, process limit, cpu and memory, and the daemon's seccomp and runtime are checked before a check session's or the app's services start | none; it is the machine's own setting |
| `runtime.default`, `runtime.untrusted` | `--runtime` for stage, check, install, app and service containers of a trusted or an untrusted card (`runsc` is gVisor). `runc` adds no flag. A daemon without the runtime ends the card as `env_broken`, step `runtime`. The egress proxy stays on `runc` | a note on the task says an untrusted card runs untrusted |
| `cache.split_by_trust` | an untrusted card (a GitHub issue or PR from outside `OWNER`, `MEMBER` or `COLLABORATOR`, or with no association on record) uses `hardness-cache-<repo>-untrusted`; `false` shares one volume | the same note |

### Toolchains

When the machine probes a repo's own base image, it also runs the version command of each `toolchains` entry it knows (node, python, go, rust or cargo, java, ruby, pnpm) and compares the major, and the minor when you give one. A tool that differs or is missing becomes a line under `notes` on the repo's row in `GET /repos`, naming the tool, the wanted version and the found one. It never blocks a run, and the machine installs nothing.

### Devcontainer support

When a repo's `luna.yaml` names no `sandbox.image.base`, the machine reads `.devcontainer/devcontainer.json` or `.devcontainer.json` from your checkout (comments and trailing commas are fine). Its `image` is the base, and you approve it as you approve any base. Its `containerEnv` (plain strings, not the proxy, the loader or `PATH`) reaches the repo's install, checks and app, not agent stages. `features`, lifecycle commands (`postCreateCommand` and the rest), `mounts`, `runArgs` and `remoteUser` are not applied; `GET /repos` lists each under `notes` as "not applied: <why>".

`build.dockerfile` (with `context` and `args`) is a base when luna.yaml names no `sandbox.image.base` and the devcontainer has no `image` (either one wins, with a note). Nothing builds until you approve the Dockerfile on the board (`A`): the approval is its exact sha-256 (the file, the sorted `build.args` and the context path), and any edit asks again. The context is `.devcontainer/` or `build.context`, and must stay inside your checkout. **This one reviewed build runs with open network access and no secrets, credentials or SSH, because BuildKit cannot use the per-run egress proxy. Every other container keeps default-deny egress.** `images.repo_base: deny` or `images.devcontainer: deny` refuses it. The approval does not cover the other files of the build context: a script the Dockerfile copies and runs can change without a new approval. The machine reads the context from your own checkout, never from a card's folder, so such a change still comes through a merged PR.

`bash_sandbox` is accepted and has no effect: the nested Bash sandbox was not built (see RFC 0009). With `on`, the machine logs a warning at start, and `GET /health` lists `bash_sandbox` under `notInForce`.

## GitHub gates

`pnpm --filter @hardness/machine gates owner/name [--checks board,machine] [--dry-run]` applies a repository ruleset named `hardness gates` to the default branch. The ruleset needs one approving review from someone other than the last pusher. It dismisses reviews when the branch moves. It allows no deletion and no force-push. It needs the named checks green. GitHub enforces it whatever an agent does. The pipeline cannot approve its own PR. The machine's side of the same gate: a writable stage refuses any branch outside `task/`.

## Approving a release on GitHub

The machine opens PRs under the account its token belongs to. With `gh auth token` that is your own account, and GitHub never lets a PR's author approve it. So an approving review from you never counts. While a card's release question is open, a PR comment whose whole body is `/ship` (any case, trimmed) counts as the release approval instead. It must come after the head commit and after the question was asked, from an `OWNER`, `MEMBER` or `COLLABORATOR`. Your own login is allowed for a comment. The approver rules still apply: when `plan.approvers.high` is above 1, the plan's approver cannot release; when release owners are named, only they can. The machine records the login and the head, and logs `release.approved_on_github` with `how: comment`. The machine never posts a comment that is only `/ship`, so none of its own comments can count.

The other way is to give the machine its own GitHub account: a separate account that is a collaborator on the repos, with its token as `GH_TOKEN` (`GITHUB_TOKEN`) for the machine. Then you are not the PR's author, and your normal approving review on the head counts as before (`how: review`).

## Environment cache

Every stage and check container mounts a docker volume named `hardness-cache-<repo>` at `/cache`, with npm, pnpm, yarn, Go, cargo, pip and uv pointed at it. A retry, or the next task of the same repo, installs from that warm cache instead of the network. `docker volume rm hardness-cache-<repo>` starts a repo over. Stages run as a non-root user, so a cache volume that an older machine filled as root must be removed once, or its folders cannot be written: `docker volume ls -q --filter name=hardness-cache- | xargs docker volume rm`. It only costs a warm-up.

`docker compose up` (and `pnpm start`) runs the machine in a container that drives your host's Docker through its socket. Every path that the machine hands to `docker run` must exist at the same path on the host. So the compose file mounts these at identical paths:

| Variable | Default | What it does |

| `MACHINE_DOCKER_PORT` | `4318` | host port for the machine container (`pnpm dev` keeps `4317`) |
| `MACHINE_PUBLIC_PORT` | compose sets it to `MACHINE_DOCKER_PORT` | the port the host reaches the machine on, when it differs from `MACHINE_PORT`: the API also accepts calls from a page on it, so Swagger at `/docs` can try routes |

| `LUNA_REPOS_DIR` | `~/Developer` | where your repos live; task repo paths must be inside it, and so must `WORKTREES_DIR` |

The other variables in the table above pass through to the container as well.

## What the machine keeps for learning (wave 18)

Everything below stays on this computer. It stays under the state dir (`MACHINE_STATE_DIR`, default `~/.local/state/hardness`). It reaches `evals/` only through `pnpm eval harvest`. The command scrubs the data. A person reviews it in a PR. It also stays in the local trace tool that you already run. The machine pushes nothing to the datasets or labelling queue of the trace tool, except by a command that a person types.

- **Decision records** (`MACHINE_DECISIONS`, on): one per decision pack call. Each holds its stored (redacted) context, answer, verdicts, what the machine did with it (`acted`), cost and later truths. Files are owner-only (0600, folders 0700).
- **What a review learns.** A review's own decisions get truth from what a person and the PR do next, written onto the records under the same `learning.truth` switch. When the verdict is posted with `a`, each finding that reached the gate as a line comment labels its `finding_confirm` record (`real: true` if the comment was posted, `real: false` if it was proposed and is gone from what was posted; `kind: person`). Dropping the review with `r` labels nothing. For the threads a review answered, the machine keeps beside the card (`<state dir>/tasks/<id>/review-threads.json`) which `thread_settle` record resolved each one and which `comment_intent` record read an acknowledgement. A resolved thread that is open again at the next re-review labels `thread_settle` wrong (`addressed` or `reply_holds` no); one still resolved when the PR merges labels it right; an acknowledged thread that a later commit settles as fixed labels `comment_intent` `acknowledgement` (all `kind: outcome`). Not labelled: the `addressed: no` of a thread left open, `already_raised`, `finding_classify` after a review, and a thread outcome when the PR closes unmerged.
- **Traces** (`MACHINE_TRACES`) have four modes. `off` sends nothing. `metadata` sends one trace per stage with the facts of the run. `host` is `metadata` plus, from the host alone, the last 200,000 characters of the transcript. For the machine's own decisions, `host` also adds the stored context and the answer. `full` adds the container's own spans and hands the key to the container, so it is never a default. `host` is the default **with a trace key and a collector on this computer**. The collector is `localhost`, a loopback address, or the compose service name `lmnr-app`. A collector at any other address defaults to `metadata`, and the boot line says why. So an upgrade never starts to send contexts, answers and transcripts to a hosted collector. Set `MACHINE_TRACES=host` to ask for it. Without a key, tracing is off. The machine then logs once at boot `traces off: no trace key; decision records and ground truth are still kept`. In `host`, no container gets the key, the address or the span. A collector that does not answer gives one warning line and no traces until the next start. `docker compose --profile observe up -d` starts the collector.
- **Retention**: `MACHINE_DECISIONS_RETENTION_DAYS` (365) bounds decision records and the files under `<state dir>/ground-truth/`. `MACHINE_DECISIONS_MAX_MB` (4096, 0 for no cap) bounds `decisions/`.
- **`learning` in `luna.yaml`** (wave 18): `records` (true), `context` (`full` or `answers`: keep no context), `truth` (true), `traces` (`off`, `metadata` or `host`). The machine refuses `full` here. A repository can only lower what the machine keeps. It can never raise it. `MACHINE_DECISIONS=off` or `MACHINE_TRACES=off` is a ceiling over any repository.
- **Disk, as an estimate (not measured)**: a card leaves a few dozen records. Each record has a few to a few tens of kilobytes. The trace tool also holds a transcript of up to 200,000 characters. This is about 0.2 to 1 MB per card. So a few cards a day take roughly 0.5 to 2 GB a year before the cap. `pnpm eval records --sizes` prints what `decisions/`, `ground-truth/` and `evals/.runs/` take today.
- **The prune** (nightly, in the machine's sweep) removes only what retention covers. It removes decision records and ground-truth files older than the retention. Over the size cap, it removes records with no truth first, oldest first. It acts only under the machine's own `decisions/` and `ground-truth/` folders. It acts only on names that it lists itself. It never acts on a link or on a name that is not its own pattern. It never removes a record younger than 7 days. It never removes a record that an open card needs. It logs one line. The machine does not prune the own store of the trace tool. To empty that store, run `docker compose --profile observe down --volumes`, which removes its data. `pnpm eval prune-runs [--older-than 30]` clears old run folders under `evals/.runs/`.
- **A transcript** goes to the trace tool only for the machine's own calls. It never goes there for a private conversation. A client's `POST /runs` call and the call of a private thread send the facts of the run and no transcript. Every transcript, span input and span output passes the machine's secret values, the token shapes, and the masking of e-mail addresses and phone numbers. The secret values are its tokens, the provider keys, the Claude token, the Codex login, the database password and the Slack tokens.
- **A client's record** (a `POST /runs` call) keeps the answer and not the context it sent.
- **What a pull writes back**: `pnpm eval dataset pull` writes cases (marked for review) and nothing onto a record. With `--write-labels`, it prints each label. It writes the label as a `queue` truth. It writes only onto a record of the machine's own that waits for a label here. The record must have no label from a person. A label that a person types at the board or at the command line always outranks it. The command skips a label that is not valid for the questions of the pack. `dataset push --queue` sends the same records that `label push` does, and no others.
- **What the machine never keeps, whatever a switch says.** It never keeps a secret, the text of a private Slack conversation, or personal data that `maskPii` masks in every copy out. The redactors run before the machine stores or traces anything. The text of a private Slack conversation leaves the stored record, and harvest and the queue skip it. A full trace and a kept decision context pass the same redaction as a stored record. Every ground-truth file passes the machine's secret values and the token shapes. The outcome file of a private conversation holds the outcome, the size of the difference and the record ids, with no text. The machine caps one record's stored context at 200 KB. It cuts a string at 20,000 characters with a marker. Each cut counts as a redaction.
- **The size cap** applies at the nightly sweep, not at each write. It never removes a record with a person's truth, a record under 7 days, the record of an open card or a ground-truth file. When what the sweep cannot prune is over the cap, the sweep says so in one warning line. The machine removes temporary files that a writer left after a day. It does not follow a symbolic link where `decisions/` or `ground-truth/` should be.
- **Limits, in plain words.** The machine does not catch a secret that someone splits, reverses, hex-encodes or compresses. It does not catch a secret with no known shape that is not among the machine's own values. The own database of the trace tool has no retention of the machine's. Anything on this computer that holds the project key reads every trace. A stored record keeps a ticket's personal data as the model got it. A harvested case replays a stranger's text to a model. `evals/baselines/` and the case folders are inputs to the defaults rule. So they need the same review as code.

## Observability (Laminar)

Luna keeps the facts of every run in Postgres (`stage_runs`, `pack_runs`) and the transcripts on disk. Laminar ([laminar.sh](https://laminar.sh), Apache 2.0, self-hosted) gives them a UI. The UI shows one trace per stage run, `POST /runs` call and eval case. It shows a session per task and cost over time. It also shows the replay evals as evaluations that you can compare across engines. Laminar is opt-in and local:

1. Run `docker compose --profile observe up -d`. It starts Laminar's lightweight stack beside the machine. The stack has its own Postgres, ClickHouse and Quickwit, bound to localhost. It needs about 2 GB of images and a couple of GB of RAM while up. The UI is `http://localhost:5667`. Anyone on this computer can sign in.
2. Create a project in the UI.
3. Put the project's API key in `~/.config/hardness/lmnr-project-api-key` (`umask 077`) or in `LMNR_PROJECT_API_KEY`. `make integrations` does this for you.
4. Restart the machine (`pnpm start` or `pnpm dev`). It logs `traces host · Laminar at …`. `MACHINE_TRACES=metadata` keeps only the facts of the run. `MACHINE_TRACES=full` also hands the containers the key.

The machine opens one root span per run. `application/telemetry.ts` is the port. `adapters/laminar/` is the adapter. It is the only place in the machine that imports `@lmnr-ai/lmnr`, and it loads only when you set a key. In `full` mode, the machine also hands the stage container the key, Laminar's address and that span, serialized, as `LMNR_SPAN_CONTEXT`. Inside the container, the factory (`apps/factory/src/core/telemetry.ts`) initializes Laminar from them. It plugs in Laminar's integrations. So the model calls are children of the machine's span. The integrations are these: the Claude Agent SDK's `query()` wrapped (every turn, tool call and subagent, with prompts, completions, tokens and cost). The AI SDK's telemetry registers before Jev's `experimental_decide`. Each built eve agent exports through `LaminarSpanProcessor`. Those spans are their own traces. The eve session id that the run's `session` event names joins them to the run. The machine closes the root span after the container exits. It adds the facts of the run row and, in `full`, the transcript. If Laminar is down at boot, the machine runs without traces and says so once in the log. The machine drops a span that it cannot send, with a warning. A container that cannot load the SDK runs untraced and says so on its transcript. The SDK runs dotenv on its working directory when it loads. The factory removes whatever dotenv added. So a `.env` committed to a repo cannot change the environment of a run. `pnpm eval` reports to the same Laminar from the same variables (see [evals/README.md](../evals/README.md)). Laminar's own AI features need a provider key in its containers. They are chat with a trace, SQL with AI, and Signals. Luna leaves them off here. The `eval_judge` pack is the judge. Direct Anthropic or OpenAI SDK instrumentation does not apply. The factory never imports those SDKs.

## Runner image

The image carries Node 24, `gh`, `shellcheck`, `openssh-client` (a repo's tests may run `ssh-keygen`, as on CI's runners; outbound SSH stays blocked by the egress proxy), Go, and pnpm at the version this repo's `package.json` pins. CI pins the same Go and Rust versions as the image (`validate.yml`; a test checks). It carries Python with a pinned Graphify (`GRAPHIFY_VERSION`). The headless code-only graph build of Graphify is `/graph-tools/build.py`, run as an entrypoint override. A stage reads the repo's graph read-only at `/graph`. The image carries a pinned Rust toolchain (`RUST_VERSION` in `apps/machine/runner/Dockerfile`, with clippy and rustfmt). So a repo whose suite is `cargo test` runs as it is. The image carries the Codex CLI (`CODEX_VERSION`, pinned). Eve's `chatgpt()` asks the CLI for the token of the login. The image also carries the factory with its three SDKs installed. It carries an eve agent built for each pack that allows an eve engine (`triage`, `slack_triage`, `chat_triage`). It carries one generic `decide` app for the decision packs and for each helper on one (`verifying--second-opinion`). Every check container also gets your git identity. This is the `user.name` and `user.email` that git resolves for the repo. So a suite that commits in a scratch repo runs as you. A repo with no identity escalates the verifying stage instead of committing as nobody.

`pnpm --filter @hardness/machine runner:build` runs `apps/machine/runner/build.sh`. The script builds the image from this checkout, with the repository root as the build context. It copies in `apps/factory/` and `packages/contracts/`. It installs them with the workspace lockfile. So the image runs exactly what the checkout tests. The script labels each image with a key over those files and the Dockerfile. It skips the build when that key is current. So `pnpm images` (run by `pnpm start` and `pnpm dev`) is instant when nothing changed. `REBUILD=1 pnpm images` builds anyway. The image has the tags `hardness-runner:dev` and `hardness-runner:<key>`. `runner-qa:build` runs the same script with `--qa`. It then builds `hardness-runner-qa:dev` from `apps/machine/runner-qa/Dockerfile` on top of it. `runner-video:build` runs it with `--video`. This builds the QA image first. It then builds `hardness-runner-video:dev` from `apps/machine/runner-video/Dockerfile` (repository root as the context). `pnpm images` builds all three.

The video image adds the tools in `/video-tools` on top of the QA image. `narrate.ts` makes the voice with kokoro-js. It makes word timestamps with whisper-tiny.en through transformers.js. The build bakes both models into `/models`, and the tool reads them offline. `cards.ts` renders a time-driven card page frame by frame through the chromium of the QA image. `compose.ts` does the ffmpeg cuts, narration, captions and chapters. `measure.ts` makes frame statistics, loudness, contact sheets and a transcript. `fixture.ts` is the demo fixture that the recorder imports. The logic is in pure libraries beside them that the machine's test suite covers. Each tool reads and writes only under its job dir `/work`. The machine runs it with no network and no credential. `pnpm --filter @hardness/machine runner-video:smoke` builds a 20-second synthetic job. It runs all four tools inside the image. Size, measured at build: the video image takes 6.55 GB on disk (1.79 GB compressed). The QA image takes 5.56 GB (1.49 GB). So the video image adds about 1 GB. The two models take 235 MB of it. The npm packages (onnxruntime among them) take most of the rest.

Inside a stage container, the runner sees `/in/stage.json`, `/out`, `/work` and `/session`. `/work` is the card's work folder. It has a git repository of the agent's own in `.git`, which the machine never reads. `/session` is the task's SDK session dir (`CLAUDE_CONFIG_DIR`). `LUNA_FACTORY=1` marks the run. `LUNA_STAGE_DRY_RUN=1` renders the prompt and the SDK options without a model call (the sandbox smoke uses it). On an eve engine, it prints the agent, model, tools and guard policy instead. For a decision pack, it prints the questions and the state that it would send to Jev. A repo may keep binding rules for every stage in `docs/agents/project-context.md`. The memory review proposes additions to it.

## Board

The board uses whichever machine answers. It tries `http://127.0.0.1:4317` (`pnpm dev`) first. Then it tries `http://127.0.0.1:4318` (`pnpm start`). It checks again on every reconnect. `HARDNESS_MACHINE_URL` pins one address instead. When `MACHINE_API_TOKEN` or `~/.config/hardness/machine-api-token` holds a token, the board sends it on every call. `HARDNESS_REPOS_DIR` is where the board's repo search (`R`) looks for repos (default `~/Developer`). `LUNA_APPROVER` names you on every approval and send-back that the board makes. If you leave it unset, the board sends no name. A plan of High risk needs two distinct names. So without it, the machine answers `approver_required`. The name is an attestation, not access control. The machine has one bearer token and no per-person identity. So the two-approver rule records who said they approved. It cannot stop one token holder from naming two people.
