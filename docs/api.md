# API

The machine's HTTP API, read straight from `machine/src/adapters/http/app.ts`. Shapes are defined in `contracts/src/api.ts`.

| Method | Path | Does |
|---|---|---|
| GET | `/health` | Liveness check; also the stage pool: `slots {max, active, draining, latched}`, where `latched` lists each credential (`claude`, `codex`, `openai`, `typesafe`) whose usage window a stage hit and until when its queued work waits; work on another credential keeps claiming. |
| GET | `/packs` | Every pack in the registry (`contracts/src/packs.ts`), in `PackId` order: `{ id, agent, kind: "agent" \| "script" \| "decision", engines: { default, allowed, fallback? }, effort, writable, maxTurns, timeoutMs, states }`. `agent` is null and `kind` `script` for a pack that calls no model (`evidence`); `kind` `decision` is a pack of typed questions to a decision model (`triage_signals`, on `jev`, `claude:haiku` or `codex:luna`), with `agent` and `effort` null; `states` are the task states the pipeline runs it in (`reviewing_memory` runs inside `shipping`; `slack_triage`, `jira_intake`, `triage_signals`, `eval_judge`, `chat_triage` and the on-demand decisions (`risk_score`, `coverage_check`, `plan_check`, `red_check`, `scope_check`, `finding_classify`, `e2e_failure_cause`, `evidence_format`) and Ship's five decisions (`event_class`, `comment_intent`, `fix_scope`, `evidence_valid`, `worth_learning`, each on a `ship` context: a review event, a comment with the pack, a fix, or a finished task's retro facts) in none; `pr_reply` runs in `shipping`; `video_script`, `recording`, `video_qa` and `video_fix` in `evidence`, run as sub-runs by the video pipeline: the Slack inbox and Jira intake run the first two, `POST /runs` any of them but `eval_judge`, which only the evals runner runs). |
| GET | `/engines` | Every engine in `contracts/src/engines.ts`, in that order: `{ id, runtime, modelId, auth, status, available, reason?, spentThisMonthUsd, budgetUsd }`. `modelId` is the pinned ID the runtime passes its SDK, `auth` how a run is paid (`subscription` for Claude, whose API key is the fallback; `chatgpt` for the Codex login; `api-key` for `openai:*` and `jev`), `status` the catalog model's (`preview`, `ga`, `deprecated`). `available` says whether this machine has the credential the engine needs (Claude: `CLAUDE_CODE_OAUTH_TOKEN`/`ANTHROPIC_API_KEY` or their files; `codex:*`: a readable `~/.codex/auth.json`; `openai:*`: `OPENAI_API_KEY` or `~/.config/hardness/openai-api-key`; `jev`: `AI_GATEWAY_API_KEY` or `~/.config/hardness/ai-gateway-api-key`, else `TYPESAFE_API_KEY` or `~/.config/hardness/typesafe-api-key`), read on every call; `reason` says what is missing. An engine on a runtime `MACHINE_DISABLE_RUNTIMES` turned off is `available: false` with `reason: "disabled by MACHINE_DISABLE_RUNTIMES"`, whatever its credential. One at a monthly cap is `available: false` with `reason: "over its monthly budget ($20.00 of $20.00 on openai)"`. `spentThisMonthUsd` is this calendar month's recorded cost (stage runs, `POST /runs` calls, Slack triage runs) against the machine cap that binds the engine (`MACHINE_ENGINE_BUDGETS`: the one reached, else the one with least left, its own or its credential's, the credential's counting all its engines), else the engine's own; `budgetUsd` is that cap, null when none. A repo's `budget.engines` is not shown here. Never a credential's value. |
| POST | `/runs` | Packs on demand: `{ pack, engine?, context }` runs one context-only pack (one that runs in no task state) on data the client sends, with no task and no worktree, and answers `200 { answer, usage: { model, engine, turns, durationMs, costUsd } }` with the pack's answer validated against its schema. The packs and their `context`, which holds the pack's own key and nothing else: `chat_triage` `{ chat: { source: "slack" \| "teams", me: {id, name}, rules?, items: [{ id, place, kind: "dm" \| "group" \| "meeting" \| "channel", author, isBot, text, context?: [{author, text}], matched?, replies?, flag?: "urgent" \| "important", floor?: "P0".."P3" }] } }` (1 to 25 items; the answer is `slack_triage`'s: one `{ id, priority, category, expectsReply, summary, why, draft, refs, deadline }` per item), `triage_signals` `{ issue: { title, description, labels?, source? } }`, `risk_score`, `coverage_check` and `plan_check` `{ plan: { record, brief, criteria, assumptions, slices, rollback?, cases?, gaps?, round?, review?, map? } }` (the plan stage runs these itself; each answers its questions), `red_check`, `scope_check`, `finding_classify` and `e2e_failure_cause` `{ check: { kind: "red" \| "scope" \| "finding" \| "e2e", ... } }` (Build's and Verify's own checks, which the machine runs itself: `finding_classify` reads `{ kind: "finding", finding, excerpt? }` and answers `severity` as `blocker`, `should_fix` or `nit`; `e2e_failure_cause` reads `{ kind: "e2e", e2e: { verdict, summary, criteria, attempt } }` and answers `cause` as `product_bug`, `test_bug` or `env_flake`), `jira_intake` `{ jira: <JiraIntakeContext> }` (a known difference from Jira intake: here `/work` is empty, with no checkout of the repo, so the pack judges the issue on its text alone where intake's run can also read the code) and `slack_triage` `{ slack: <SlackTriageContext> }`. `eval_judge` is never run here: it is for the evals runner only. `engine` must be one of the pack's `engines.allowed` (default: its `engines.default`; no luna.yaml applies). An `X-Luna-Client` header (1 to 64 of `[A-Za-z0-9_.-]`, e.g. `notch`) names the caller in the record. 400 `not_on_demand` for a pack that runs in a task or `eval_judge`, `engine_not_allowed`, `invalid_request` for a context that does not fit the pack; 409 `no_credential` when this machine lacks the engine's credential (nothing ran); 409 `runtime_disabled` when the engine's runtime is turned off by `MACHINE_DISABLE_RUNTIMES` (nothing ran); 409 `budget` when the engine is at its monthly cap (`MACHINE_ENGINE_BUDGETS`; nothing ran); 422 `run_failed` with the run's error when the pack ran but gave no valid answer (no structured output, off-schema, a timeout, no result); 429 `rate_limited` with `resetsAt` (ISO, or null; the soonest of the windows hit) once the engine and every fallback the pack names (`engines.fallback`, skipping those whose credential is missing or whose window the pipeline holds) have hit their usage limit: a limit on the engine asked for moves the call at once to the next fallback, in the same place, `usage.engine` naming the engine that answered and each run kept as its own `pack_runs` row; 429 `budget` while the trailing 24 hours' spend is at `MACHINE_DAILY_BUDGET_USD` (nothing ran; a call's cost counts toward that ceiling like a stage run's, and there is no monthly one here, that one being per repo); 429 `queue_full` when two calls are running and eight wait (nothing ran); 503 `agents_off` only with `MACHINE_AGENTS=off` (a missing credential is the asked engine's own 409, so a machine with only a Codex login still runs `codex:*`). At most two calls run at once, apart from the stage pool's slots; up to eight more wait their turn. A client that disconnects is dropped while it waits, and its container is stopped while it runs (recorded as failed; the dead connection gets 499 `client_closed`). **What is kept**: one `pack_runs` row per call that ran (`pack`, `engine`, `model`, `client`, `ok`, `error`, `turns`, `duration_ms`, `cost_usd`, `started_at`, `ended_at`, and the run's `runtime`, `model_id`, `sdk_version` and `fingerprint`). **What is not**: the context and the answer. The run folder holding them (`MACHINE_STATE_DIR/pack-runs/<pack>-<uuid>`, apart from the stage runs' `runs/`: stage.json, result.json, the transcript) is removed when the call ends, answered or failed, and any a crash left is removed at start-up; the container is removed when it exits. The nightly sweep deletes `pack_runs` rows older than `MACHINE_RETENTION_DAYS` (90). |
| POST | `/drain` | Take no new work: running stages finish, the queue waits. Answers with the pool. |
| POST | `/resume` | Carry on: the queue is picked up again at once. |
| PATCH | `/slots` | `{max}`: resize the pool at run time (at least 1). |
| GET | `/metrics` | Factory metrics over a window: `?since=7d\|30d\|<ISO timestamp>` (default `7d`). Cycle time, first-pass rate, escalations, cost, queue depth, and `gates` (`answered`: gates you answered in the window, `withinSla`: the share answered inside the gate SLA, `waitMs`: median and p90 wait per gate state); also streamed as `task.metrics`. `&repo=<path>` limits the numbers to one checkout (`repo=` to the tasks with none); `&groupBy=repo` adds `byRepo`, one slim row per checkout (tasks, escalation rate, first-pass verifying, cost). `&groupBy=engine` adds `byEngine`, one row per engine the window's stage runs started on (`stage_runs.engine`; named engines in order, then `engine: null` for host-only stages and runs from before engines): `{ engine, stageRuns, firstPassRate, escalations, rateLimited, meanTurns, meanDurationMs, costUsd }`. `firstPassRate` is the share of first attempts that passed, of those that passed or failed; `escalations` counts the tasks that escalated in the window, each against the engine of its latest run before it; `rateLimited` the runs that ended on a usage limit (a fallback's run is its own row on its own engine); `meanTurns` and `meanDurationMs` are over the runs that passed or failed; `costUsd` sums the runs' recorded cost (`codex:*` runs record none). It composes with `repo`. `&groupBy=fingerprint` adds `byFingerprint`, one row per harness fingerprint over the window's stage runs (`fingerprint`, null for runs from before fingerprints and listed last, then the most runs first; `runs`, `passRate` of passed over passed and failed, `costUsd`, `durationMs` median and p90, the `stages` and `engines` it ran). Any other `groupBy` is a 400. |
| GET | `/tasks` | List every task with its state, column and `route` (`feature`, `setup`, or a PR task's `ci_fix`, `review` or `address`). Each task carries `jira` (the linked issue as last seen: `key`, `url`, `issueType`, `status`, `priority`, `dueAt`, `syncedAt`, `blocked` with `{wanted, current, why, at}` when the last declared transition was refused, `linkedAt` when the link was made by hand (null for one made with the ticket), `timeZone` the Jira site's zone once JiraWatch has read it; null when unlinked) and `sla` (the ticket's clocks, computed at answer time from the row's `state_since` and the running stage run: `gate {dueAt, overdue, targetSecs, since, state}` while waiting on you, `stage {dueAt, overdue, targetSecs, stage, warn}` for a running stage the repo gave a target, `cycle {dueAt, overdue, targetSecs}` and `jiraDue` for the issue's due date, which ends at 23:59:59 in the site's timezone (UTC until known) and whose `targetSecs` counts from the task's creation or its link time, whichever is later; each null when it does not apply, the whole thing null when none does). A minute tick republishes a task on `task.updated` when any clock goes overdue or a stage clock starts warning. Each task also carries `lastRun` (the latest stage run that ended: `{ stage, engine, outcome, summary, at }`, `summary` being the pack's summary, else its error, else triage's brief, cut to 2000 characters; null before any run ended) and `gate` (while an approval is open: `{ state, requested }`, `requested` being what the gate asks, e.g. the plan or the questions; at `awaiting_ship` it carries `evidence` with the pack's `format`, `summary`, `media[]`, `commitSha`, `note?` and `video?`, which a send-back with a reason answers; null otherwise), on `GET /tasks`, `GET /tasks/:id`, `task.updated` and the replay alike, so a client catching up needs no `GET` per task. A task intake made from a GitHub or Jira issue on a machine with a Jev credential carries `classification`, what `triage_signals` said about the issue: `{ kind, area, ready, size, confidence, at, model }` (`kind` one of `bug`, `feature`, `chore`, `question`; `area` the part of the repo; `ready` whether it has testable criteria; `size` the rubric score, 0 tiny to 3 large, fractional between; `confidence` the lowest of the answers'; `at` when; `model` the one that answered); null on every other task. Each task also carries `record` (triage's `TriageRecord`) and `evidence` (the `EvidencePack`: `format` `video`, `captures` or `text`, `summary`, `scenarios`, `findings`, `outOfMap`, `risk`, `rollback`, `howToVerify`, `commitSha`, `media[]` of `{ kind, label, url }`, a `note` when a format was degraded and, for a video, `video: { file, durationS, verdict: ship | one_more_pass | degraded, scores, defects[], rounds, transcript? }`), both null until a stage writes them, and `archiveReason` (`duplicate`, `sla_expired`, `rejected`, `not_for_agent`, `pr_closed`; null unless the task is `archived`). |
| POST | `/tasks` | Create a task: title, description, criteria, repo path, source (`source.kind: notch` for a Luna Notch work order: `{ ref, id, jiraKey? }`), `start: true` to start it in the same call, and `stages` (`{ "<pack>": "<engine>" }`, e.g. `{ "triage": "claude:opus" }`): the task's own engine per pack, over the repo's `luna.yaml` `engines` and the pack's default; 400 for an engine the pack does not allow (`GET /packs`) or a pack that never runs in a task (`slack_triage`, `jira_intake`, `triage_signals`, `chat_triage`, `eval_judge`). With an `Idempotency-Key` header (1 to 200 characters, kept on the task), a retry with the same key and body answers the task already made (200, no second task, started once) and the same key with another body is 409 `idempotency_conflict`, whose `taskId` names the task the key made. "The same body" is the same order with every default filled in (`description: ""`, `criteria: []`, `repoPath: null`, `source: null`, `stages: {}`, a source's absent `jiraKey` as null) and `start` left out, so an equivalent retry is never a conflict; a key used before this rule keeps matching a retry of the body it was first sent with; without one, every call makes a task (201). |
| GET | `/tasks/:id` | One task with its stage runs, approvals, recent events and artifacts. Jira events: `jira.linked {key, url, created?}`, `jira.unlinked {key}`, `jira.transitioned {from, to, fields?}`, `jira.blocked {wanted, current, why}`, `jira.commented {url}` (the "PR opened" comment went out for that url; it is what stops a repeat after a restart) or `jira.commented {kind: "shipped", number}` (the shipped summary went out once), `task.shipped {title, prUrl, number, mergedSha, by, format, howToVerify, media}` (the task's PR merged; `by` is `machine` or `person`, `media` has web urls only), `jira.moved {status, key}` (the issue reached Done, Cancelled or Won't Do in Jira while the task is open), `jira.intake {key, verdict, reason}` (made by intake). A verifying run carries `cases: [{ title, ok }]` (one verdict per approved case, from the pack's `results[]`; null when it reported none). Every stage run carries `engine`, the one it started on (null for a host-only stage or a run from before engines), and what its result named it ran on: `runtime` (`claude`, `eve`, `jev`), `modelId` (the pinned model ID), `sdkVersion` (the runtime's SDK version as installed in the image) and `fingerprint` (a sha256 over the template, role, skills, access, answer schema and factory rules it ran; see [architecture](architecture.md#factory-mode)), each null for a host-only stage, a run still going or one from before fingerprints; `stage.engine {pack, engine, reason}` says why an engine asked for was passed over (not allowed for the pack, or no credential on this machine, in which case the pack's default ran), and `task.stages {stages}` records each change of the task's engines. Every task carries `stages`, its own engine per pack (`{}` when it names none). |
| PATCH | `/tasks/:id` | Edit the ticket's text (title, description, criteria, repo path). `source` never changes once the task exists: another one is 400 `source_immutable` (the same one again is no change). The repo path moves only while the task has no worktree or branch, else 409 `has_worktree` (the same path again is no change); a refused edit changes nothing. |
| PATCH | `/tasks/:id/plan` | Edit triage's plan while it awaits your approval, or later while the task is `awaiting_test_check` (nothing is built yet; the approved plan is edited and the ticket's criteria follow): `{ "brief"?, "criteria"?, "assumptions"? }`, at least one field. Only the fields given change; slices stay as triage wrote them. Each edit appends `{ at, before, after }` (changed fields only) to the approval's `requested.revisions` and logs a `plan.edited` event with the field names. 409 `no_plan` at any other state. |
| PATCH | `/tasks/:id/cases` | Replace test_design's cases while the task is `awaiting_test_check`: `{ "cases": [{ "title", "criterion", "approach" }] }`, at least one. The open test-check approval keeps its other fields; logs a `cases.edited` event. 409 `no_cases` at any other state. |
| PATCH | `/tasks/:id/stages` | `{ "stages": { "<pack>": "<engine>" \| null } }`: set the task's engine for each pack named (`null` goes back to `luna.yaml`'s, else the pack's default); the others stay. Answers the task and publishes `task.updated`. 400 for an engine the pack does not allow or a pack that never runs in a task; 409 `stage_started` when a pack named has already run or is running on this task (nothing changes then). |
| GET | `/tasks/:id/diff` | The task branch against its merge base with the base branch (origin's default branch, else `main`, else the repo's HEAD): `{ base, head, files: [{ path, status: "A"\|"M"\|"D"\|"R", added, removed }] }`. `?file=<path>` adds `patch` (that file's unified diff). Read-only. 404 `no_worktree` when the task has no worktree or it is gone from disk. |
| DELETE | `/tasks/:id` | Delete a task with its runs, approvals and events (blocked while a stage is running); closes its herdr watch tab (via `task.closed`). |
| POST | `/tasks/:id/start` | Start the pipeline. A repo with no `luna.yaml` gets the `setup` stage and its gate before triage. |
| POST | `/repos/setup` | `{ "repoPath" }`: a setup-only task (route `setup`) for that checkout, started at once; its one gate is the proposed `luna.yaml` with the proof per check. Approving writes the file and closes the task. |
| POST | `/tasks/:id/answers` | Answer triage questions: `{ "answers": { "<question>": "<answer>" } }`. |
| POST | `/tasks/:id/decision` | Approve or send back whatever the task waits on, including an escalation: `{ "decision": "approved" \| "sent_back", "reason"?, "applyRules"?, "approver"? }`. `approver` names who decides (the board sends `LUNA_APPROVER`) and is kept on the decision (`response.approver`). A plan whose `requested.risk.level` is `high` needs two distinct names: the first approval keeps its name on the gate (`requested.approvers`, so a client shows 1 of 2), logs `approval.partial` and leaves the gate open (200, the task as it was); a second, different name closes it; the same name twice is `409 same_approver`, and no name on such a plan is `400 approver_required`. A gate triage opened for a reply or an archive (`requested.outcome` of `conversation` or `archive`) is approved in one click by anyone: an archive archives the task with its reason, a reply is recorded as a `task.reply` event (posted on the ticket's thread) and the task is archived as `not_for_agent`. A send-back at such a gate runs triage again; at the plan gate it runs the plan stage again. |
| POST | `/tasks/:id/abort` | Stop a running or queued stage; the task then waits for you. A Luna Notch task (`source.kind: notch`) also stops at an `awaiting_*` gate (the notch's Stop): the gate's approval is closed as `sent_back` with reason `stopped`, and the task goes to `escalated` with reason `stopped`, where approving re-runs the stage that opened the gate. For any other task, and for a notch task already `escalated`, an abort at a gate is 409 `invalid_transition`. |
| POST | `/tasks/:id/archive` | Ends the task as `archived`, a terminal state in Done, from any state that has not ended: body `{ "reason": "duplicate" \| "sla_expired" \| "rejected" \| "not_for_agent" \| "pr_closed" }` (400 for any other), the running stage stopped, the close steps run (the worktree is removed). The task carries `archiveReason`. A task that already ended is 409 `invalid_transition`. |
| POST | `/tasks/:id/resume` | Re-run the stage a task paused in after a usage limit. |
| POST | `/tasks/:id/worktree/remove` | Remove the task's worktree from disk. The task, its branch and commits stay. |
| GET | `/github/prs` | The PR inbox: every open PR involving you, as the machine last polled it: `{ prs, polledAt, error }`. Each PR carries its `split` (`review_requested`, `ready_to_merge`, `ci_failed`, `ci_running`, `changes_requested`, `mine`), `mergeState` (GitHub's own verdict: `CLEAN`, `HAS_HOOKS`, `UNSTABLE`, `BLOCKED`, `BEHIND`, `DIRTY`, `DRAFT`, `UNKNOWN`; `ready_to_merge` follows it), `checks` (`state`, `passed`, `total`, the `failed` checks and `all` of them as `{ name, state, url }`), `localPath` (the checkout the machine would act in; null until cloned) and `task` (the PR task in flight, if any). |
| POST | `/github/prs/refresh` | Poll GitHub now; answers the fresh snapshot. |
| POST | `/github/prs/:owner/:name/:number/actions` | `{ "action": "ci_fix" \| "review" \| "address" }`: creates and starts a PR task on the PR's own head branch; answers the task (201). 409 `pr_busy` while a task runs for that PR, `no_checkout` without a clone, `fork` for a fix or an address on a fork head, `own_pr` for a review of your own PR. |
| POST | `/github/prs/:owner/:name/:number/merge` | Merges the PR the way its repo allows (squash, else a merge commit, else a rebase) and deletes its branch; 409 `not_ready` unless its split is `ready_to_merge`. Answers `{ "merged": true }`. |
| POST | `/github/prs/:owner/:name/:number/close` | Closes the PR without merging (its branch stays); 409 `pr_busy` while a PR task runs for it, 404 `no_pull` for a PR not in the inbox. Answers `{ "closed": true }`. |
| POST | `/github/clone` | `{ "repo": "owner/name", "dest": "/abs/path" }`: clones in the background (202); the next `github.prs` event shows the checkout. 400 for a relative `dest`, a missing parent or an existing target. |
| GET | `/slack/items` | The Slack inbox, as the machine last polled it: `{ items, watches, me, polledAt, error, socket, sla }`. Each item carries its `split` (`needs_reply`, `waiting_on_them`, `decide`, `fyi`, `snoozed`, `done`), `triage` (priority, category, `expectsReply`, summary, why, draft, refs, deadline; null until the `slack_triage` pack ran, which happens after the poll publishes), `matched` (why it is in the inbox), `count` (messages folded into it), `replies`, `youReplied`, `reopenedAt`, `dueAt` (ISO: the latest message plus the reply SLA of its priority, null when no reply is expected or the item is cleared or snoozed), `overdue` (`dueAt` passed with no reply from you; recomputed every minute, so the stream publishes when an item goes overdue with no Slack event) and `linked` (`pr` from the PR inbox, `taskId`). `sla` is the reply SLA in effect, seconds by priority, from the rules file's `## SLA` (0 means none). `socket` is `off` without an app token. |
| POST | `/slack/refresh` | Poll Slack now; answers the fresh snapshot. |
| PATCH | `/slack/items/:id` | `{ done?, snoozedUntil?, seen?, priority? }`: `done: true` clears the item on our side (and in Slack when `MACHINE_SLACK_MARK_READ=on`), `false` reopens it; `snoozedUntil` is ISO or null; `priority` overrides triage and survives a re-triage. Answers the item; 404 `no_item`. |
| POST | `/slack/items/:id/reply` | `{ "text" }`: posts in the item's thread as you with your user token, clears the item and records the response time. 409 `no_token` without `MACHINE_SLACK_USER_TOKEN`. |
| POST | `/slack/items/:id/task` | `{ title?, repoPath? }`: a Backlog task from the message and its thread, `source.kind = slack`; answers the task (201). 409 `already_task` when the item already became one. |
| GET | `/slack/watches` | The handles, broadcasts, keywords and channels the inbox treats as addressed to you. `@here`, `@channel` and `@everyone` are built in. |
| POST | `/slack/watches` | `{ kind: "usergroup" \| "broadcast" \| "keyword" \| "channel", value, label?, channels?, priority? }`: `value` is the usergroup id, the broadcast word, the keyword or the channel id; the label is resolved from Slack when absent (201). |
| PATCH | `/slack/watches/:id` | `{ label?, channels?, priority?, enabled? }`; 404 `no_watch`. |
| DELETE | `/slack/watches/:id` | Removes a watch (204); 409 `builtin` for the three broadcasts, which can only be switched off. |
| GET | `/slack/metrics?since=7d\|30d` | How fast you answer: items and replies by priority, the share answered within an hour, `withinSla` (of the replies, how many inside their priority's SLA, by priority; a priority with the SLA off counts none) with the `sla` in effect, median and p90 seconds from the message to your reply, and a per-day series. |
| GET | `/slack/triage-runs?since=7d\|30d` | What triage cost: `{ since, runs, items, costUsd }`, one row per `slack_triage` pack run (`id`, `startedAt`, `endedAt`, `items`, `model`, `engine` (absent on runs from before engines), `runtime`, `modelId`, `sdkVersion` and `fingerprint` (absent on runs from before fingerprints), `turns`, `costUsd`, `ok`, `error`), newest first, with the items and dollars summed. |
| GET | `/slack/usergroups` | `[{ id, handle, name }]` from `usergroups.list`, cached ten minutes, for the watch popup's autocomplete. |
| GET | `/slack/channels` | `[{ id, name, kind }]`: the channels you are in, cached ten minutes. |
| GET | `/jira/status` | `{ configured, site, tokenExpiresAt, error }`: whether Jira is set up and the token works (`error` is Jira's words when not; `tokenExpiresAt` is `MACHINE_JIRA_TOKEN_EXPIRES` as set, or the date a 401 named once the token has gone, else null). Present only when `MACHINE_JIRA_SITE`, `MACHINE_JIRA_EMAIL` and `MACHINE_JIRA_TOKEN` are set, like every `/jira/*` and `/tasks/:id/jira*` route. |
| GET | `/jira/search?q=` | Issues to pick from: a key (`PLAT-123`) answers that issue; text searches `text ~ "q"`, your open issues first, at most 15. `[{ key, summary, status, issueType, url }]`. |
| POST | `/tasks/:id/jira` | `{ "key": "PLAT-123" }`: links the ticket to the issue (status, priority and due date read now; `J` on the board). Answers the task; 404 `no_issue` when Jira has no such issue, 409 `no_token` when Jira is unconfigured, 409 `already_linked_elsewhere` when another open task holds that issue (close or unlink it first), 409 `has_worktree` when the ticket already works on a branch named from another issue (the same key again only refreshes the link), 409 `notch_task` for a notch task (also from `/jira/create`). |
| DELETE | `/tasks/:id/jira` | Unlinks the ticket. Answers the task; 409 `has_worktree` once the ticket works on a branch, since that branch was named from the link. |
| POST | `/tasks/:id/jira/create` | `{ project?, issueType? }`: creates an issue from the ticket (title; description plus the criteria as a checklist) in `project` or the repo's `luna.yaml` `jira.project`, with `issueType` (default `Task`), and links it (201). 409 `already_linked` when the ticket carries one, 409 `no_project` when neither names a project. |
| GET | `/events` | SSE: `task.updated` (the whole task, with its `seq`), `task.event` (one activity entry), `task.deleted` (`id` and the tombstone's `seq`), `task.metrics`, `stage.started` (a stage container is running: task id, tab label, worktree, container name), `task.closed` (its watch tab can go), `task.shipped` (the task's PR merged: `{ id, title, prUrl, number, mergedSha, format, howToVerify, media: [{ kind, label, url }], at }`), `budget.alert` (a spend passed 80, 90 or 100% of a task's, a repo's month's or the day's ceiling, or an engine's monthly cap: `{ scope: "task" \| "repo" \| "day" \| "engine", taskId, repo, engine?, pct, spentUsd, limitUsd }`, where an `engine` alert names the cap's engine or credential, `repo` is set for a luna.yaml cap, and `taskId` is null when a `POST /runs` call crossed it), `github.prs` (the PR inbox changed; the whole snapshot), `slack.items` (the Slack inbox changed: items, watches, error or socket state; the whole snapshot), plus `ready` and a `ping` every 15s. `task.updated` also fires when a task's Jira link changes (an event starting `jira.`, or JiraWatch's refresh) and when one of its SLA clocks flips. `seq` comes from one Postgres sequence: every insert or update of a task row takes the next number (`Task.seq`), a delete leaves a tombstone with its own, and numbers are handed out in commit order. A message that only recomputes a clock repeats the task's `seq`. |
| GET | `/events?since=<seq>&source=<kind>` | The same stream, made to resume: it first replays, compacted and in `seq` order, the current `task.updated` of every task whose `seq` is past `since` and a `task.deleted` for every tombstone past it, then `ready`, then goes on live; its task snapshots are read from Postgres in `seq` order (a bus message only prompts a read), so none is lost or sent twice across the replay, and a clock-only refresh is not sent. `source` (a `source.kind`, e.g. `notch`) limits the replay and the live task snapshots to tasks of that source, and lets through the other per-task messages (`task.event`, `stage.started`, `task.closed`, `task.shipped`, `budget.alert`) only for a task of that source, whether or not the stream has sent its snapshot (a new task's first events, the live events of a task unchanged since `since`), in the order they came; a task's source never changes, so a task never leaves the stream but by being deleted; alone, it streams from now. Store the last `seq` handled and pass it as `since` on reconnect. A tombstone is kept 30 days (the nightly sweep), so a client away longer re-reads `GET /tasks` rather than replaying deletions. 400 for a `since` that is not a non-negative integer or an unknown `source`. |
| POST | `/dev/stubs` | Dev only, when stub stages are in use: queue results for a stage, e.g. three `fail`s for `verifying`. |

Errors use `{ "error", "message" }`: 400 for invalid input, 404 for an unknown task, 409 for an action that does not fit the task's state, 500 otherwise.

## Who may call

The machine's clients are the board, Luna Notch and scripts; none is a web page. Every request, on every route (`/events` and `/health` included), passes these checks in order (`machine/src/adapters/http/access.ts`):

- **Host**: while `MACHINE_HOST` is a loopback address, a `Host` header must be `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>`, else 403 `forbidden_host` (a DNS name rebound to 127.0.0.1). Beyond loopback the check is skipped and the token is required instead.
- **Origin**: only browsers send one; any but the machine's own (`http://127.0.0.1:<port>`, `http://localhost:<port>`) is 403 `forbidden_origin`.
- **Token**: when `MACHINE_API_TOKEN` is set (env, else `~/.config/hardness/machine-api-token`), `Authorization: Bearer <token>`, else 401 `unauthorized`. A machine bound beyond loopback with no token refuses to start. The board and the golden scripts read the same variable and file.
- **Body**: a request that sends a body must say `Content-Type: application/json` (a `; charset=…` is fine), else 415 `unsupported_media_type`. A page can only send that across sites after a CORS preflight, which the machine never allows, so a cross-site form or `no-cors` fetch cannot create, start, merge or close anything.

## Example session

```sh
curl -s -X POST 127.0.0.1:4317/tasks -H 'content-type: application/json' \
  -d '{"title":"Login page","criteria":["Bad password shows an error"]}'
curl -s -X POST 127.0.0.1:4317/tasks/<id>/start
curl -s -X POST 127.0.0.1:4317/tasks/<id>/decision -H 'content-type: application/json' \
  -d '{"decision":"approved"}'
curl -sN 127.0.0.1:4317/events      # live updates
curl -s '127.0.0.1:4317/metrics?since=7d'   # factory metrics (7d, 30d or ISO): cycle time, first-pass, escalations, cost; also streamed as task.metrics
curl -s '127.0.0.1:4317/metrics?groupBy=repo'   # the same, plus one row per repo
curl -s '127.0.0.1:4317/metrics?groupBy=engine' # the same, plus one row per engine
curl -s '127.0.0.1:4317/metrics?groupBy=fingerprint'   # the same, plus one row per harness fingerprint
```

Give a task a `"repoPath"` so the agents have a repo to work on.
