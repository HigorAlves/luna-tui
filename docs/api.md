# API

This is the machine's HTTP API. It comes straight from `machine/src/adapters/http/app.ts`. `contracts/src/api.ts` defines the shapes.

| Method | Path | Does |
|---|---|---|
| GET | `/health` | Liveness check, answering 503 `{ok: false, problems: [...]}` when the machine cannot do its job: no GitHub token, no git identity, or every stage a stub because the Claude credential or the runner image was missing at boot (not for `MACHINE_AGENTS=off`, which is a choice). The compose healthcheck, `docker compose up --wait` and `make doctor` read it. It also carries the stage pool: `slots {max, active, draining, latched}`, where `latched` lists each credential (`claude`, `codex`, `openai`, `typesafe`) whose usage window a stage hit and until when its queued work waits; work on another credential keeps claiming. |
| GET | `/packs` | Every pack in the registry (`contracts/src/packs.ts`), in `PackId` order: `{ id, agent, kind: "agent" \| "script" \| "decision", engines: { default, allowed, fallback? }, effort, writable, maxTurns, timeoutMs, states }`. `agent` is null and `kind` `script` for a pack that calls no model (`evidence`); `kind` `decision` is a pack of typed questions to a decision model (`triage_signals`, on `jev`, `claude:haiku` or `codex:luna`), with `agent` and `effort` null; `states` are the task states the pipeline runs it in (`reviewing_memory` runs inside `shipping`; `slack_triage`, `jira_intake`, `triage_signals`, `eval_judge`, `chat_triage` and the on-demand decisions (`risk_score`, `coverage_check`, `plan_check`, `red_check`, `scope_check`, `finding_classify`, `e2e_failure_cause`, `ci_failure_class`, `frame_privacy`, `evidence_format`) and Ship's five decisions (`event_class`, `comment_intent`, `fix_scope`, `evidence_valid`, `worth_learning`, each on a `ship` context: a review event, a comment with the pack, a fix, or a finished task's retro facts) in none; `pr_reply` runs in `shipping`; `video_script`, `recording`, `video_qa` and `video_fix` in `evidence`, run as sub-runs by the video pipeline: the Slack inbox and Jira intake run the first two, `POST /runs` any of them but `eval_judge`, which only the evals runner runs). |
| GET | `/engines` | Every engine in `contracts/src/engines.ts`, in that order: `{ id, runtime, modelId, auth, status, available, reason?, spentThisMonthUsd, budgetUsd }`. `modelId` is the pinned ID the runtime passes its SDK, `auth` how a run is paid (`subscription` for Claude, whose API key is the fallback; `chatgpt` for the Codex login; `api-key` for `openai:*` and `jev`), `status` the catalog model's (`preview`, `ga`, `deprecated`). `available` says whether this machine has the credential the engine needs (Claude: `CLAUDE_CODE_OAUTH_TOKEN`/`ANTHROPIC_API_KEY` or their files; `codex:*`: a readable `~/.codex/auth.json`; `openai:*`: `OPENAI_API_KEY` or `~/.config/hardness/openai-api-key`; `jev`: `AI_GATEWAY_API_KEY` or `~/.config/hardness/ai-gateway-api-key`, else `TYPESAFE_API_KEY` or `~/.config/hardness/typesafe-api-key`), read on every call; `reason` says what is missing. An engine on a runtime `MACHINE_DISABLE_RUNTIMES` turned off is `available: false` with `reason: "disabled by MACHINE_DISABLE_RUNTIMES"`, whatever its credential. One at a monthly cap is `available: false` with `reason: "over its monthly budget ($20.00 of $20.00 on openai)"`. `spentThisMonthUsd` is this calendar month's recorded cost (stage runs, `POST /runs` calls, Slack triage runs) against the machine cap that binds the engine (`MACHINE_ENGINE_BUDGETS`: the one reached, else the one with least left, its own or its credential's, the credential's counting all its engines), else the engine's own; `budgetUsd` is that cap, null when none. A repo's `budget.engines` is not shown here. Never a credential's value. |
| POST | `/runs` | Packs on demand: `{ pack, engine?, context }` runs one context-only pack (one that runs in no task state) on data the client sends, with no task and no worktree, and answers `200 { answer, usage: { model, engine, turns, durationMs, costUsd } }` with the pack's answer validated against its schema. The packs and their `context`, which holds the pack's own key and nothing else: `chat_triage` `{ chat: { source: "slack" \| "teams", me: {id, name}, rules?, items: [{ id, place, kind: "dm" \| "group" \| "meeting" \| "channel", author, isBot, text, context?: [{author, text}], matched?, replies?, flag?: "urgent" \| "important", floor?: "P0".."P3" }] } }` (1 to 25 items; the answer is `slack_triage`'s: one `{ id, priority, category, expectsReply, summary, why, draft, refs, deadline }` per item), `triage_signals` `{ issue: { title, description, labels?, source? } }`, `risk_score`, `coverage_check` and `plan_check` `{ plan: { record, brief, criteria, assumptions, slices, rollback?, cases?, gaps?, round?, review?, map? } }` (the plan stage runs these itself; each answers its questions), `red_check`, `scope_check`, `finding_classify` and `e2e_failure_cause` `{ check: { kind: "red" \| "scope" \| "finding" \| "e2e", ... } }` (Build's and Verify's own checks, which the machine runs itself: `finding_classify` reads `{ kind: "finding", finding, excerpt? }` and answers `severity` as `blocker`, `should_fix` or `nit`; `e2e_failure_cause` reads `{ kind: "e2e", e2e: { verdict, summary, criteria, attempt } }` and answers `cause` as `product_bug`, `test_bug` or `env_flake`), `jira_intake` `{ jira: <JiraIntakeContext> }` (a known difference from Jira intake: here `/work` is empty, with no checkout of the repo, so the pack judges the issue on its text alone where intake's run can also read the code) and `slack_triage` `{ slack: <SlackTriageContext> }`. `eval_judge` is never run here: it is for the evals runner only. `engine` must be one of the pack's `engines.allowed` (default: its `engines.default`; no luna.yaml applies). An `X-Luna-Client` header (1 to 64 of `[A-Za-z0-9_.-]`, e.g. `notch`) names the caller in the record. 400 `not_on_demand` for a pack that runs in a task or `eval_judge`, `engine_not_allowed`, `invalid_request` for a context that does not fit the pack; 409 `no_credential` when this machine lacks the engine's credential (nothing ran); 409 `runtime_disabled` when the engine's runtime is turned off by `MACHINE_DISABLE_RUNTIMES` (nothing ran); 409 `budget` when the engine is at its monthly cap (`MACHINE_ENGINE_BUDGETS`; nothing ran); 422 `run_failed` with the run's error when the pack ran but gave no valid answer (no structured output, off-schema, a timeout, no result); 429 `rate_limited` with `resetsAt` (ISO, or null; the soonest of the windows hit) once the engine and every fallback the pack names (`engines.fallback`, skipping those whose credential is missing or whose window the pipeline holds) have hit their usage limit: a limit on the engine asked for moves the call at once to the next fallback, in the same place, `usage.engine` naming the engine that answered and each run kept as its own `pack_runs` row; 429 `budget` while the trailing 24 hours' spend is at `MACHINE_DAILY_BUDGET_USD` (nothing ran; a call's cost counts toward that ceiling like a stage run's, and there is no monthly one here, that one being per repo); 429 `queue_full` when two calls are running and eight wait (nothing ran); 503 `agents_off` only with `MACHINE_AGENTS=off` (a missing credential is the asked engine's own 409, so a machine with only a Codex login still runs `codex:*`). At most two calls run at once, apart from the stage pool's slots; up to eight more wait their turn. A client that disconnects is dropped while it waits, and its container is stopped while it runs (recorded as failed; the dead connection gets 499 `client_closed`). **What is kept**: one `pack_runs` row per call that ran (`pack`, `engine`, `model`, `client`, `ok`, `error`, `turns`, `duration_ms`, `cost_usd`, `started_at`, `ended_at`, and the run's `runtime`, `model_id`, `sdk_version` and `fingerprint`). **What is not**: the context and the answer. The run folder holding them (`MACHINE_STATE_DIR/pack-runs/<pack>-<uuid>`, apart from the stage runs' `runs/`: stage.json, result.json, the transcript) is removed when the call ends, answered or failed, and any a crash left is removed at start-up; the container is removed when it exits. The nightly sweep deletes `pack_runs` rows older than `MACHINE_RETENTION_DAYS` (90). |
| POST | `/drain` | Take no new work: running stages finish, the queue waits. Answers with the pool. |
| POST | `/resume` | Carry on: the queue is picked up again at once. |
| PATCH | `/slots` | `{max}`: resize the pool at run time (at least 1). |
| GET | `/repos` | Each repository the machine knows (the repo map, the repos dir and live tasks), with its sandbox image and code graph: `{ repo, image: { inUse, base, builtAt, lastFailure }, graph: { on, commit, behind, graphify, builtAt, building, lastFailure } }`. `inUse` is the machine's runner image or the repository's own (`hardness-runner-<slug>:<hash>`); `base` is what `sandbox.image.base` names; `builtAt` and image `lastFailure` are known for builds made since the machine started; text (a base's name, a failure reason) is flattened and capped. `image.pendingBase` is a base the repository's `luna.yaml` names that nobody approved yet (flattened). An empty list when the machine keeps no graphs or images. |
| POST | `/repos/base/approve` | `{ repo, base }`: approves that exact base reference for that repository, so the machine pulls and builds from it. A 400 unless the repository is one the machine knows and `base` is exactly what its `luna.yaml` on your checkout names now. An approved base is trusted with the stage's credential, like code you run yourself. |
| GET | `/economy?repo=<absolute path>` | The token economy of one repository (RFC 0007): `envelopes` (per pack: `samples` and the `envelope`, null before `economy.guard.envelope_min_samples` passing runs), `guard` (the last 50 things the loop guard did), `cost` (`exec` and `overhead` in effective tokens, `overheadShare`, and `overheadUnpriced`: the overhead runs that reported no tokens, so `overhead` is a floor while it is above 0), `facts` (each learned fact: `id`, `family`, `source`, `state`, `text`, counts) and `tools` (per pack: the approved `mask` and the `proposal` of unused units with their `unusedRuns` and `cards`). A 400 unless `repo` is an absolute path of a repository the machine knows. The route is absent with `MACHINE_ECONOMY=off`, as are the four below. |
| POST | `/economy/facts/:id/drop` | `{ repo }`: a learned fact is wrong. It is never told again and its key is never learned again. Answers `{ dropped }`: false for an id the repository does not hold. |
| POST | `/economy/mask/approve` | `{ repo, pack }`: the tools proposed for that pack become its mask, and its next run starts without them. `pack` is a pack id. Answers `{ approved }`: false when the pack has no proposal. |
| POST | `/economy/mask/restore` | `{ repo, pack, unit }`: brings a unit (`web`, `agent`, `luna:<tool>`) back into the pack. It is not proposed again. Answers `{ restored }`: false for a unit the pack does not have. |
| POST | `/economy/import` | `{ repo }`: folds the runs already on disk, once. It teaches the envelopes from passing runs and the tool evidence from Claude runs. Old runs carry no observation and no reliable token count, so it learns no fact and writes no cost record. A run is never folded twice, so a second call answers `{ runs: 0 }`. Answers `{ runs }`: the runs folded. A run with no events file is skipped. |
| GET | `/metrics` | Factory metrics over a window: `?since=7d\|30d\|<ISO timestamp>` (default `7d`). Cycle time, first-pass rate, escalations, cost, queue depth, and `gates` (`answered`: gates you answered in the window, `withinSla`: the share answered inside the gate SLA, `waitMs`: median and p90 wait per gate state); also streamed as `task.metrics`. `&repo=<path>` limits the numbers to one checkout (`repo=` to the tasks with none); `&groupBy=repo` adds `byRepo`, one slim row per checkout (tasks, escalation rate, first-pass verifying, cost). `&groupBy=engine` adds `byEngine`, one row per engine the window's stage runs started on (`stage_runs.engine`; named engines in order, then `engine: null` for host-only stages and runs from before engines): `{ engine, stageRuns, firstPassRate, escalations, rateLimited, meanTurns, meanDurationMs, costUsd }`. `firstPassRate` is the share of first attempts that passed, of those that passed or failed; `escalations` counts the tasks that escalated in the window, each against the engine of its latest run before it; `rateLimited` the runs that ended on a usage limit (a fallback's run is its own row on its own engine); `meanTurns` and `meanDurationMs` are over the runs that passed or failed; `costUsd` sums the runs' recorded cost (`codex:*` runs record none). It composes with `repo`. `&groupBy=fingerprint` adds `byFingerprint`, one row per harness fingerprint over the window's stage runs (`fingerprint`, null for runs from before fingerprints and listed last, then the most runs first; `runs`, `passRate` of passed over passed and failed, `costUsd`, `durationMs` median and p90, the `stages` and `engines` it ran). Any other `groupBy` is a 400. `economy` (RFC 0007): the token economy of `repo`, or added up over the repositories the machine knows when none is given: `{ effective: { exec, overhead }, overheadShare, overheadUnpriced, guard: { redirects, stops }, facts: { active, promoted }, masked }`. The guard counts are over its last 50 events per repository, and `masked` counts masked units. It is read from the economy's own files, and absent with `MACHINE_ECONOMY=off` and for `repo=`. `flow` (v2.2): `planCycleMs` (triage passed to plan approved), `coverageRounds` (mean per planned task), `buildRuns` (implementer runs per task), `leadTimeMs` (created to merged), `mergesPerWeek`, each with `n`, the count it rests on, and read from the event log through `namesOf`; `changeFailureRate` and `timeToRestoreMs` are null with a `reason`, because nothing records a failed change yet. |
| GET | `/tasks` | List every task with its state, column and `route` (`feature`, `setup`, or a PR task's `ci_fix`, `review` or `address`). Each task carries `jira` (the linked issue as last seen: `key`, `url`, `issueType`, `status`, `priority`, `dueAt`, `syncedAt`, `blocked` with `{wanted, current, why, at}` when the last declared transition was refused, `linkedAt` when the link was made by hand (null for one made with the ticket), `timeZone` the Jira site's zone once JiraWatch has read it; null when unlinked) and `sla` (the ticket's clocks, computed at answer time from the row's `state_since` and the running stage run: `gate {dueAt, overdue, targetSecs, since, state}` while waiting on you, `stage {dueAt, overdue, targetSecs, stage, warn}` for a running stage the repo gave a target, `cycle {dueAt, overdue, targetSecs}` and `jiraDue` for the issue's due date, which ends at 23:59:59 in the site's timezone (UTC until known) and whose `targetSecs` counts from the task's creation or its link time, whichever is later; each null when it does not apply, the whole thing null when none does). A minute tick republishes a task on `task.updated` when any clock goes overdue or a stage clock starts warning. Each task also carries `lastRun` (the latest stage run that ended: `{ stage, engine, outcome, summary, at }`, `summary` being the pack's summary, else its error, else triage's brief, cut to 2000 characters; null before any run ended) and `gate` (while an approval is open: `{ state, requested }`, `requested` being what the gate asks, e.g. the plan or the questions; at `awaiting_ship` it carries `evidence` with the pack's `format`, `summary`, `media[]`, `commitSha`, `note?` and `video?`, which a send-back with a reason answers; null otherwise), on `GET /tasks`, `GET /tasks/:id`, `task.updated` and the replay alike, so a client catching up needs no `GET` per task. A task whose triage stage got a reading carries `classification`, what `triage_signals` said about it, read again each time triage runs: `{ kind, typeOfWork, sizeBucket, subScores, priority, riskPrelim, ready, size, confidence, at, model, recordId? }` (`kind` one of `bug`, `feature`, `task`, `chore`, `question`, `incident`; `sizeBucket` `XS` to `XL`; `subScores` the five urgency sub-scores, 1 to 3; `priority` `P0` to `P3`; `confidence` the lowest of the answers'; `recordId` the decision record the reading left; a card read before wave 9 has `area` and one `urgency` score instead of `typeOfWork` to `riskPrelim`); null before triage ran or when no model could read it. Each task also carries `record` (triage's `TriageRecord`) and `evidence` (the `EvidencePack`: `format` `video`, `captures` or `text`, `summary`, `scenarios`, `findings`, `outOfMap`, `risk`, `rollback`, `howToVerify`, `commitSha`, `media[]` of `{ kind, label, url, localPath?, scanned? }` (`scanned: false` is an image whose text could not be read: it is uploaded only after a person approved the preview), `results` by layer, `findingsDetail`, `diffSummary { what, why, files, added, removed }`, `revision`, `source`, a scenario `result` that can be `not_run`, a `note` when a format was degraded or a part was missing and, for a video, `video: { file, durationS, verdict: ship | one_more_pass | degraded, scores, defects[], rounds, transcript?, confidence? }`), both null until a stage writes them, and `archiveReason` (`duplicate`, `sla_expired`, `rejected`, `not_for_agent`, `pr_closed`, `no_setup`, `no_answer`; null unless the task is `archived`). |
| POST | `/tasks` | Create a task: title, description, criteria, repo path, source (`source.kind: notch` for a Luna Notch work order: `{ ref, id, jiraKey? }`), `start: true` to start it in the same call, and `stages` (`{ "<pack>": "<engine>" }`, e.g. `{ "triage": "claude:opus" }`): the task's own engine per pack, over the repo's `luna.yaml` `engines` and the pack's default; 400 for an engine the pack does not allow (`GET /packs`) or a pack that never runs in a task (`slack_triage`, `jira_intake`, `triage_signals`, `chat_triage`, `eval_judge`). With an `Idempotency-Key` header (1 to 200 characters, kept on the task), a retry with the same key and body answers the task already made (200, no second task, started once) and the same key with another body is 409 `idempotency_conflict`, whose `taskId` names the task the key made. "The same body" is the same order with every default filled in (`description: ""`, `criteria: []`, `repoPath: null`, `source: null`, `stages: {}`, a source's absent `jiraKey` as null) and `start` left out, so an equivalent retry is never a conflict; a key used before this rule keeps matching a retry of the body it was first sent with; without one, every call makes a task (201). |
| GET | `/tasks/:id` | One task with its stage runs, approvals, recent events and artifacts. Jira events: `jira.linked {key, url, created?}`, `jira.unlinked {key}`, `jira.transitioned {from, to, fields?}`, `jira.blocked {wanted, current, why}`, `jira.commented {url}` (the "PR opened" comment went out for that url; it is what stops a repeat after a restart) or `jira.commented {kind: "shipped", number}` (the shipped summary went out once), `task.shipped {title, prUrl, number, mergedSha, by, format, howToVerify, media}` (the task's PR merged; `by` is `machine` or `person`, `media` has web urls only), `jira.moved {status, key}` (the issue reached Done, Cancelled or Won't Do in Jira while the task is open), `jira.intake {key, verdict, reason}` (made by intake). A verifying run carries `cases: [{ title, ok }]` (one verdict per approved case, from the pack's `results[]`; null when it reported none). Every stage run carries `engine`, the one it started on (null for a host-only stage or a run from before engines), and what its result named it ran on: `runtime` (`claude`, `eve`, `jev`), `modelId` (the pinned model ID), `sdkVersion` (the runtime's SDK version as installed in the image) and `fingerprint` (a sha256 over the template, role, skills, access, answer schema and factory rules it ran; see [architecture](architecture.md#factory-mode)), each null for a host-only stage, a run still going or one from before fingerprints; `stage.engine {pack, engine, reason}` says why an engine asked for was passed over (not allowed for the pack, or no credential on this machine, in which case the pack's default ran), and `task.stages {stages}` records each change of the task's engines. Every task carries `stages`, its own engine per pack (`{}` when it names none). `reports {build, verify}` are the v2.2 Build Report (on the passing `implementing` finish as `detail.report`) and Verify Report (on the passing `ci_watch` finish), each null until its stage has passed; a stream event carries `names` (the v2.2 diagram's name or names for the fact, absent when it has none). |
| GET | `/tasks`, `/tasks/:id` (card fields) | Every task also carries `sources` (the first is `source`), `reporter`, `hints`, `originMachine`, `attachments` (name, url, mediaType, size: references), `project`, `owners`, `followers`, `links`, `demand`, `merged`, `mergedInto`, `related`, and once started `history`, `resolved` and `dedup` (the shortlist, answers and outcome of the duplicate check). A row from before reads as one source and empty lists. `POST /tasks` accepts the same fields. |
| PATCH | `/tasks/:id` | Edit the ticket's text (title, description, criteria, repo path). `source` never changes once the task exists: another one is 400 `source_immutable` (the same one again is no change). The repo path moves only while the task has no worktree or branch, else 409 `has_worktree` (the same path again is no change); a refused edit changes nothing. |
| GET | `/tasks/:id` (ship) | `ship`: the watched PR as the board shows it, built from the ship cursor, or null for a card with none: `{ pr { slug, number, url }, head, ready, checklist [{ id, ok, detail }], autoMerge { allowed, reason }, review { required, by }, fixRounds, queued, quietSince, lastEvent { class, at }, at }`. Details are flattened and capped; it holds no reviewer text and no thread. `EvidencePack.fixes` (at most 20: `{ sha, scope, summary, at }`) lists the fixes after review. The release question is an `awaiting_ship` approval whose `requested` holds `gate: "ship_approval"`, `head`, `prUrl`, `number`, `risk`, `checklist`, `question: "safe to release now?"`, `releaseOwners` and `evidence`; it has two answers, `approved` (the approver must not be one of the plan's approvers: `409 not_release_owner`; an approving GitHub review at that head from a person other than the machine's login answers it too, with that login as the approver, and logs `release.approved_on_github`) and `rejected` (archives the card; `ship.override { kind: "rejected_ready" }`). |
| POST | `/tasks/:id/findings/:findingId/dismiss` | A person dismisses a finding the last Verify reported, while the card waits at `awaiting_ship`: `{ "reason"? }` (500 characters, kept as ground truth, out of the stream). `409` at any other state, `404` for an id the last Verify did not report. Logs `finding.dismissed { id }`. |
| POST | `/tasks/:id/findings` | A person adds a finding Verify missed: `{ title, severity: blocker \| should_fix \| nit, path?, line? }`. Logs `finding.added { severity }`. |
| - | events of Ship | `ship.merged` (the merge, with the merge commit GitHub reports; `task.shipped` rows and the stream message of that name still read), `ship.event { kind, class }` (the class is an enum value: `review_comment`, `ci_flaky`, `ci_real`, `conflict`, `base_moved`, `freeze`, `blocked_by_other_pr`, `noise`), `ship.override`, `finding.dismissed`, `finding.added`, `evidence.edited { sha, bytes }`, `sla.reminder { gate: "awaiting_ship", quietDays }` and `sla.escalated { gate: "awaiting_ship", afterDays, to }`. A container cannot write any of them: its lines are stored under `stage.`. |
| PATCH | `/tasks/:id/plan` | Edit triage's plan while it awaits your approval, or later while the task is `awaiting_test_check` (nothing is built yet; the approved plan is edited and the ticket's criteria follow): `{ "brief"?, "criteria"?, "assumptions"?, "steps"?, "rollback"?, "risk"?, "map"? }`, at least one field. Only the fields given change. `steps` is `[{ description, files[], done_when[], est_loc }]` (the slices Build reads follow them); `risk` is `{ level: low \| medium \| high, reason }`: the machine's own level is a floor, a higher one applies at once and a lower one is kept with its reason (`requested.overrides.risk.applied: false`) while the approvers rule and Ship keep reading the higher; `map` is `{ components?, files: [{ path, role }], entry_points?, owners?, reason }`, kept with its reason as ground truth. Every text is bounded (400 on more). Any edit raises the Plan's `version` and clears the approvers so far. Once the plan is approved (the legacy `awaiting_test_check` edit), `steps`, `risk`, `map` and `rollback` are refused with `409 plan_approved`. Each edit appends `{ at, before, after }` (changed fields only) to the approval's `requested.revisions` and logs a `plan.edited` event with the field names. 409 `no_plan` at any other state. |
| PATCH | `/tasks/:id/record` | Correct the Triage Record while the task waits at a gate: `{ "kind"?, "typeOfWork"?, "size"?, "riskPrelim"?, "priority"? }`, enum values only (`kind` `bug`, `feature`, `task`, `chore`, `question`, `incident`; `typeOfWork` `frontend`, `backend`, `infra`, `data`, `docs`, `mixed`; `size` `XS` to `XL`; `riskPrelim` `low`, `medium`, `high`; `priority` `P0` to `P3`), at least one, no other key (400). The record's `version` rises, its `decisionBy` is `person` and `editedFields` names what changed; each corrected field except the priority is written as ground truth (`source: record_edit`) onto the `triage_signals` decision record that read it. A lower `riskPrelim` than the machine's is kept and shown, but the risk the plan's floor and the approver and ship rules read stays at the higher of the two (`record.riskMachine`); a higher one applies at once. 409 `record_locked` when the task has no record or is not at `awaiting_answers` or `awaiting_approval`. Answers the task. |
| POST | `/tasks/:id/questions/post` | A person's tap (`p` on the board): post the open questions at `awaiting_answers` where the card came from, as one flattened comment. The machine posts the questions it built from the signals by itself; an agent's own questions wait for this tap. Idempotent (the same questions are posted once; `posted` says whether this call did). 409 `no_questions` away from that gate, 409 `secret` when a question carries a token-shaped string. |
| PATCH | `/tasks/:id/cases` | Replace test_design's cases while the task is `awaiting_test_check`: `{ "cases": [{ "title", "criterion", "approach" }] }`, at least one. The open test-check approval keeps its other fields; logs a `cases.edited` event. 409 `no_cases` at any other state. |

## Who may call

The machine's clients are the board, Luna Notch and scripts. None is a web page. Every request passes these checks in order. This applies to every route, including `/events` and `/health`. The checks are in `machine/src/adapters/http/access.ts`:

- **Host**: while `MACHINE_HOST` is a loopback address, a `Host` header must be `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>`. Any other host gets 403 `forbidden_host`. This stops a DNS name that rebinds to 127.0.0.1. Beyond loopback, the machine skips the check and requires the token instead.
- **Origin**: only browsers send one. Any origin but the machine's own gets 403 `forbidden_origin`. The machine's own origins are `http://127.0.0.1:<port>` and `http://localhost:<port>`.
- **Token**: when you set `MACHINE_API_TOKEN` (env, else `~/.config/hardness/machine-api-token`), each request needs `Authorization: Bearer <token>`. Without it, the response is 401 `unauthorized`. A machine that binds beyond loopback with no token refuses to start. The board and the golden scripts read the same variable and file.
- **Body**: a request that sends a body must say `Content-Type: application/json`. A `; charset=…` is fine. Any other type gets 415 `unsupported_media_type`. A page can send that type across sites only after a CORS preflight. The machine never allows a CORS preflight. So a cross-site form or `no-cors` fetch cannot create, start, merge or close anything.

## What a run was refused

A stage logs `sandbox.egress_blocked` on the card. It logs one row for each refused (host, port, via), at most 20 for each stage. After that it logs one `{ step, more }` row. The payload is `{ step, host, port, via, reason, count }`. The `step` is `stage`, `check`, `install`, `app`, `seed` or `deploy`. The `via` is `connect`, `http` or `dns`. The `reason` is `not_listed`, `address`, `private_address`, `sni_mismatch`, `unresolved` or `head_too_large`. The host is text that a container chose. The machine flattens and caps it, and replaces the value of a secret in it. A container cannot write this kind, because the machine reserves it. The board shows it as `blocked: host:port (step, via)`.

## Example session

```sh
curl -s -X POST 127.0.0.1:4317/tasks -H 'content-type: application/json' \
  -d '{"title":"Login page","criteria":["Bad password shows an error"]}'
curl -s -X POST 127.0.0.1:4317/tasks/<id>/start
curl -s -X POST 127.0.0.1:4317/tasks/<id>/decision -H 'content-type: application/json' \
  -d '{"decision":"approved"}'
curl -sN 127.0.0.1:4317/events      # live updates
curl -s '127.0.0.1:4317/economy?repo=/Users/me/shop'   # one repository's envelopes, guard events, cost, facts and tool proposals
curl -s -X POST 127.0.0.1:4317/economy/import -H 'content-type: application/json' -d '{"repo":"/Users/me/shop"}'   # fold its past runs once
curl -s '127.0.0.1:4317/metrics?since=7d'   # factory metrics (7d, 30d or ISO): cycle time, first-pass, escalations, cost; also streamed as task.metrics
curl -s '127.0.0.1:4317/metrics?groupBy=repo'   # the same, plus one row per repo
curl -s '127.0.0.1:4317/metrics?groupBy=engine' # the same, plus one row per engine
curl -s '127.0.0.1:4317/metrics?groupBy=fingerprint'   # the same, plus one row per harness fingerprint
```

Give a task a `"repoPath"` so the agents have a repo to work on.

## Change size and stacked cards (wave 15)

- **A task's stack.** `GET /tasks` and `GET /tasks/:id` carry the card's own fields as they are: `splitFrom`, `splitPart` (`{ n, of }`), `splitInto`, `dependsOn`, `base` (`{ card, branch }`), `riskFloor` and `startWhenReady`. They hold ids, numbers and enum values only. A card with none of them shows none. A client's `POST /tasks` cannot set them.
- **Events** the pipeline alone logs (no container can): `card.split`, `card.child`, `card.held` (`reason`, `waitingOn`, `text`), `card.released`, `size.overridden` and `stack.retargeted`. The ship watch logs `ship.event { kind: "stack", class: "parent_changed" | "parent_merged" }`.
- **The backlog.** Each entry of `GET /backlog` has `schedulable` and `blockedBy` (`{ id, kind: "card" | "item", state }`). `POST /backlog/:id/promote` of an entry that is not schedulable answers `409 not_schedulable` with `blockedBy`. The machine removes nothing. The machine makes a promoted card with `dependsOn` for its card dependencies. The other items that named it now name the new card.
- **A ticket's split.** A ticket whose recommendation is `split` gets a draft of kind `split`. The draft has `children`, numbered `text` and `created` once you approve it. The ticket gets the status `split_proposed`. With no valid split, the ticket has no draft. Its assessment says `split.failed`, and its status is `needs_decision`. `POST /tickets/:key/approve` on the draft creates the child tickets in the origin's own project or repository. A failure partway leaves the draft waiting with `created`. Approving again goes on. The same call marks the origin `epic` and posts one comment that lists the keys. Editing the draft gives `409 ticket_refused`. The assessment carries `sizeEstimate` (`estLoc`, `estFiles`, `reviewable`, `confidence`).
