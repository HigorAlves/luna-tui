# API

This is the machine's HTTP API. It comes straight from `machine/src/adapters/http/app.ts`. `contracts/src/api.ts` defines the shapes.

| Method | Path | Does |
|---|---|---|
| GET | `/health` | Liveness check. It also shows the stage pool: `slots {max, active, draining, latched}`. `latched` lists each credential (`claude`, `codex`, `openai`, `typesafe`) whose usage window a stage hit. It also says until when the queued work of that credential waits. Work on another credential keeps claiming. |
| GET | `/packs` | Every pack in the registry (`contracts/src/packs.ts`), in `PackId` order: `{ id, agent, kind: "agent" \| "script" \| "decision", engines: { default, allowed, fallback? }, effort, writable, maxTurns, timeoutMs, states }`. For a pack that calls no model (`evidence`), `agent` is null and `kind` is `script`. A pack of `kind` `decision` asks typed questions of a decision model (`triage_signals`, on `jev`, `claude:haiku` or `codex:luna`). Its `agent` and `effort` are null. `states` are the task states that the pipeline runs the pack in. `reviewing_memory` runs inside `shipping`. These packs run in no state: `slack_triage`, `jira_intake`, `triage_signals`, `eval_judge` and `chat_triage`. The on-demand decisions also run in none: `risk_score`, `coverage_check`, `plan_check`, `red_check`, `scope_check`, `finding_classify`, `e2e_failure_cause`, `ci_failure_class`, `frame_privacy`, `evidence_format`. Ship's five decisions also run in none: `event_class`, `comment_intent`, `fix_scope`, `evidence_valid`, `worth_learning`. Each of the five runs on a `ship` context: a review event, a comment with the pack, a fix, or a finished task's retro facts. `pr_reply` runs in `shipping`. `video_script`, `recording`, `video_qa` and `video_fix` run in `evidence`, as sub-runs of the video pipeline. The Slack inbox and Jira intake run the first two packs that run in no state. `POST /runs` runs any of those packs but `eval_judge`. Only the evals runner runs that one. |
| GET | `/engines` | Every engine in `contracts/src/engines.ts`, in that order: `{ id, runtime, modelId, auth, status, available, reason?, spentThisMonthUsd, budgetUsd }`. `modelId` is the pinned ID that the runtime passes its SDK. `auth` says what pays for a run. It is `subscription` for Claude, whose API key is the fallback. It is `chatgpt` for the Codex login, and `api-key` for `openai:*` and `jev`. `status` is the catalog model's status (`preview`, `ga`, `deprecated`). `available` says whether this machine has the credential that the engine needs. Claude needs `CLAUDE_CODE_OAUTH_TOKEN`/`ANTHROPIC_API_KEY` or their files. `codex:*` needs a readable `~/.codex/auth.json`. `openai:*` needs `OPENAI_API_KEY` or `~/.config/hardness/openai-api-key`. `jev` needs `AI_GATEWAY_API_KEY` or `~/.config/hardness/ai-gateway-api-key`, else `TYPESAFE_API_KEY` or `~/.config/hardness/typesafe-api-key`. The machine reads the credentials on every call. `reason` says what is missing. An engine on a runtime that `MACHINE_DISABLE_RUNTIMES` turned off is `available: false` with `reason: "disabled by MACHINE_DISABLE_RUNTIMES"`, whatever its credential. An engine at a monthly cap is `available: false` with `reason: "over its monthly budget ($20.00 of $20.00 on openai)"`. `spentThisMonthUsd` is this calendar month's recorded cost: stage runs, `POST /runs` calls and Slack triage runs. It counts against the machine cap that binds the engine (`MACHINE_ENGINE_BUDGETS`). That cap is the one reached, else the one with least left. It can be the engine's own cap or its credential's cap. A credential's cap counts all its engines. With no machine cap, the field counts the engine's own cost. `budgetUsd` is that cap, null when none. This route does not show a repo's `budget.engines`. It never shows a credential's value. |
| POST | `/runs` | Packs on demand. `{ pack, engine?, context }` runs one context-only pack on data that the client sends. A context-only pack runs in no task state. The call has no task and no worktree. It answers `200 { answer, usage: { model, engine, turns, durationMs, costUsd } }`. The machine validates the pack's answer against its schema. The `context` holds the pack's own key and nothing else. The packs and their `context` follow. `chat_triage` takes `{ chat: { source: "slack" \| "teams", me: {id, name}, rules?, items: [{ id, place, kind: "dm" \| "group" \| "meeting" \| "channel", author, isBot, text, context?: [{author, text}], matched?, replies?, flag?: "urgent" \| "important", floor?: "P0".."P3" }] } }` with 1 to 25 items. Its answer is `slack_triage`'s answer: one `{ id, priority, category, expectsReply, summary, why, draft, refs, deadline }` per item. `triage_signals` takes `{ issue: { title, description, labels?, source? } }`. `risk_score`, `coverage_check` and `plan_check` take `{ plan: { record, brief, criteria, assumptions, slices, rollback?, cases?, gaps?, round?, review?, map? } }`. The plan stage runs these itself, and each answers its questions. `red_check`, `scope_check`, `finding_classify` and `e2e_failure_cause` take `{ check: { kind: "red" \| "scope" \| "finding" \| "e2e", ... } }`. These are Build's and Verify's own checks, and the machine runs them itself. `finding_classify` reads `{ kind: "finding", finding, excerpt? }`. It answers `severity` as `blocker`, `should_fix` or `nit`. `e2e_failure_cause` reads `{ kind: "e2e", e2e: { verdict, summary, criteria, attempt } }`. It answers `cause` as `product_bug`, `test_bug` or `env_flake`. `jira_intake` takes `{ jira: <JiraIntakeContext> }`. It has one known difference from Jira intake. Here `/work` is empty, with no checkout of the repo. So the pack judges the issue on its text alone, but intake's run can also read the code. `slack_triage` takes `{ slack: <SlackTriageContext> }`. This route never runs `eval_judge`: only the evals runner runs it. `engine` must be one of the pack's `engines.allowed`. The default is its `engines.default`, and no luna.yaml applies. An `X-Luna-Client` header names the caller in the record. Its value is 1 to 64 of `[A-Za-z0-9_.-]`, e.g. `notch`. 400 `not_on_demand` for a pack that runs in a task or for `eval_judge`. 400 `engine_not_allowed`. 400 `invalid_request` for a context that does not fit the pack. 409 `no_credential` when this machine lacks the engine's credential (nothing ran). 409 `runtime_disabled` when `MACHINE_DISABLE_RUNTIMES` turned off the engine's runtime (nothing ran). 409 `budget` when the engine is at its monthly cap (`MACHINE_ENGINE_BUDGETS`; nothing ran). 422 `run_failed` with the run's error when the pack ran but gave no valid answer. That covers no structured output, an off-schema answer, a timeout and no result. 429 `rate_limited` with `resetsAt` once the engine and every fallback that the pack names have hit their usage limit. `resetsAt` is ISO, or null, and gives the soonest of the windows hit. The fallbacks are `engines.fallback`, without those whose credential is missing or whose window the pipeline holds. A limit on the asked engine moves the call at once to the next fallback, in the same place. `usage.engine` names the engine that answered. The machine keeps each run as its own `pack_runs` row. 429 `budget` while the trailing 24 hours' spend is at `MACHINE_DAILY_BUDGET_USD` (nothing ran). A call's cost counts toward that ceiling like a stage run's cost. This route has no monthly ceiling, because that one is per repo. 429 `queue_full` when two calls are running and eight wait (nothing ran). 503 `agents_off` only with `MACHINE_AGENTS=off`. A missing credential gives the asked engine's own 409. So a machine with only a Codex login still runs `codex:*`. At most two calls run at once, apart from the stage pool's slots. Up to eight more wait their turn. The machine drops a client that disconnects while it waits. If the client disconnects while its call runs, the machine stops the container. The machine records that run as failed, and the dead connection gets 499 `client_closed`. **What is kept**: one `pack_runs` row per call that ran. The row holds `pack`, `engine`, `model`, `client`, `ok`, `error`, `turns`, `duration_ms`, `cost_usd`, `started_at` and `ended_at`. It also holds the run's `runtime`, `model_id`, `sdk_version` and `fingerprint`. **What is not**: the context and the answer. The run folder holds them: `MACHINE_STATE_DIR/pack-runs/<pack>-<uuid>`, apart from the stage runs' `runs/`. The folder holds stage.json, result.json and the transcript. The machine removes the folder when the call ends, answered or failed. At start-up, the machine removes any run folder that a crash left. The machine removes the container when it exits. The nightly sweep deletes `pack_runs` rows older than `MACHINE_RETENTION_DAYS` (90). |
| POST | `/drain` | Take no new work: running stages finish, the queue waits. Answers with the pool. |
| POST | `/resume` | Carry on: the machine picks up the queue again at once. |
| PATCH | `/slots` | `{max}`: resize the pool at run time (at least 1). |
| GET | `/repos` | Each repository the machine knows (the repo map, the repos dir and live tasks), with its sandbox image and code graph: `{ repo, image: { inUse, base, builtAt, lastFailure }, graph: { on, commit, behind, graphify, builtAt, building, lastFailure } }`. `inUse` is the machine's runner image or the repository's own (`hardness-runner-<slug>:<hash>`). `base` is what `sandbox.image.base` names. The machine knows `builtAt` and the image's `lastFailure` for the builds it made since it started. The machine flattens and caps text, such as a base's name or a failure reason. `image.pendingBase` is a base that the repository's `luna.yaml` names and that nobody approved yet (flattened). The list is empty when the machine keeps no graphs or images. |
| POST | `/repos/base/approve` | `{ repo, base }`: approves that exact base reference for that repository, so the machine pulls and builds from it. A 400 unless the repository is one the machine knows and `base` is exactly what its `luna.yaml` on your checkout names now. The machine trusts an approved base with the stage's credential, like code you run yourself. |
| GET | `/metrics` | Factory metrics over a window: `?since=7d\|30d\|<ISO timestamp>` (default `7d`). The metrics are cycle time, first-pass rate, escalations, cost, queue depth and `gates`. `gates` holds `answered`, `withinSla` and `waitMs`. `answered` counts the gates you answered in the window. `withinSla` is the share answered inside the gate SLA. `waitMs` is the median and p90 wait per gate state. The machine also streams the metrics as `task.metrics`. `&repo=<path>` limits the numbers to one checkout, and `repo=` limits them to the tasks with none. `&groupBy=repo` adds `byRepo`, one slim row per checkout (tasks, escalation rate, first-pass verifying, cost). `&groupBy=engine` adds `byEngine`, one row per engine that the window's stage runs started on (`stage_runs.engine`). Named engines come first, in order. Then comes `engine: null` for host-only stages and runs from before engines. Each row is `{ engine, stageRuns, firstPassRate, escalations, rateLimited, meanTurns, meanDurationMs, costUsd }`. `firstPassRate` is the share of first attempts that passed, of those that passed or failed. `escalations` counts the tasks that escalated in the window, each against the engine of its latest run before it. `rateLimited` counts the runs that ended on a usage limit. A fallback's run is its own row on its own engine. `meanTurns` and `meanDurationMs` are over the runs that passed or failed. `costUsd` sums the runs' recorded cost, and `codex:*` runs record none. It composes with `repo`. `&groupBy=fingerprint` adds `byFingerprint`, one row per harness fingerprint over the window's stage runs. Each row has `fingerprint`, `runs`, `passRate`, `costUsd`, `durationMs`, and the `stages` and `engines` it ran. `fingerprint` is null for runs from before fingerprints, and those rows come last. The other rows come with the most runs first. `passRate` is passed over passed and failed. `durationMs` gives the median and p90. Any other `groupBy` is a 400. `flow` (v2.2) holds `planCycleMs`, `coverageRounds`, `buildRuns`, `leadTimeMs` and `mergesPerWeek`. `planCycleMs` runs from triage passed to plan approved. `coverageRounds` is the mean per planned task. `buildRuns` counts the implementer runs per task. `leadTimeMs` runs from created to merged. Each carries `n`, the count it rests on. The machine reads each from the event log through `namesOf`. `changeFailureRate` and `timeToRestoreMs` are null with a `reason`, because nothing records a failed change yet. |
| GET | `/tasks` | List every task with its state, column and `route` (`feature`, `setup`, or a PR task's `ci_fix`, `review` or `address`). Each task carries `jira`: the linked issue as last seen, or null when unlinked. It holds `key`, `url`, `issueType`, `status`, `priority`, `dueAt` and `syncedAt`. It holds `blocked` with `{wanted, current, why, at}` when Jira refused the last declared transition. It holds `linkedAt` when a person made the link by hand (null for a link made with the ticket). It holds `timeZone`, the Jira site's zone, once JiraWatch has read it. Each task also carries `sla`, the ticket's clocks. The machine computes them at answer time from the row's `state_since` and the running stage run. `gate {dueAt, overdue, targetSecs, since, state}` applies while the task waits on you. `stage {dueAt, overdue, targetSecs, stage, warn}` applies to a running stage that the repo gave a target. Then come `cycle {dueAt, overdue, targetSecs}` and `jiraDue`, for the issue's due date. That date ends at 23:59:59 in the site's timezone (UTC until known). Its `targetSecs` counts from the task's creation or its link time, whichever is later. Each clock is null when it does not apply, and the whole field is null when none applies. A minute tick republishes a task on `task.updated` when any clock goes overdue or a stage clock starts warning. Each task also carries `lastRun`, the latest stage run that ended: `{ stage, engine, outcome, summary, at }`. Its `summary` is the pack's summary, else its error, else triage's brief, cut to 2000 characters. It is null before any run ended. Each task also carries `gate` while an approval is open: `{ state, requested }`. `requested` is what the gate asks, e.g. the plan or the questions. At `awaiting_ship` it carries `evidence` with the pack's `format`, `summary`, `media[]`, `commitSha`, `note?` and `video?`. A send-back with a reason answers it. The gate field is null otherwise. These fields are the same on `GET /tasks`, `GET /tasks/:id`, `task.updated` and the replay. So a client that catches up needs no `GET` per task. A task whose triage stage got a reading carries `classification`: what `triage_signals` said about it. The machine reads it again each time triage runs. It is `{ kind, typeOfWork, sizeBucket, subScores, priority, riskPrelim, ready, size, confidence, at, model, recordId? }`. `kind` is one of `bug`, `feature`, `task`, `chore`, `question`, `incident`. `sizeBucket` is `XS` to `XL`. `subScores` are the five urgency sub-scores, 1 to 3. `priority` is `P0` to `P3`. `confidence` is the lowest confidence of the answers. `recordId` is the decision record that the reading left. A card read before wave 9 has `area` and one `urgency` score instead of `typeOfWork` to `riskPrelim`. The field is null before triage ran or when no model could read the task. Each task also carries `record` (triage's `TriageRecord`) and `evidence` (the `EvidencePack`). The pack holds `format` (`video`, `captures` or `text`), `summary`, `scenarios`, `findings`, `outOfMap`, `risk`, `rollback`, `howToVerify` and `commitSha`. It holds `media[]` of `{ kind, label, url, localPath?, scanned? }`. `scanned: false` marks an image whose text the machine could not read. The machine uploads that image only after a person approved the preview. The pack also holds `results` by layer, `findingsDetail`, `diffSummary { what, why, files, added, removed }`, `revision` and `source`. A scenario `result` can be `not_run`. The pack holds a `note` when the machine degraded a format or a part was missing. For a video, it holds `video: { file, durationS, verdict: ship | one_more_pass | degraded, scores, defects[], rounds, transcript?, confidence? }`. Both fields are null until a stage writes them. Each task also carries `archiveReason`: `duplicate`, `sla_expired`, `rejected`, `not_for_agent`, `pr_closed`, `no_setup` or `no_answer`. It is null unless the task is `archived`. |
| POST | `/tasks` | Create a task. The body holds title, description, criteria, repo path and source. For a Luna Notch work order, the source is `source.kind: notch` with `{ ref, id, jiraKey? }`. `start: true` starts the task in the same call. `stages` (`{ "<pack>": "<engine>" }`, e.g. `{ "triage": "claude:opus" }`) sets the task's own engine per pack. It wins over the repo's `luna.yaml` `engines` and the pack's default. The call answers 400 for an engine that the pack does not allow (`GET /packs`). It also answers 400 for a pack that never runs in a task (`slack_triage`, `jira_intake`, `triage_signals`, `chat_triage`, `eval_judge`). An `Idempotency-Key` header holds 1 to 200 characters, and the machine keeps it on the task. A retry with the same key and body answers the task already made (200, no second task, started once). The same key with another body is 409 `idempotency_conflict`. Its `taskId` names the task that the key made. "The same body" is the same order with every default filled in. The defaults are `description: ""`, `criteria: []`, `repoPath: null`, `source: null`, `stages: {}` and a source's absent `jiraKey` as null. The compare leaves `start` out. So an equivalent retry is never a conflict. A key from before this rule keeps matching a retry of the body that the client first sent with it. Without a key, every call makes a task (201). |
| GET | `/tasks/:id` | One task with its stage runs, approvals, recent events and artifacts. Jira events: `jira.linked {key, url, created?}`, `jira.unlinked {key}`, `jira.transitioned {from, to, fields?}` and `jira.blocked {wanted, current, why}`. `jira.commented {url}` means that the "PR opened" comment went out for that url. That event stops a repeat after a restart. `jira.commented {kind: "shipped", number}` means that the shipped summary went out once. `task.shipped {title, prUrl, number, mergedSha, by, format, howToVerify, media}` means that the task's PR merged. `by` is `machine` or `person`, and `media` has web urls only. `jira.moved {status, key}` means that the issue reached Done, Cancelled or Won't Do in Jira while the task is open. Intake makes `jira.intake {key, verdict, reason}`. A verifying run carries `cases: [{ title, ok }]`, one verdict per approved case, from the pack's `results[]`. It is null when the pack reported none. Every stage run carries `engine`, the engine it started on. It is null for a host-only stage or a run from before engines. Every stage run also carries what its result named it ran on. `runtime` is `claude`, `eve` or `jev`. `modelId` is the pinned model ID. `sdkVersion` is the runtime's SDK version as installed in the image. `fingerprint` is a sha256 over the template, role, skills, access, answer schema and factory rules it ran. See [architecture](architecture.md#factory-mode). Each is null for a host-only stage, a run still going or one from before fingerprints. `stage.engine {pack, engine, reason}` says why the machine passed over an engine that someone asked for. The pack did not allow the engine, or this machine had no credential for it. In that case the pack's default ran. `task.stages {stages}` records each change of the task's engines. Every task carries `stages`, its own engine per pack (`{}` when it names none). `reports {build, verify}` are the v2.2 Build Report and Verify Report. The Build Report is on the passing `implementing` finish as `detail.report`. The Verify Report is on the passing `ci_watch` finish. Each is null until its stage has passed. A stream event carries `names`, the v2.2 diagram's name or names for the fact. It is absent when the fact has none. |
| GET | `/tasks`, `/tasks/:id` (card fields) | Every task also carries `sources` (the first is `source`), `reporter`, `hints`, `originMachine` and `attachments`. The `attachments` are references: name, url, mediaType, size. A task also carries `project`, `owners`, `followers`, `links`, `demand`, `merged`, `mergedInto` and `related`. Once started, it carries `history`, `resolved` and `dedup`. `dedup` holds the shortlist, answers and outcome of the duplicate check. A row from before reads as one source and empty lists. `POST /tasks` accepts the same fields. |
| PATCH | `/tasks/:id` | Edit the ticket's text (title, description, criteria, repo path). `source` never changes once the task exists. Another source is 400 `source_immutable`, and the same one again is no change. The repo path moves only while the task has no worktree or branch. Else the call is 409 `has_worktree`, and the same path again is no change. A refused edit changes nothing. |
| GET | `/tasks/:id` (ship) | `ship` is the watched PR as the board shows it, built from the ship cursor. It is null for a card with none. Its shape is `{ pr { slug, number, url }, head, ready, checklist [{ id, ok, detail }], autoMerge { allowed, reason }, review { required, by }, fixRounds, queued, quietSince, lastEvent { class, at }, at }`. The machine flattens and caps the details. The field holds no reviewer text and no thread. `EvidencePack.fixes` (at most 20: `{ sha, scope, summary, at }`) lists the fixes after review. The release question is an `awaiting_ship` approval whose `requested` holds `gate: "ship_approval"`, `head`, `prUrl`, `number`, `risk`, `checklist`, `question: "safe to release now?"`, `releaseOwners` and `evidence`. It has two answers. For `approved`, the approver must not be one of the plan's approvers, else `409 not_release_owner`. `rejected` archives the card, with `ship.override { kind: "rejected_ready" }`. |
| POST | `/tasks/:id/findings/:findingId/dismiss` | A person dismisses a finding that the last Verify reported, while the card waits at `awaiting_ship`. The body is `{ "reason"? }`, at most 500 characters. The machine keeps the reason as ground truth, out of the stream. The call is `409` at any other state, and `404` for an id that the last Verify did not report. It logs `finding.dismissed { id }`. |
| POST | `/tasks/:id/findings` | A person adds a finding Verify missed: `{ title, severity: blocker \| should_fix \| nit, path?, line? }`. Logs `finding.added { severity }`. |
| - | events of Ship | `ship.merged` is the merge, with the merge commit that GitHub reports. The machine still reads `task.shipped` rows and the stream message of that name. `ship.event { kind, class }` carries a class that is an enum value: `review_comment`, `ci_flaky`, `ci_real`, `conflict`, `base_moved`, `freeze`, `blocked_by_other_pr`, `noise`. The other events are `ship.override`, `finding.dismissed`, `finding.added`, `evidence.edited { sha, bytes }`, `sla.reminder { gate: "awaiting_ship", quietDays }` and `sla.escalated { gate: "awaiting_ship", afterDays, to }`. A container cannot write any of them: the machine stores its lines under `stage.`. |
| PATCH | `/tasks/:id/plan` | Edit triage's plan while it awaits your approval. You can also edit it later, while the task is `awaiting_test_check`. Build has made nothing yet then: the edit changes the approved plan, and the ticket's criteria follow. The body is `{ "brief"?, "criteria"?, "assumptions"?, "steps"?, "rollback"?, "risk"?, "map"? }`, with at least one field. Only the fields given change. `steps` is `[{ description, files[], done_when[], est_loc }]`, and the slices that Build reads follow them. `risk` is `{ level: low \| medium \| high, reason }`. The machine's own level is a floor. A higher level applies at once. The machine keeps a lower level with its reason (`requested.overrides.risk.applied: false`). The approvers rule and Ship keep reading the higher level. `map` is `{ components?, files: [{ path, role }], entry_points?, owners?, reason }`. The machine keeps it with its reason as ground truth. Every text has a bound (400 on more). Any edit raises the Plan's `version` and clears the approvers so far. Once a person approved the plan (the legacy `awaiting_test_check` edit), the machine refuses `steps`, `risk`, `map` and `rollback` with `409 plan_approved`. Each edit appends `{ at, before, after }` (changed fields only) to the approval's `requested.revisions`. It also logs a `plan.edited` event with the field names. 409 `no_plan` at any other state. |
| PATCH | `/tasks/:id/record` | Correct the Triage Record while the task waits at a gate. The body is `{ "kind"?, "typeOfWork"?, "size"?, "riskPrelim"?, "priority"? }`, with enum values only. It needs at least one key and no other key (400). `kind` is `bug`, `feature`, `task`, `chore`, `question` or `incident`. `typeOfWork` is `frontend`, `backend`, `infra`, `data`, `docs` or `mixed`. `size` is `XS` to `XL`. `riskPrelim` is `low`, `medium` or `high`. `priority` is `P0` to `P3`. The record's `version` rises, its `decisionBy` is `person` and `editedFields` names what changed. The machine writes each corrected field except the priority as ground truth (`source: record_edit`). It writes the field onto the `triage_signals` decision record that read it. The machine keeps and shows a lower `riskPrelim` than its own. But the risk that the plan's floor and the approver and ship rules read stays at the higher of the two (`record.riskMachine`). A higher one applies at once. 409 `record_locked` when the task has no record or is not at `awaiting_answers` or `awaiting_approval`. Answers the task. |
| POST | `/tasks/:id/questions/post` | A person's tap (`p` on the board) posts the open questions at `awaiting_answers` where the card came from. It posts them as one flattened comment. The machine posts the questions it built from the signals by itself. An agent's own questions wait for this tap. The call is idempotent: the machine posts the same questions once, and `posted` says whether this call did. 409 `no_questions` away from that gate. 409 `secret` when a question carries a token-shaped string. |
| PATCH | `/tasks/:id/cases` | Replace test_design's cases while the task is `awaiting_test_check`: `{ "cases": [{ "title", "criterion", "approach" }] }`, at least one. The open test-check approval keeps its other fields. The call logs a `cases.edited` event. 409 `no_cases` at any other state. |
| PATCH | `/tasks/:id/stages` | `{ "stages": { "<pack>": "<engine>" \| null } }` sets the task's engine for each pack named. `null` goes back to `luna.yaml`'s engine, else the pack's default. The other packs stay. The call answers the task and publishes `task.updated`. 400 for an engine that the pack does not allow or a pack that never runs in a task. 409 `stage_started` when a pack named has already run or is running on this task, and then nothing changes. |
| GET | `/tasks/:id/diff` | The task branch against its merge base with the base branch: `{ base, head, files: [{ path, status: "A"\|"M"\|"D"\|"R", added, removed }] }`. The base branch is origin's default branch, else `main`, else the repo's HEAD. `?file=<path>` adds `patch`, that file's unified diff. ## Who may call

The machine's clients are the board, Luna Notch and scripts. None is a web page. Every request passes these checks in order. This applies to every route, including `/events` and `/health`. The checks are in `machine/src/adapters/http/access.ts`:

- **Host**: while `MACHINE_HOST` is a loopback address, a `Host` header must be `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>`. Any other host gets 403 `forbidden_host`. This stops a DNS name that rebinds to 127.0.0.1. Beyond loopback, the machine skips the check and requires the token instead.
- **Origin**: only browsers send one. Any origin but the machine's own gets 403 `forbidden_origin`. The machine's own origins are `http://127.0.0.1:<port>` and `http://localhost:<port>`.
- **Token**: when you set `MACHINE_API_TOKEN` (env, else `~/.config/hardness/machine-api-token`), each request needs `Authorization: Bearer <token>`. Without it, the response is 401 `unauthorized`. A machine that binds beyond loopback with no token refuses to start. The board and the golden scripts read the same variable and file.
- **Body**: a request that sends a body must say `Content-Type: application/json`. A `; charset=…` is fine. Any other type gets 415 `unsupported_media_type`. A page can send that type across sites only after a CORS preflight. The machine never allows a CORS preflight. So a cross-site form or `no-cors` fetch cannot create, start, merge or close anything.

## What a run was refused

A stage logs `sandbox.egress_blocked` on the card. It logs one row for each refused (host, port, via), at most 20 for each stage. After that it logs one `{ step, more }` row. The payload is `{ step, host, port, via, reason, count }`. The `step` is `stage`, `check`, `install`, `app`, `seed` or `deploy`. The `via` is `connect`, `http` or `dns`. The `reason` is `not_listed`, `address`, `private_address`, `sni_mismatch`, `unresolved` or `head_too_large`. The host is text that a container chose. The machine flattens and caps it, and replaces the value of a secret in it. A container cannot write this kind, because the machine reserves it. The board shows it as `blocked: host:port (step, via)`.

## Example session

```sh
curl -s -X POST 127.0.0.1:4317/tasks -H 'content-type: application/json' \
  -d '{"title":"Login page","criteria":["Bad password shows an error"]}'
curl -s -X POST 127.0.0.1:4317/tasks/<id>/start
curl -s -X POST 127.0.0.1:4317/tasks/<id>/decision -H 'content-type: application/json' \
  -d '{"decision":"approved"}'
curl -sN 127.0.0.1:4317/events      # live updates
curl -s '127.0.0.1:4317/metrics?since=7d'   # factory metrics (7d, 30d or ISO): cycle time, first-pass, escalations, cost; also streamed as task.metrics
curl -s '127.0.0.1:4317/metrics?groupBy=repo'   # the same, plus one row per repo
curl -s '127.0.0.1:4317/metrics?groupBy=engine' # the same, plus one row per engine
curl -s '127.0.0.1:4317/metrics?groupBy=fingerprint'   # the same, plus one row per harness fingerprint
```

Give a task a `"repoPath"` so the agents have a repo to work on.

## Change size and stacked cards (wave 15)

- **A task's stack.** `GET /tasks` and `GET /tasks/:id` carry the card's own fields as they are: `splitFrom`, `splitPart` (`{ n, of }`), `splitInto`, `dependsOn`, `base` (`{ card, branch }`), `riskFloor` and `startWhenReady`. They hold ids, numbers and enum values only. A card with none of them shows none. A client's `POST /tasks` cannot set them.
- **Events** the pipeline alone logs (no container can): `card.split`, `card.child`, `card.held` (`reason`, `waitingOn`, `text`), `card.released`, `size.overridden` and `stack.retargeted`. The ship watch logs `ship.event { kind: "stack", class: "parent_changed" | "parent_merged" }`.
- **The backlog.** Each entry of `GET /backlog` has `schedulable` and `blockedBy` (`{ id, kind: "card" | "item", state }`). `POST /backlog/:id/promote` of an entry that is not schedulable answers `409 not_schedulable` with `blockedBy`. The machine removes nothing. The machine makes a promoted card with `dependsOn` for its card dependencies. The other items that named it now name the new card.
- **A ticket's split.** A ticket whose recommendation is `split` gets a draft of kind `split`. The draft has `children`, numbered `text` and `created` once you approve it. The ticket gets the status `split_proposed`. With no valid split, the ticket has no draft. Its assessment says `split.failed`, and its status is `needs_decision`. `POST /tickets/:key/approve` on the draft creates the child tickets in the origin's own project or repository. A failure partway leaves the draft waiting with `created`. Approving again goes on. The same call marks the origin `epic` and posts one comment that lists the keys. Editing the draft gives `409 ticket_refused`. The assessment carries `sizeEstimate` (`estLoc`, `estFiles`, `reviewable`, `confidence`).
